<a id="finding-simplifications"></a>

# 寻找简化机会

用于调查明确范围内的简化机会，并在已有授权下实施。先确认消费方和既有约束，再比较维护成本与收益，形成可核验的候选结论；不是每次开发都要执行的清单。

| 本次任务 | 执行范围 |
| --- | --- |
| 寻找机会或评审方案 | 只读调查，输出候选、依据、取舍、验证要求和未覆盖项 |
| 实施已确认的简化 | 核对候选仍成立，按授权修改，完成项目要求的留底与验证 |
| 吸收其他分支或 PR 的方案 | 额外核对真实比较基线和独立贡献，按下方条件流程执行 |

<a id="scope-and-permissions"></a>

## 执行范围与权限

从用户指定的文件、目录、模块、当前差异或可唯一确定的上下文确定范围，不自动扩大到整个仓库。评审只报告发现，修改须在授权范围内；需要逐项讨论时按用户要求进行，不使用模式参数决定写入权限。排除 `vendor/`（包括经符号链接进入）和项目已有的冻结归档笔记；归档位置与创建条件见 [Agent Notes 目录约定](../weetion-doc-archive-agent-notes/SKILL.md#basic-framework-contract)。仅为理解历史入站引用读取归档的精确目标，不修改快照或其出站链接。搜索须显式传入范围，并将排除项置于包含规则之后。依据实际来源区分生成物和手写测试数据，不凭 fixture 或快照名称排除；生成内容从已授权的源内容或场景修改并重新生成，影响输入、断言、提示词或可见行为时执行相应验证。

纯调查或评审不自动写 Note、加 TODO 或删除内容；用户要求留存调查结论时，按记录授权执行。实施简化时，项目要求的相关 Note 属于交付内容，按下方[留底规则](#write-the-agent-note)办理，不因本技能而额外索取一次独立的记录编写授权。删除、归档及扩大范围仍遵守项目的确认要求。相关笔记核查限定于候选项涉及的决策，不自动开展全仓库笔记审计。

<a id="start-with-repo-context"></a>

## 从仓库上下文开始

- 从目标项目根目录及目标文件所在目录层级查找适用的 `AGENTS.md`，按其指引读取任务相关的开发、防御式编程和测试规范。路径从目标项目解析，不从技能安装位置推算；不存在的规范文件不要求补建。
- 判断模块前，定位该项目实际维护的架构说明，结合代码确认模块职责、依赖方向和运行时边界；与已记录架构约束冲突的简化需要额外证据，不假定模块位于 `packages/`。
- 按 [weetion-doc-archive-agent-notes 的项目约定查找规则](../weetion-doc-archive-agent-notes/SKILL.md#read-the-contracts)定位目标项目的活动决策记录，只读取与候选项相关的依据及必要历史引用，理解有意采用的架构；不存在记录时依据代码和其他可核实证据判断，不要求原项目示例笔记存在。
- 以目标项目已确认的设计、受支持能力和兼容承诺为约束，不预设适配器数量、存储格式或框架。推翻已有设计须说明原理由为何不再成立、替代方案的证据及影响，并获得对应变更授权；在不破坏这些约束时，仍可调查内部未使用的实现或重复机制。

<a id="what-counts-as-a-strong-candidate"></a>

## 什么是有力的候选项

有力的候选项必须有证据表明维护成本确实高于收益。以下情况是调查线索，不是删除指令：

- 接口、配置、事件、模块或辅助实现疑似未使用；按下方[消费方核查](#prove-or-reject-each-candidate)确认真实用途、动态调用、外部消费方及兼容义务。
- 只被测试或文档引用的内容，经核实不再承担回归保护、兼容承诺、运维、开发工具或示例验证职责。
- 多种表示重复维护同一事实，且合并不会丢失不同的时效、所有权、历史记录或兼容语义。
- 抽象要求各实现支持没有实际需求的方法，或独立模块带来额外发布与依赖成本；须比较其复用、隔离、工具及演示价值，不能因非生产用途直接删除。
- 泛化能力缺少已确认需求与实际用途，同时引入可测或可说明的维护成本；不根据多会话、后台任务等功能名称判定过度设计。
- 防御、回滚或专用测试只服务于已确认不再支持的行为，且没有独立保护职责或仍需处理的历史数据。
- 手工实现与目标技术生态中维护良好的依赖或最低支持运行时的内置能力重叠；评估实际可移除的实现、专用测试及新增维护成本，遵循[依赖替换要求](#hand-rolled-code-versus-a-dependency)。

简化默认保持可观察行为，包括返回值、错误、副作用、顺序、持久化及兼容约定。涉及行为变化时，明确前后差异、消费方影响、迁移或兼容措施及验证要求，获得对应变更授权后实施；“新行为合理”或“更容易解释”不能代替这些证据。

修正拼写、静态分析工具的一次报告、搜索零命中或“看起来复杂”的印象，都不足以证明某项机制可删除，也不足以单独支撑重大简化提案。证据不足时报告待核实内容，不把未查到当作不存在。

<a id="audit-invariant-companions"></a>

### 审计不变量配套模块

按能否发现实际错误评估检查模块：说明它保护的约束、可捕获的失败，以及现有替代检查是否覆盖同一阶段和失败路径。比较独立来源的观测可以提供有效证据，但启动检查、配置校验、服务注册验证和简单断言也可能保护真实约束，不能因形式简单而删除。

对恒真、自我验证或重复检查，先确认是否仍有执行路径、异常传播、集成连接或回归保护价值。只有证明没有独立价值，或已有等效覆盖，并获准实施后，才移除相关检查；不能通过删除测试或放宽断言掩盖问题。同步处理已确认只供该模块使用的导出、构建入口、依赖、测试和文档，保留其他消费方仍需的内容。

<a id="survey-broadly"></a>

## 广泛调查

用户要求广泛调查时，先按目标与实际结构划分需要覆盖的领域，再选择独立执行或多智能体协作。仅在任务可拆分、工具可用且适用授权允许时使用子智能体，不因范围广或希望找到多个候选项而强制并行。可用领域包括：

- 核心业务与数据：业务流程、状态转换、持久化、缓存、迁移及恢复。
- 接口与集成：公开 API、协议、适配器、配置加载及外部消费方。
- 并发与资源：取消、任务所有权、异常传播、清理及进程或线程协作。
- 展示与交互：页面、文案、交互状态；实际涉及模型时再检查提示词、工具接口及输出处理。
- 模块与工程支持：模块拆分、依赖、构建、脚本、运维、测试及示例。

按目标项目真实结构选择适用领域，不要求项目具备上述全部组件。

委派时明确子任务范围、排除项、需要提交的证据，以及只读或修改权限；子任务不能扩大原任务授权。尽量分配可独立核查的领域，说明共享边界，避免重复调查；涉及写入时明确文件归属和交接方式，避免并发修改冲突。

主执行者必须复核子智能体的关键证据、实际消费方及行为影响，合并重复候选并解决相互矛盾的结论。子智能体报告是待核实的输入，不能直接作为已验证事实；无法复核的部分明确标为证据缺口。

无论是否使用子智能体，都应覆盖已承诺的范围。优先检查与目标相关、维护成本高或已有证据指向的部分；文件大小和差异量仅是线索，不替代用途判断。不要因找到第一个候选项就提前结束，也不要只检查易发现的未使用符号而漏掉范围内的生命周期或防御机制。

当约定范围已检查、候选项已按证据确认或否决、仍未解决的证据缺口与重要取舍已说明时，结束本轮调查。无法覆盖的部分须具体报告，并标明结果仅为部分调查，不声称全面完成；需要扩大范围时另行确认。候选数量不是完成指标，允许结论为“未发现值得实施的简化”，不为凑数提出薄弱建议或无限扩展调查。

<a id="simplify-prose-with-the-code"></a>

## 与代码一同简化文字

仅在调查涉及注释或文档时读取[表达与语义保留规则](../weetion-doc/references/style.md#clear-technical-expression)。先确认需求变化、分析依据、方案取舍、行为约束和验证证据在对应记录中有完整归属，再清理重复或无独立事实的叙述，不能用简化抹去唯一依据。

保留必需注释、失败与边界条件、项目框架说明及定位入口；按项目规范和资料用途判断是否重复，不因能够搜索源码就删除维护者需要的说明。具体执行见[文档评审规则](../weetion-doc/references/review.md#redundancy-and-expression)。

<a id="audit-trust-and-lifecycle-boundaries"></a>

## 审计信任与生命周期边界

对每次防御性复制、冻结、验证和回调捕获，追踪输入来源、校验位置、数据所有权、共享引用、可变性及后续使用时机。按实际语言运行时、插件权限和并发模型判断可信范围；同进程、静态类型或只读声明本身不能证明运行时输入可信或对象不可变。

先确认防御措施保护的具体失败路径及项目威胁模型，再判断是否冗余。反射、动态加载、外部插件、回调重入或并发修改在适用场景下都可能构成真实风险；没有证据时，不把相关测试认定为推测，也不扩展无关的假想风险。移除措施前须证明保护职责已不适用或已由其他机制等效承担。

对于复杂异步代码，梳理所有权和状态转换，将状态标记、异步完成信号、取消路径与释放操作对应到实际职责。多个机制描述相近状态时，先核对触发时机、可见性、失败、重入和清理顺序；只有证明职责重叠且合并保持这些语义时，才提出合并方案，不预设必须改成事务或单一控制器。独立保护发布与回滚、回调隔离、终态裁决、线程／进程所有权或完全清理的机制应保留。

<a id="hand-rolled-code-versus-a-dependency"></a>

## 手工代码与依赖

依赖替换可以作为简化候选，准入及审批要求遵循目标项目实际的依赖政策；不以原项目历史笔记替代当前项目规则。调查协议解析器、分帧器、重试／退避循环、glob 匹配器、差异引擎和类似基础设施时，应询问：目标技术生态中维护良好的依赖或项目最低支持运行时的内置功能，是否已经提供相同能力？

像验证其他候选项一样验证依赖替换方案，并额外执行以下检查：

- 阅读手工实现，并明确外部包覆盖的确切范围；外部包未覆盖的剩余语义计入替换成本，在调查结论中说明，实施时纳入相关 Agent Note。
- 如实检查包的健康程度（维护情况、使用广度、传递依赖规模），如果最低支持版本已具备内置能力，则优先使用内置能力。
- 核对候选项相关的活动决策、接口及兼容承诺。会推翻既有设计的替换方案，必须解释原理由为何不再适用并提供更充分的证据，不能仅凭“可以引入依赖”要求替换。
- 衡量净删除量：实现加专用测试加文档，再减去剩余衔接代码。只是把同样复杂度换个位置的包装层，不算收益；仅增加未来能力的依赖属于功能决策。
- 记录实际维护责任的减少、未覆盖语义及供应链影响，包括项目要求的许可、兼容性、安全维护与更新责任。没有明确依赖政策时按这些证据评估并报告未决条件，不推断为一律禁止或无条件准入。

<a id="prove-or-reject-each-candidate"></a>

## 验证或否决每个候选项

对每个符号或行为，先分类其消费方，再编写内容：

- 运行时与外部消费方：实际入口、部署配置、任务、动态加载、插件注册、公开接口和受支持的仓库外调用方。
- 工程与运维消费方：测试、构建、发布、迁移、排障、开发工具及可运行示例；不直接服务生产请求仍可能承担必要职责。
- 文档与兼容依据：接口说明、决策记录、历史数据、协议格式、快照及生成物；核实它们是否记录有效承诺或被其他工具消费。
- 归属不明确的内容：继续追踪真实入口和使用方式，明确证据缺口，不按目录名、文件类型或未查到调用直接判定无用。

首先使用 `rg` 搜索精确符号、事件名、模块名、配置键及协议字符串，再按目标语言的调用、注册和加载方式追踪消费方。结合构建清单、导出声明、部署配置、反射或动态加载入口、测试及文档核查，不把文本搜索等同于完整调用图。公开接口、外部插件或历史数据的使用范围无法核实时，应标明未知并暂缓删除；在固定排除范围内的内容也不能因未读取而认定不存在消费方。

出现以下情况时，否决候选项或降低其优先级：

- 存在受支持的消费方或兼容义务，却没有保持行为的替代方案、迁移措施或对应变更授权；存在调用方不妨碍保持行为的内部简化。
- 已实施 Agent Note 或来之不易的防御式模式明确说明了 API 的合理性，而新证据不足以推翻该理由。
- 删除会迫使无关内容发生大面积改动，却没有实际减少公开 API 或必需行为。

改动小本身不是否决或延期理由。证据充分、收益明确且在实施授权内时，可以直接完成局部简化；是否需要 Note 按变更性质判断，不按行数判断。未获实施授权或暂不实施的候选，在结论中说明原因；只有需要在源码保留明确后续入口且写入已获授权时才使用 [TODO](#inline-todo-notes)。

<a id="write-the-agent-note"></a>

## 实施留底与相关决策记录

编写门槛、格式、替代关系和生命周期统一遵循 [Agent Note Skill](../weetion-doc-archive-agent-notes/SKILL.md#when-to-write-a-note)。非小改动在同一次变更中留底，保留需求变化及来源、消费方证据、分析依据、保留现状的最有力理由、真实备选方案、放弃的能力、关联实现和验证缺口。调查中被否决的方案若影响本次决定，也应保留否决依据；没有考虑过的方案不得编造。

简化记录须具体指出拟删除、合并或迁移的对象及所属文件，区分运行时、工程与运维、文档与兼容消费方，说明可观察的验收条件。提案与已实现记录使用各自状态的格式；已有记录负责同一决策时更新实现事实，决策或理由改变时另建记录并交叉链接，不能仅因主题重叠就覆盖旧决定。

新增记录时检查相关替代关系；只有任务包含笔记整理或本次实现影响旧记录时，才处理对应记录，不扩大到全库。部分替代保留双方，完整合并须承接全部独有依据、备选方案、后果、必要验证及覆盖缺口，修复入站链接和项目要求的关联文件；具体条件见[完整承接规则](../weetion-doc-archive-agent-notes/SKILL.md#check-supersession-when-adding-a-note)。判断成立不自动授权删除，冻结归档仍不得修改。

功能移除只有在生产代码、配置、schema、持久化或协议格式、迁移、兼容行为、当前文档及受支持行为测试中均不再保留该能力时，才可能构成完全替代；一种传输、默认值、实现或展示方式被移除仍可能只是部分替代。原始动机、移除原因、其他方案、放弃的能力、重新引入条件和删除完整性证据须有归属。旧实现清单和仅验证已删除行为的测试不能当作当前验证证据；有独立约束价值的否定性决定继续保留。

<a id="inline-todo-notes"></a>

## 未实施的小项

需要在源码保留后续入口且写入已获授权时，可按项目约定使用 TODO/FIXME/XXX，写清具体对象、已有依据、待做动作及必要前提。项目未定义标签或紧急程度时不自行套用其他项目的分级。它不代替本应编写的 Agent Note，也不承载推测性抱怨；纯调查只在报告中列出未实施项。

<a id="when-folding-another-pr-or-branch"></a>

## 涉及其他分支或 PR 时

仅在任务涉及跨分支方案时，依据真实目标分支、依赖关系及本地可用引用确定比较基线，区分独立贡献与继承改动，不固定远端或分支名。基线不明时说明缺口并澄清，不猜测，也不自动切换、重置、合并或推送。

移植须有对应授权，承接有证据的方案及其原始依据，核对重叠记录属于同一决定还是新的取舍，并按上方留底规则处理；不为保留数量重复移植。创建或更新 PR、发布评论、关闭 PR、提交、推送及改变评审状态，只在任务明确包含相应操作时按目标项目流程执行；调查或本地编辑不附带这些权限，也不要求创建 PR。关闭重复 PR 前须确认有效内容已有归属并保留关联；未完成的工作或必需检查不得表述为已具备交付条件。

<a id="validation-and-pr-hygiene"></a>

## 验证与交付

只读调查报告已核实的事实、方法与证据缺口，不把静态分析写成行为测试通过。实施后按项目入口运行相关及必需检查，验证最终修改版本、受影响的真实消费方、行为保持或已授权的行为变化；不能删除测试或放宽断言来获得通过。生成内容核对来源和衍生产物，Git 工作区执行适用范围的差异检查，未跟踪文件也须覆盖。

交付说明调查范围及未覆盖部分、各候选确认或否决的依据、实际改动与收益、方案取舍和验证结果。列出相关 Note 的归属与完整或部分替代关系；发生合并时给出旧记录、当前负责记录、内容承接及删除依据。所有命令、结果、未验证项和剩余风险据实报告；无值得实施的候选也可作为完整结论，不以候选或删除数量评价完成。
