<a id="trimming-chain-of-thought-leakage"></a>

# 清理文字中的创作过程残留

本技能处理持久文字中的创作过程残留：依赖私人会话或未交付草稿的引用、混入当前行为说明的过程叙述，以及不能帮助维护者理解事实的评审辩解。是否需要清理由文档用途、证据与完整语义决定，不按关键词机械删除。改写须保留事实、必要理由和行为约束；暂时无法核实的内容标明疑点，不能仅因缺少访问条件就删除。改写时读取[表达与语义保留规则](../weetion-doc/references/style.md#clear-technical-expression)，已有有效上下文可复用；[可独立定位的引用](#resolvable-citations)说明引用要求及理由。这是指导原则，不是脚本。

<a id="the-one-test"></a>

## 判断依据

先确定任务对应的版本或交付范围，以及文字的用途：当前行为说明、提案、历史记录或审批记录。读者能否在不依赖私人会话的情况下定位依据，并核实与该版本有关的主张？核对目标版本、文档路径与来源内容，不一律要求在 Git `HEAD` 上成立；同次变更新增且纳入交付的文档可以引用，非 Git 项目按实际交付范围判断。

区分三种情况：已证实失效的引用应修复或移除，但保留仍成立的事实；暂时无法访问或证据不足的内容保留疑点并报告，不改写成已证实错误；已核实的引用还须判断是否适合当前位置。能解析不等于事实正确，也不等于应在当前行为说明中保留全部历史叙述。

<a id="resolvable-citations"></a>

## 可独立定位的引用

持久文字应引用在目标版本或交付范围内可定位的归属文档、议题或权威外部来源；同次变更中的新文档不必先单独提交。引用其他文档时，在文件内至少给出一次路径或稳定链接，后续可用可搜索的名称指代；没有外部依据依赖的文字不强制添加引用。核实引用对象及其支持的事实，不能只因编号或链接形式正确就视为有效。读者不应依赖已关闭的会话、无归属的设计序号或不在交付范围内的草稿还原依据。

有归属文档的会话序号，改为决策名称和文档路径；已确认不存在可交付依据时，删除失效引用，将仍成立的事实改写为独立陈述。无法核实是否存在依据时，报告缺口，不据此删除。不要为了保留序号而要求提交整份会话记录，也不要连同引用一起删除必要理由。当前行为与历史证据的归属遵循 [weetion-doc 的事实归属与历史记录规则](../weetion-doc/references/structure-hierarchy.md#fact-ownership-and-history)；Agent Note 的维护遵循 [weetion-doc-archive-agent-notes](../weetion-doc-archive-agent-notes/SKILL.md)。

<a id="taxonomy"></a>

## 分类体系

1. **失效的设计会话引用**——例如 `(decision 7)`、`(audit C2)`、`design §4.7` 或阶段代号。先核实是否有可定位的归属文档；存在则引用名称和路径，已确认失效则移除引用并保留有效事实。不能仅凭编号形式判定失效。
2. **堆叠和 PR 视角**——当前行为说明中的“本 PR 新增”“后续 PR 实现”等应改为该版本的真实能力；仍有效的待办按项目约定记录。PR 描述、发布说明及工作流文档可以按用途描述变更，不为消除将来时而把计划写成已交付。
3. **变更叙述和版本标记**——当前行为说明应直接陈述机制和约束；历史记录、复盘及迁移指南可以保留相关的前后差异。明确版本、协议标识、运行时时间，以及有清楚指代的“本版”不因用词被禁止；只有依赖未知创作时刻的指代才需补明范围或改写。
4. **评审过程描述**——不影响长期理解的轮次、草稿序号或争辩可以精简，保留有效决策及理由。必要审批、责任归属和审计记录可在项目要求的位置保留有依据的人物、时间与结论；人的确认不能单独证明技术正确性。
5. **写给评审者看的辩解**——将纯粹辩护改为可核实的不变式、条件及失败后果；代码已清楚表达的重复内容可以删除。不要仅因出现“因为”或“安全”就删除必要理由，也不能将待验证的安全假设写成保证。
6. **复述和推导过程记录**——删除没有新增信息的控制流或测试步骤解说，保留不明显的约定、不变式及操作指南中必要的步骤与验证。
7. **含糊措辞和规划残留**——按证据说明真实界限与不确定性；确有后续工作且任务授权时，按项目约定记录待办。不得为了改写“应该够用”而编造测量、保证或新增需求。
8. **创作语言残留**——结合目标文档语言、句意和上下文识别未完成的翻译、会话分隔符或仅供创作者使用的片段。按[语言与项目约定](../weetion-doc/references/style.md#clear-technical-expression)改写仍有意义的内容，只删除没有独立信息的残留；标识符、术语、原文引用和有意的多语言内容不因语言不同而视为泄露。

<a id="what-is-not-leakage"></a>

## 哪些不属于泄露

仅凭直觉清理引用会在两个方向上出错：删除可长期使用的引用，保留失效引用。结合用途与证据应用以下保留规则；判断有歧义时，按问题读取[示例](references/examples.md)的对应章节，不默认通读全部示例：

- **议题与待办**——核实议题所属项目、真实目标、状态及其与当前文字的关系；跨项目或可能歧义时使用完整链接。`TODO(name):` 只是标签，不自动构成有效外部引用。有效且适合当前位置的内容可以留在 README；无法访问时报告未核实，不默认有效，也不直接删除。
- **Agent Notes 和事故复盘（postmortem）中的已合并 PR 与议题引用**——依照 [weetion-doc 的事实归属与历史记录规则](../weetion-doc/references/structure-hierarchy.md#fact-ownership-and-history)，它们属于允许保留的证据。
- **抑制检查的理由**——抑制、排除或有意忽略异常仍存在时，应保留有效理由；理由错误时核实真实依据，不能补造借口。相应抑制或机制已移除且没有其他用途时，可在授权范围内同步清理过时说明。
- **现在时反事实回归约束**——“没有 X，就会发生 Y”“朴素的 X 会……”。
- **实测界限**——保留“实测”等证据性质说明，以及可追溯的版本、环境、方法和结果；示例数字不是项目测量结果。过时数据标明适用范围或重新测量，不能去掉来源后当作固定保证。
- **运行时旧/新状态**——“旧连接排空之后，新连接才开始接受请求”描述的是运行时生命周期，不是变更历史。
- **历史、版本及审批记录**——在决策记录、复盘、发布或迁移说明等适当位置，保留有依据的阶段、版本、人物和时间；明确所指对象，不把当时结论冒充当前事实。
- **外部与章节引用**——标准章节、设计稿名称及文档内部编号可以使用，但须定位来源并核实其确实支持主张；章节符号、画框名称或文档标题本身不证明有效。
- **项目语气和文体形式**——作为项目口吻的“我们”；笔记中的“已考虑的备选方案”章节。

<a id="scope-and-permissions"></a>

## 执行范围与权限

从用户指定的文件、目录、模块、当前差异或可唯一确定的上下文确定范围，不自动扩大到整个仓库。评审只报告发现，修改须在授权范围内；需要逐项讨论时按用户要求进行，不使用模式参数决定写入权限。排除 `vendor/`（包括经符号链接进入）和项目已有的冻结归档笔记；归档位置与创建条件见 [Agent Notes 目录约定](../weetion-doc-archive-agent-notes/SKILL.md#basic-framework-contract)。仅为理解历史入站引用读取归档的精确目标，不修改快照或其出站链接。搜索须显式传入范围，并将排除项置于包含规则之后。依据实际来源区分生成物和手写测试数据，不凭 fixture 或快照名称排除；生成内容从已授权的源内容或场景修改并重新生成，影响输入、断言、提示词或可见行为时执行相应验证。

<a id="workflow"></a>

## 工作流

先按任务选择执行路径；两种路径都须核对事实来源和完整语义，写入权限仍由任务授权决定。

| 任务 | 读取与发现方式 | 修改后的复核 |
| --- | --- | --- |
| 已定位文字的局部修正 | 直接读取目标段落、必要上下文及事实来源；不默认运行探针或读取探针文档 | 比较改写前后的命题、引用与约束，运行适用检查 |
| 多文件或目录的批量审计 | 读取[召回探针调用规则](references/recall-batteries.md#invocation-rules)，按实际内容选择探针；同时独立阅读范围内相关的关键文字 | 复跑本轮使用且受修改影响的探针，逐项判断剩余命中，再做语义与适用检查 |

1. 按[执行范围与权限](#scope-and-permissions)确定本轮目标和排除项，再读取对应文字及事实来源。局部修正发现范围外线索时先报告，不自动扩大为批量审计。
2. 使用探针时，核对已有校准是否仍适用；新增或调整探针、缺少可核验的校准依据，或匹配条件及语料类型变化使原依据失效时，用已知正例和易混淆反例重新校准。具体复用条件见调用规则。探针可能误报和漏报，命中和零命中都不能代替语义判断，更不能作为自动删除依据。
3. 按内容位置优先修复源头：生成目录 → 追踪受影响的消费方，修复所属源注释或生成器模板，再重新生成受影响的衍生内容；引用源码或类型定义的代码块 → 修复真实来源，按项目实际同步约定更新受影响的示例并验证一致性；多语言内容 → 遵循[语言与项目约定](../weetion-doc/references/style.md#clear-technical-expression)，不自行要求语言配对或字节一致；模型或用户可见字符串 → 按 [表达与语义保留规则](../weetion-doc/references/style.md#clear-technical-expression) 处理，只有具备所属行为验证时才修改，否则保持原样并报告暂缓。
4. 删除任何内容之前，列举段落中的命题（依据文字规范），核对事实、义务、假设、分析依据、取舍及证据来源是否完整保留。判断有歧义时读取[矫枉过正的陷阱](references/examples.md#overcorrection-traps)中对应示例；不因减少示例读取而跳过命题检查。需求变动、决策理由和验证历史按其用途保留在归属文档或 Agent Note，不将有独立信息的记录当作冗余删除；非小改动按项目留底要求记录。
5. 验证：按上表复核本次修改；批量审计区分实际残留、允许保留的内容，以及示例或决策记录中用于说明问题的引文。按任务对应版本核对引用对象及其支持的事实，报告尚未核实的引用；按目标项目的实际检查入口执行相关文档、源码示例一致性及行为检查，并如实报告范围、证据和缺口；仅在项目明确要求时执行多语言同步检查，不绑定固定命令。
