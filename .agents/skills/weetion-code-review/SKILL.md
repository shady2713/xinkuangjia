<a id="code-review"></a>

# 代码评审

<a id="review-actions"></a>

## 确定评审范围

先明确评审目标、文件或模块及本次关注的问题。评审变更时区分差异与原有行为；评审完整模块时覆盖约定模块及必要调用链。局部任务不自动扩大成全仓审计。

有 Git 差异或 PR 时确认实际比较基线及版本，区分已提交、暂存、未暂存和纳入范围的未跟踪内容；没有 Git 时直接评审明确的文件或补丁，不要求建立仓库。范围工具只辅助定位，仍需读取相关实现与消费方。评审期间内容或基线变化后，重新核实受影响结论。

评审默认在当前对话报告发现，保持只读；修复或写入其他位置按用户已有授权执行。需要运行验证时遵守任务环境与副作用边界，不能因评审自动启动真实服务或收费调用。静态证据足以确认的问题无需为报告机械重跑全部检查。

<a id="sources-of-truth"></a>

## 按需读取依据

从目标项目规则、当前实现、配置和实际调用关系确定契约。只读取与评审对象有关的资料，已完整读取且版本未变的上下文直接复用；缺少规则时保留缺口，不用其他项目的约定代替。

| 涉及内容 | 读取范围 |
| --- | --- |
| basic-framework Java | [Java 规范](../weetion-development-java-standards/SKILL.md)中对应模块与场景的引用 |
| Python 质量与交付辅助工具 | 根规则、相关脚本、测试和相邻实现；本框架没有 Python 业务服务或独立 Python 技能 |
| basic-framework Web | [Web 规范](../weetion-development-web-standards/SKILL.md)中受影响的框架、组件及注释约定 |
| 资源与异步生命周期 | [通用防御性模式](../../../docs/测试与可靠性/通用防御性模式.md)的相关章节，具体行为以模块契约为准 |
| 共享状态、并发、时钟、子进程或清理相关测试 | [测试可靠性](../../../docs/测试与可靠性/测试可靠性.md)的相关章节；调查已有偶发失败时才读[诊断流程](../../../docs/测试与可靠性/偶发失败诊断.md) |
| 验证证据与测试入口 | 目标工程的测试配置和实际报告；basic-framework 使用[测试策略](../../../docs/测试与可靠性/测试策略.md)与[脚本索引](../../../docs/开发指南/脚本使用索引.md)，行为证据边界见[通用测试原则](../../../docs/测试与可靠性/通用测试原则.md) |
| 文档或文字的专项评审 | [文档规范](../weetion-doc/SKILL.md)对应主题及[表达规则](../weetion-doc/references/style.md#clear-technical-expression)；普通代码评审核对受影响说明的准确性，不自动扩展为全文润色 |
| 评审非小改动，或设计取舍、记录状态受影响 | 本次需求与相关活动决策记录；按项目记录门槛核对是否已有对应 Note，编写及生命周期细则见[Agent Note 规则](../weetion-doc-archive-agent-notes/SKILL.md#when-to-write-a-note) |

表内资料按条件组合，不要求全部加载。语言规范仍要求读取的专项内容不能省略；其回链到本技能时不重复读取。其他项目使用自身框架与规则，跨项目复用共享资料时核对依赖或映射，不将 basic-framework 的实现与命令视为通用要求。

<a id="manual-checks"></a>

## 沿实际行为检查

沿受影响入口、状态变化、数据存取和消费方检查下列相关项，不以条目数量代替覆盖，也不为未涉及的能力要求新增框架或设施。

| 关注点 | 核对内容 |
| --- | --- |
| 行为与边界 | 正常结果、空值及边界输入、错误传播、取消和重试是否符合需求；约束是否在实际执行点生效，直接或替代调用能否绕过 |
| 输入、权限与敏感信息 | 外部输入的校验与信任边界、身份和资源权限、危险操作及日志或输出泄露；界面限制、提示词或静态类型不能代替执行时保护 |
| 数据与状态一致性 | 事务边界、部分失败、重复执行与幂等要求；缓存或派生状态是否对应权威来源，更新、失效、事件时机及借用数据的所有权是否一致 |
| 接口与兼容性 | 实现与真实消费方、字段及默认值、错误语义、配置和序列化是否匹配；公开行为变化是否同步受影响文档或生成来源。已有本地化、模型输入输出等契约只在受影响时核对 |
| 生命周期与并发 | 创建和可见时机、持有与释放责任、重入和竞争、失败与取消后的资源状态；停止请求是否真正完成，迟到回调是否仍修改已释放状态 |
| 规模与成本 | 实际调用频率、输入规模和单项成本；限制是否覆盖完整输出及元数据，必要时核对极小值、恰好达到上限、单项超大输入和多字节计量 |
| 实际入口与验证 | 启动、装配、导出、构建产物或配置入口受影响时，核对真实入口的证据；测试是否用独立的输出或状态识别目标回归，不仅复述实现或相信组件自报成功 |

对已有不变量或状态检查，核对真实约束、检查时点与独立观察；契约要求生效前拒绝时不能延迟到生效后，空检查或固定成功不能作为证据。涉及恢复或热重载时才核对其重建过程。受控反例在隔离环境验证，无法安全执行则报告缺口。

注释与文档应准确说明受影响的行为、限制和必要理由；注释必需内容按语言规范判断。对项目要求留底的非小改动，核对相关 Note 是否覆盖需求变化、决策依据、真实备选方案与取舍、关联实现及验证；缺少记录、以新决定覆盖旧理由或记录与交付不符时，报告具体缺口。检查限定于本次变更及相关记录，不扩大为全库维护；只读评审不自动补写笔记。

<a id="verify-findings"></a>

## 报告前核验

每个拟报告的问题先核实下列内容，避免把缺少上下文或个人偏好当作缺陷。

1. **核对对象。** 定位当前文件、行号及足够的周边实现，沿相关调用链核实版本与行为；不能只凭孤立 diff 或过时评论判断。材料缺失、内容变化或判断存疑时补读，不要求重复展示全部源码。
2. **排除已有保护。** 检查当前层、上层调用方、框架和资源负责方是否已承担校验、异常处理或清理责任。框架行为不确定时按实际版本核对源码或官方资料。
3. **核实消费方与设计依据。** 声称未使用时核对导出、注册、模板、反射、动态调用与兼容义务；仓库搜索无结果不证明没有外部使用。单一内部调用方不直接证明公开 API 不合理；抽象、状态机或兼容路径依据实际需求和维护代价判断。
4. **证明触发与影响。** 给出能够成立的输入、配置、执行顺序或生命周期，并排除符合契约的有意行为。并发问题说明争议顺序，性能问题用测量、调用链或可核实的复杂度分析支持，不能凭写法或固定数据量判定。
5. **匹配证据强度。** 代码、配置、调用链或有效复现均可支持结论；必须运行才能判断而未能执行时，报告验证缺口。核对测试与报告实际对应的内容、配置及范围，区分本次执行和仍适用的复用证据。测试通过不能否定已核实的语义缺陷，发现冲突时检查覆盖与断言。

复审核验原问题及修复引入的相关回归，不能因是复审就忽略新发现的相关缺陷。范围外发现单独说明，不擅自扩大任务；收到不同意见时重新核对证据，必要时修正或撤回判断。

## 输出发现与结论

先简述评审对象、范围和版本；有差异比较时说明基线。按实际影响排列发现，遵守用户或项目的报告格式。每项给出文件与行号、触发条件、后果及证据；跨模块问题列出关键调用链，不挂在无关行上，并说明属于本次引入、暴露的已有问题还是范围外发现。

- **已确认缺陷：** 严重程度依据影响、触发可能性、覆盖范围和紧迫性。阻断须有实际契约或明确项目要求支持；修复是否需要新增代码、测试或模块不决定等级。
- **验证缺口：** 写明缺少什么证据、影响什么结论。项目要求的检查或矩阵必须核对，缺少时按项目规则判断是否阻断；未运行、跳过、失败或未知不能写成通过，也不能虚构功能故障。
- **改进建议：** 说明收益、代价和可选性质。个人偏好与未核实的怀疑不列为确定缺陷，不为凑数量制造问题。

报告列出实际检查、复用证据和未验证范围；未运行测试须明确说明。没有发现问题时，结论限定于覆盖范围，不承诺无缺陷。纯评审不要求同时交付修复，也不由检查通过推导已获批准或已经发布。
