# 文档专项规则

按[任务入口](../SKILL.md#workflow)选择下方与当前任务对应的章节，不要求每次编辑通读本页。页面结构、元数据、模板及笔记门槛沿用现行约定。

<a id="workflow"></a>

## 工作流程

对每个请求范围遵循此顺序。让常见读者路径保持简短，但不要仅为压缩字数就删除失败行为、所有权、限制或其他必需约定。

1. 先定位本次任务的目标项目，读取其根目录及目标文件所在目录层级中适用的 `AGENTS.md`，以及这些规则指定的文档规范；再阅读目标页面、其源码／测试和负责导航的文件。项目规则从目标项目查找，不按技能安装位置解析；文档目录的约定文件存在时才读取，不要求为使用本技能创建它们。
2. 按一个主要用途与读者类型对页面分类：产品快速入门、用户任务指南、贡献者教程、架构概览、包／子系统参考、生成的参考资料、智能体指令、决策记录或临时材料。
3. 按目标项目现有的模块归属、文档入口和导航组织页面。模块约定放在模块维护的 README 或文档中；跨模块资料按读者与用途放入项目已有的文档体系，具体遵循[文档层次](structure-hierarchy.md#documentation-hierarchy)。
4. 编写细节之前，先定义读者的起始状态、可观察结果、可能的失败、恢复路径，以及下一层有用的深入内容。
5. 按[元数据规则](metadata-links.md#readme-metadata)添加或修订 YAML；包 README 必须包含非空的 `description` 和 `kind`，`kind` 必须对应明确模板，并与文档用途及包的真实接口一致。在文档类型允许时，按[页面顺序](structure-hierarchy.md#page-order)编写摘要、目录、正文、可选的深入探索；分隔线和开发笔记按需使用，不强制数量、固定层级或位置，已有开发者细节与开发笔记正文仍须折叠。标题默认中文，项目机器规则要求的标题保留。
6. 按用户要求及项目规范确定文档语言；均未指定时默认使用中文。代码标识、命令、字段名及需精确引用的原文保持原样，不强行翻译。
7. 对照代码、测试、生成器、包元数据或当前决策的负责方核实每项陈述，按下方事实核查流程选择静态核对、实际测试或仍适用的既有证据。先核实权威来源，再同步派生产物；发现文档与实现不一致时，查明差异，不为迎合文字擅自修改实现。
8. 从目标项目的规则、构建配置和 CI 中确认实际检查入口，先运行针对性检查，再执行项目要求的文档、格式和构建检查；Git 工作区同时运行 `git diff --check`。重新阅读完整差异，先检查正确性，再检查简洁性及与仓库的一致性。

非小改动必须在同一次变更中新增或更新至少一份相关 Agent Note；编写条件、格式、替代关系及生命周期统一遵循 [weetion-doc-archive-agent-notes](../../weetion-doc-archive-agent-notes/SKILL.md)。

<a id="fact-check-procedure-test-do-not-assume"></a>

## 事实核查流程：证据与验证

每项实质陈述必须有与其性质相符的证据，并明确适用版本和条件。静态定义可以核对源码与配置，命令、操作流程及运行结果必须由实际执行的证据支持；阅读源码或测试文件不能表述为操作已运行或测试已通过。普通文档核实所声明的当前行为，历史记录核实其明确指定的版本。

1. **编写安装说明前先核实使用方式。** 阅读目标项目的包清单、公开入口、加载机制和构建配置，确认该包是供调用方引入的库、由宿主加载的插件或服务，还是组合多个组件的分发包。按真实接口选择包模板，使用项目实际的依赖管理、安装、启用或调用方式；不要根据文件夹名推断，也不要沿用其他包不适用的命令。
2. **按事实类型验证。** 类型、字段定义、声明的默认值和配置项等静态事实，对照文档对应版本的权威源码或配置核实；涉及有效默认值、配置覆盖、错误输出、平台差异等运行结果时须实测。新增或修改的命令与操作流程，必须在适用测试环境中按文档给出的形式执行，记录观察到的结果、警告和失败情况。
3. **有条件地复用证据。** 未变内容可以引用已有测试或执行记录，但须核对版本、依赖、配置、环境和覆盖范围仍适用，且相关实现未发生使证据失效的变化。仅有旧 README、记忆、测试源码或相邻包的示例不构成执行证据；证据失效或无法判断适用性时重新验证。项目明确要求重跑的检查仍须执行。
4. **区分错误与未验证。** 复现失败时先查明是陈述错误、版本或环境差异，还是缺少依赖、凭据或网络。已证实错误的内容应修正；暂时无法验证时，标明已有依据、阻碍、未覆盖范围和后续验证方式或负责方，不因环境缺失自动删除已有依据的内容，也不将缺少证据的新陈述写成确定事实。不得通过修改测试来迎合错误文字。
5. **使用实际基线。** 先确定文档对应的版本，以及本次任务需要的项目基线或目标分支；仅在需要比较变更时对照相关内容，不固定远端、分支名或要求每次获取远端。需要最新远端证据时，按项目实际远端和已有授权获取；无法获取时注明基线及其时效限制，不声称已对照最新版本。
6. **遵守执行边界并记录结果。** 只在适用测试环境和已有授权范围内验证。删除、迁移、部署、付费或影响外部系统的命令不能因写在文档中而自动获得执行授权；缺少必要授权或条件时记录未验证部分。验证记录须包含对应版本、环境、方法或准确命令、结果、证据位置及未覆盖范围，明确区分静态核对、本次实测、复用证据和未验证结论。

<a id="kind-system-and-templates"></a>

## 类别体系与模板

前置元数据字段 `kind` 必须且只能指定一个已定义类别，并选择其对应模板。[元数据参考](metadata-links.md#the-kind-system)维护类别、用途及模板映射；根据文档内容和包的真实接口核验分类，不根据固定目录名推断。

- `package-group` → [templates/package-group.md](../templates/package-group.md)：包组或模块组导览，介绍能力家族、列出直接下属包，并链接到由各包维护的细节。
- `package-reference` → [templates/package-reference.md](../templates/package-reference.md)：插件、服务或其他功能包，说明实际接入方式、必要配置、可观察行为及限制。
- `package-library` → [templates/package-library.md](../templates/package-library.md)：供调用方引入的库，说明依赖获取、公开入口、调用示例及使用边界。
- `package-bundle` → [templates/package-bundle.md](../templates/package-bundle.md)：组合多个组件的分发包或预设，说明实际安装、启用、移除方式及组合关系。
- `persistence-change` → [templates/persistence-change.md](../templates/persistence-change.md)：持久化格式变更确认记录，说明来源版本、变更前后约定、兼容性决策及迁移验证。
- `persistence-release` → [templates/persistence-release.md](../templates/persistence-release.md)：比较明确发布版本的持久化结构，保留差异和来源证据；比较结果本身不证明兼容性或迁移安全。
- `persistence-format` → [templates/persistence-format.md](../templates/persistence-format.md)：记录选定历史检查点的存储格式及完整结构证据，与当前格式约定区分。

只有涉及相应持久化格式任务时才使用这 3 类记录，不要求无相关需求的项目创建它们。目录、机器声明、附件和验证工具按项目实际约定执行；没有专用工具时仍须记录来源、差异及核验结果，明确未验证结论。

编写前打开对应模板，遵循其内容要求及事实核查规则。新增类别必须说明用途和与已有类别的边界，提供对应模板，并在[类别体系](metadata-links.md#the-kind-system)中登记核验规则；已有自动检查覆盖该分类时，同步更新，否则逐项人工核验并报告，不要求仅为新增类别创建检查工具。

<a id="voice-rules"></a>

## 表述规则

这些规则决定一个章节可以表达什么。规则适用于所有人工编写、面向读者的页面，对包 README 尤其严格。

- **摘要说明主题能够做什么。** 开头的摘要和面向用户的章节，应说明用户或智能体能够用该主题完成什么：结果、收益、选择时机及主要代价；绝不叙述它的角色、类型或内部身份。包摘要中“它是什么”仅指读者可见的能力，不是它的框架注册角色或内部组件。除非读者会在配置、命令或公开 API 中直接使用，否则省略源码标识符。“该组件注册内部服务并追加内部事件记录”是在叙述身份；“你可以为每条消息保存一条笔记，重启后仍然存在”才是在说明它的用途。
- **开发者章节重在解释，绝不罗列。** 开发者细节必须折叠，章节标题与锚点保留可见；必要操作、限制和警告不得藏入折叠区。实现内容应涵盖整体设计概念、架构及概略的数据流，让读者足以理解包如何运作，并链接代码供查阅精确细节。折叠区域中不得放入完整 API 目录、穷尽的字段列表、事件载荷枚举或对 接口文档 的复述。
- **开发笔记按需设置。** 在本技能页面格式适用范围内，不完整想法、草稿、未决定的方向、测量产物和工作假设只能放在可选的开发笔记中，明确标记为非权威内容；没有内容时可省略章节，不限制数量、固定层级或末尾位置。其他章节描述经过核实的当前状态。页面开发笔记不代替非小改动必需的 Agent Note，特殊格式的适用边界见[页面顺序](structure-hierarchy.md#page-order)。
- **仅描述当前状态。** 普通文档描述当前行为，历史与决策按[事实归属规则](structure-hierarchy.md#fact-ownership-and-history)单独记录。专门的 `persistence-change`、`persistence-release` 和 `persistence-format` 记录保留持久化格式的历史证据；发布比较和格式检查点描述观察到的历史，不能仅凭结构证据声称兼容性或迁移安全。Agent Note 和事故复盘各自保留其历史范围。
- **使用清晰、准确的技术表达。** 明确执行者和主要动作，统一术语，优先使用直接动词，拆开堆叠的指令与条件。准确区分“必须、应当、可以、禁止”，保留条件、例外及不确定程度；不得为精简而改变约束。具体遵循[技术表达规则](style.md#clear-technical-expression)。

<a id="quality-criteria"></a>

## 质量标准

在评审中使用以下定义。每节在子节或穷尽细节之前，先用一个简短段落引导读者。

- **简洁：** 常见路径只包含达成结果所必需的事实；完整事实仍可通过一个直接链接或下一层详情获得。
- **直观：** 先讲前置知识，再讲依赖它们的概念；下一步操作明确；标题采用读者会搜索的术语。
- **友好：** 读者能够识别成功状态，在操作前理解风险，从常见失败中恢复，并决定是否继续深入。
- **准确：** 每项长期保留的陈述都有唯一负责方，以及与其风险相称的验证路径。
- **智能体可读：** 元数据、稳定标题、锚点、术语、所有权和当前／提议状态支持定向检索，无须加载全部文档。
- **对新读者完整：** 没有仓库背景的专业工程师，通过三到五篇相互链接的页面，就能还原相关架构或功能。

不要对详尽参考资料套用统一字数限制。应测量入口路径长度、单次查找需要扫过的无关内容、最大章节、标题数量及页面大小；当检索成本过高时，按已有领域负责方拆分。

<a id="audit-the-corpus"></a>

## 审计全部文档

阅读权威约定，不要再次概括：主题范围、教程／参考资料形式及事实归属见[页面结构与层次](structure-hierarchy.md#scope-and-document-type)，冗余内容检查见[评审标准](review.md#redundancy-and-expression)，通用文档类型及事实归属分类见上述内部参考，项目特有分类遵循目标项目的实际规范，篇幅控制见[字数预算](#wordcount-budgets)；Agent Note 规则见 [weetion-doc-archive-agent-notes](../../weetion-doc-archive-agent-notes/SKILL.md)；常设规则按[工作流程](#workflow)从目标项目的适用规则中读取。将目标项目的归档笔记排除在内容审计与编辑之外，已归档笔记是冻结的历史记录。

对范围内每个人工面向读者的文档（不包括 Agent Note），按[主题范围与文档类型](structure-hierarchy.md#scope-and-document-type)组织内容，并按[事实归属与历史记录](structure-hierarchy.md#fact-ownership-and-history)核对权威来源。然后检查位置约束：生成的目录绝不能手工编辑；移动操作必须与修复所有入站链接在同一次变更中原子完成。

结构检查完成后，按[冗余与表达检查](review.md#redundancy-and-expression)核查重复规则、手写生成目录、过程性叙述和过度强调。使用 [weetion-doc-trim-cot-leakage](../../weetion-doc-trim-cot-leakage/SKILL.md) 进一步检查推理记录泄漏。Agent Note 的状态与表述按 [weetion-doc-archive-agent-notes](../../weetion-doc-archive-agent-notes/SKILL.md#note-format)核对。使用项目已有的篇幅统计工具定位异常文档；没有工具时，人工检查入口路径、最大章节及查阅时需要扫过的无关内容；如果删除文字会改变承诺的行为，而不只是改变解释，应先提出行为变更（遵循 [weetion-doc-find-simplifications](../../weetion-doc-find-simplifications/SKILL.md)）。保留每一条关键规则，最好用一到三行加上设计依据链接；不要仅为转移可丢弃的推理而新写一份解释。

<a id="wordcount-budgets"></a>

## 字数预算

先读取目标项目已有的篇幅规范、预算配置和统计工具，遵循其计数方式、适用范围及上限。没有预算配置时，不强制新增预算文件或校验工具，也不套用固定字数和余量比例；根据读者完成任务与查找信息所需的阅读量判断是否需要精简。

文档过长时，依次处理：将不属于本页的内容移到其所属文档并保留链接；压缩重复或可简化的表述；仅在必要内容确实需要空间时，按项目变更流程调整已有上限，并说明理由。

上限用于控制阅读成本，不是删减目标。不得为了满足篇幅要求删除关键行为、限制、失败条件或例外，也不得为了让检查通过而擅自放宽阈值。摘要应简短、完整，具体长度要求以目标项目规范为准。

<a id="validation"></a>

## 验证

验证受影响的格式，而不只是 Markdown 语法。强约束承诺需要针对性的有效测试样例，以及能够证明顶层门禁会失败的无效测试样例。

- README 元数据：按[元数据核验规则](metadata-links.md#metadata-verification)检查 YAML、必填字段、描述质量、类别及模板对应关系；`name`、`audience`、`tags` 仅在目标项目明确要求时允许。有对应工具时执行自动检查，没有时逐项人工核验并报告结果。
- 教程：按[事实核查流程](#fact-check-procedure-test-do-not-assume)验证新增或修改的操作路径；未变内容仅复用仍适用的执行证据。受环境或授权限制未能执行时，明确缺口和后续验证方式或负责方，指定负责方不等于验证完成。
- 生成的参考资料：运行确定性的新鲜度检查，并报告检索规模指标。
- 包 README：检查摘要是否简短、完整，并遵循项目已有的长度要求；执行项目实际提供的摘要、模型体验和限制检查。行为陈述变化时运行针对性测试，新增或修改的命令及操作按[事实核查流程](#fact-check-procedure-test-do-not-assume)实测；未变内容的证据复用和未验证情况遵循同一规则。
- 技能：执行项目实际提供或技能工具自带的元数据检查。

按[评审标准中的验证流程](review.md#verification)选择项目实际提供的检查。先执行范围明确、成本较低的检查，再执行项目要求的完整检查。缺失或无法运行的检查须如实说明，不编造命令，也不将人工复核表述为自动检查通过。
