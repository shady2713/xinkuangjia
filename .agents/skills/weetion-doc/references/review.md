# 评审标准

<a id="summary"></a>

## 摘要

评审文档时，应看读者能否完成目标，而不是看所有模板标题是否齐全。对照代码和测试核实文字，保留精确约定，让包 README 对消费方有用，同时向维护者提供足够的实现细节。运行当前项目实际提供的检查，按下方规则选择参考示例。

<a id="newcomer-test"></a>

## 新读者测试

没有仓库背景的专业工程师，在阅读三到五篇相互链接的页面后，应能够回答：产品或功能做什么，如何安全运行或使用，状态存放在哪里，由哪个组件负责，会如何失败，以及应在哪里修改。如果读者仅为了解公开流程就必须查看源码，应补回缺失的解释。如果读者必须消化无关的内部细节，应把这些细节移到更深层。

<a id="evidence-review"></a>

## 证据评审

对照最有权威性的负责来源检查每项实质陈述。名称与入口使用包元数据；API 约定使用公开类型和 接口文档；行为使用运行时代码；实际测试过的失败路径使用测试；穷尽清单使用生成的目录；设计依据使用活跃 Agent Note。绝不要把先前的 README、讨论或报告视为比当前代码和测试更有力的依据。

按[事实核查流程](../SKILL.md#fact-check-procedure-test-do-not-assume)评审证据类型、适用性及执行边界。静态定义可以对照权威源码和配置；新增或修改的命令、操作流程及运行结果须有实测证据。未变内容复用既有执行记录时，核对版本、依赖、配置、环境和覆盖范围仍适用，不将测试源码等同于测试已执行。

核对文档对应版本及任务实际使用的基线，不固定远端和分支名，也不将未刷新的本地资料称为最新远端证据。已证实错误的陈述应修正，暂时无法验证的内容应明确依据和缺口；源码核对、本次实测、复用证据及未验证结论必须区分。每份验证记录须包含版本、环境、方法或命令、结果、证据位置和未覆盖范围；仅指定验证负责方不能视为完成验证。

评审安装说明前先读取目标项目的包清单、公开入口、加载机制和构建配置，确认真实使用方式。库说明依赖获取和调用入口，插件或服务说明实际加载、启用或运行方式，组合包说明安装及组成关系。不从目录名、其他项目的框架约定或相邻包的命令推断接入方式。

只有当陈述能帮助目标读者行动、理解或避免误用时，才保留它。将设计依据、历史、测试讲解、重复目录和无关包细节移到各自归属位置。

<a id="redundancy-and-expression"></a>

## 冗余与表达检查

确认事实完整后，再检查下面的内容。精简必须保留行为、限制、失败条件、例外和必要的设计依据；事实的归属遵循[事实归属与历史记录](structure-hierarchy.md#fact-ownership-and-history)。

- 重复规则：搜索具有辨识度的短语，确认是否在多处维护同一要求。保留权威来源，其他位置只保留局部必需的说明及链接。
- 手写生成目录：检查是否重复罗列由源码或生成器维护的接口、配置、模块、测试或状态清单。改为链接权威来源；局部示例应明确用途和范围，不充当完整清单。
- 过程性叙述：先核对其中的需求变化、分析依据、方案取舍、约束及验证证据是否已在对应决策记录、需求文档或复盘中完整保留，并提供可定位引用；没有归属时先承接，不能仅因暂时看不出长期价值而删除。再清理当前说明中重复、无独立事实的实现经过、显而易见的分支解释、测试流水账和临时讨论。必要操作步骤，以及历史记录中有依据的变化和取舍，继续保留。
- 过度强调：检查大面积加粗、全大写或反复使用“极其重要”等措辞。只强调会影响操作或决策的关键条件，并保持原有要求强度。
- 历史混入当前说明：核对版本、状态和时间范围，将历史经过及决策背景放到对应记录，保证当前说明与实际行为一致。

<a id="package-readme-review"></a>

## 包 README 评审

要求满足以下内容，但不要强制所有文档采用一套通用内部标题：

- 符合[元数据核验规则](metadata-links.md#metadata-verification)的 YAML：`description` 和 `kind` 为非空字符串，描述具体且可检索，类别与文档用途、真实接口和对应模板一致；
- 摘要简短、完整，说明主题能为用户或 智能体读者做什么，长度遵循项目规范，并附带可点击的目录；
- 使用[清晰、准确的技术表达](style.md#clear-technical-expression)：语言按用户与项目要求确定，未指定时默认中文；明确执行者、统一术语、使用直接动词，保留条件关系和约束强度，不翻译代码标识、命令及字段名；
- 何时选择或避免使用该包；
- 给出适用的最小安全配置或使用路径：库说明依赖获取及调用示例，插件或服务说明实际接入方式，组合包说明安装、启用及移除方式；不提供不受支持的操作；
- 与消费方相关的可观察行为、失败情况、持久性、安全性及性能限制；
- 面向开发者、无法从公开类型中轻易还原的概念层所有权和数据／生命周期设计，包括整体设计、架构及概略数据流，并提供代码链接以查看精确细节；
- 据实说明已知限制、影响及可用替代方式；没有已知限制时如实说明，不编造限制，也不要求登记白名单；仅在涉及模型交互时说明本包对模型输入、输出、上下文或资源消耗的实际影响，项目规定的检查仍须遵循；
- 当相邻文档具有实质帮助时，提供面向新读者的“深入探索”，不设固定篇数、不凑数量；
- 章节分隔线按需使用；开发者细节必须折叠，标题与锚点可见，必要操作、限制和警告不隐藏在折叠区；
- “开发笔记”按需设置，已有正文须折叠并标为非权威内容，不要求数量、固定层级或末尾位置；它是页面内未整理内容的唯一归属，不代替非小改动必需的 Agent Note；

不要复述 接口文档 或生成的目录。链接权威来源，只解释当前局部需要的决策或关系。包摘要描述读者可见的能力，而非框架注册角色或内部组件；除非读者会在配置、命令或公开 API 中直接使用，否则应省略源码标识符。拒绝任何叙述内部细节（以函数为主体、事件流、数据流）的用户章节，以及任何罗列 API 而不解释概念的折叠区。

<a id="reference-example"></a>

## 参考示例

优先选择目标项目中仍受维护、使用方式相近且事实可核验的 README 作为参考，借鉴其适用内容和项目约定，不直接复制命令、默认值或行为。没有合适示例时，使用本技能对应包模板；不要求项目存在指定包或参考文件。每项陈述都应有其权威来源和验证依据。

<a id="verification"></a>

## 验证

先阅读目标项目的规则、构建配置和 CI，确认文档检查的实际入口、执行条件及顺序。根据改动选择文件与图片链接、锚点、格式、元数据、生成内容新鲜度及篇幅预算检查；项目已规定的必需检查仍须执行。

迭代时先运行范围明确的针对性检查，再执行项目要求的完整检查。Git 工作区同时运行 `git diff --check`。技能变更使用项目实际提供或技能工具自带的元数据校验器，不假定项目采用特定包管理器或脚本名称。

项目没有某类检查工具时，进行相应的人工复核并说明方式；已有必需检查无法运行时，报告原因与未验证范围，不擅自跳过、替换或降低要求。交付时记录实际命令和结果，区分自动检查、人工复核与未验证事项。

重新阅读最终差异，一遍检查事实完整性，另一遍检查简洁性、导航和所有权。
