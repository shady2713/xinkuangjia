# 页面结构与层次

<a id="summary"></a>

## 摘要

每个页面都先为新读者提供简短入口，再展开操作或实现深度。文档位置遵循目标项目的模块归属、读者需求和现有导航。小型规则文件各自负责一个可独立搜索的要求，但任意碎片化并非目标。可选的开发笔记将当前工作上下文与稳定的解释隔离。

<a id="scope-and-document-type"></a>

## 主题范围与文档类型

先确定文档负责的主题和读者目标，再决定细节深度。文档只完整解释自身主题；介绍下级模块或相邻主题时，说明其用途、职责和主要行为，并链接到负责具体细节的文档。测试机制、示例数据和执行框架等细节放在其所属模块的文档中，上层文档保留入口链接。

按读者用途区分教程与参考资料，而不是按文件名或目录判断：

- 教程带领读者按步骤达成可观察的目标。先说明起点和前置条件，按概念依赖及难度安排步骤，每一步只引入完成该步需要的知识，并提供结果验证方式；非必需的进阶内容链接到后续教程或参考资料。
- 参考资料明确可查阅的主题范围，按读者会查找的概念、接口或配置组织当前行为、限制和边界，使读者无需走完整个教程就能找到答案。
- 同一页面包含大量教程和参考内容时，拆成相互链接的文档；只有少量补充内容时，用清晰的章节标题区分。

编写顺序为：确定主题与位置、划定细节范围、选择文档类型、组织内容，再将超出范围的细节移到其所属文档并修复链接。参考资料可以详尽，但详尽程度不能扩大其主题范围。

<a id="fact-ownership-and-history"></a>

## 事实归属与历史记录

同一事实只维护一个权威来源。根据事实的性质确定其归属，例如行为由实现和测试核实，接口约定由接口定义维护，完整清单由生成器维护，设计依据由决策记录维护。其他页面可提供理解当前主题必需的简短说明，并链接到权威来源，不另行维护完整副本；事实变化时，更新权威来源和受影响的说明或链接。

普通使用文档和参考资料描述当前行为。变更经过、旧版本行为、决策理由和事故时间线分别放入项目已有的变更记录、版本历史、决策记录或事故复盘中，并标明适用版本或历史范围。当前文档在需要解释背景时链接这些记录，不将历史状态或未实施方案写成当前能力。

<a id="page-order"></a>

## 页面顺序

在格式负责方允许时，人工编写、面向读者的页面必须使用以下顺序。标题默认使用中文；用户或项目指定其他语言时使用对应语言，项目机器规则要求的固定标题保留。生成产物可以生成相同的入口章节；Agent Note 与事故复盘保留项目规定的各自骨架。

1. 按[元数据规则](metadata-links.md#readme-metadata)及对应模板提供 YAML 元数据。
2. H1 标题。
3. `## 摘要`：用简短、完整的段落说明读者能够做什么或观察什么、为何值得关注、主要运行模型及最重要的边界。具体长度遵循项目规范。
4. `## 目录`：链接到页面的 H2 章节；保持导航用途，不作内容描述。
5. 正文先说明基础使用，再进入进阶内容和开发者细节；教程按完成目标的步骤展开，参考资料按查阅主题组织。
6. 可选的 `## 深入探索`，为新读者提供相邻主题链接。
开发笔记为可选章节，用于保存非权威的当前工作上下文；没有内容时可省略，不强制数量、标题层级或末尾位置。

摘要和目录沿用极短文件、生成片段及特殊解析格式的既有例外，不为套用骨架制造无效输出。生成格式、解析器管理的格式及上文专门骨架按其明确约定处理。包 README 将“深入探索”放在限制章节之前；涉及模型交互时，在限制章节前补充“模型体验”，开发笔记按需设置。模型体验的适用性及内容遵循[包 README 评审标准](review.md#package-readme-review)。分隔线按需使用，参见[分隔线说明](style.md#section-separators)。

<a id="section-progression"></a>

## 章节递进

每个实质性的 H2 章节都必须在表格、代码或 H3 子节之前，以简短的引导段落开头，说明主题及与操作或判断相关的要点。不要复述标题或为了填满结构凑字数。

页面内按照读者需要的深度排列内容：

1. 基础使用：何时选择该功能、必需输入、最简安全示例、可观察的成功结果，以及常见恢复方法。
2. 进阶使用：配置选择、限制、运维操作及集成行为。
3. 开发者细节：所有权、生命周期、数据模型、失败行为、性能、安全性及值得维护的扩展点。

面向开发者的实现细节及已有开发笔记正文必须收进 `<details>` 块，保留章节标题和锚点可见（机制见[折叠规则](style.md#foldable-content-sections)）。读者完成任务所需的操作、限制、风险和警告必须在普通正文中可见，不能只存在于折叠区。

折叠的开发者细节按要求必须保持在概念层：整体设计概念、主要组件架构及概略数据流，足以理解包如何运作；再提供源码映射表及代码链接以供查阅精确细节。它绝不能变成穷尽目录：不得罗列完整 API、字段列表、事件载荷或复述 接口文档。开发笔记是唯一允许容纳不完整想法、草稿和未决定方向的位置；其他所有内容，包括折叠区，都应是经过润色、描述当前状态的文字。

详尽的生成类型、schema 或目录应放在简短入口段落及稳定索引之后。如果一次查找需要扫过无关分组，应按已有领域负责方拆分。

<a id="documentation-hierarchy"></a>

## 文档层次

先查看目标项目的目录规范、模块 README、文档入口和导航配置，确认各类内容的实际归属。模块约定由该模块的 README 或专属文档维护；跨模块资料按受众和用途组织，避免将无关主题堆在同一页面或目录中。

目录名称、层级和组件划分沿用项目已有约定。学习资料、用户指南、开发者指南、架构参考和临时讨论是内容用途，不要求各自建立固定名称的目录。组件说明依据实际模块及其职责划分；逻辑并列的主题可保持同级，存在包含关系或检索负担时再分层。

目录调整限于当前任务涉及的主题。在同一次变更中修复受影响的入站链接、图片引用、目录和索引；具体核验遵循[仓库链接规则](metadata-links.md#repository-links-and-path-mentions)。

需要受版本跟踪并在交接后保留的临时讨论，放在项目规定的位置，注明负责方、创建日期、到期时间及转为正式内容的目标位置。本地可丢弃笔记按项目忽略规则处理。

<a id="small-rule-files"></a>

## 小型规则文件

当一条可独立搜索的规则、实践、示例家族或决策具有自己的负责方、变更节奏、入站链接或验证方式时，为其分配一个小文件。将相关文件归到具有描述性名称的层次结构下，例如在开发指南下按代码质量主题分类。如果拆分会迫使读者打开多个文件才能理解一项义务，就应将紧密耦合的规则保留在一起。

索引页面用三到五句话解释文件夹，并按用途链接其直接子项，不重复每个子项的规则。

-----

<a id="further-exploration"></a>

## 深入探索

此可选章节面向已读完页面、希望理解相邻主题的新读者。只链接直接相关且有实质帮助的页面，不设固定篇数，也不为凑数量添加链接，从最接近的前置知识到更深入的探索依次排列，并用简短短语说明每篇补充什么。不要将其变成完整的文档索引。

-----

<a id="dev-note-ownership"></a>

## 开发笔记的归属

普通人工页面可按需设置开发笔记，并明确它不具权威性；没有内容时可省略，不要求唯一、固定层级或末尾位置。当前假设、兼容性顾虑、粗略备选方案、进度指引和未决问题可以放在其中；稳定行为、必需的限制和已接受的依据应放到常规归属位置。页面开发笔记是临时工作上下文，Agent Note 是独立决策记录，两者不能互相替代；非小改动必须新增或更新 Agent Note 的要求保持不变。

开发笔记可以映射或链接任务进度，但不能成为第二个可写队列。工作结束后，将持久有效的结论转入正式内容，将可复用的依据移入 Agent Note，将事故时间线保留在事故复盘中，并删除已解决的讨论。旧版本迭代由 Git 历史保存。
