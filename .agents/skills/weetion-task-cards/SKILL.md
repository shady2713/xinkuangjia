# 需求卡生成规范

生成需求卡时，按下列结构创建文件，填满模板后检查再交付。只生成文档，不自动实施业务、创建 Goal 或执行 Git 操作；不启动子代理。讨论和单独检查保持只读。

<a id="选择形式与计划落盘"></a>

## 输出结构与命名

需求卡是一个文件夹。默认放在仓库根目录的 [docs/需求卡](../../../docs/需求卡/README.md)，用户指定位置时使用指定位置。

```text
docs/需求卡/YYYYMMDD-NN-需求名称/
├── 需求卡总览.md
├── G01-T01-动作名称.md
├── G01-T02-动作名称.md
├── G01-T03-整体回归与组验收.md
├── G02-T01-动作名称.md
└── G02-T02-整体回归与组验收.md
```

- 需求编号为 `YYYYMMDD-NN`：首次创建日期加当天序号，从 `01` 递增，超过 `99` 后继续使用 `100` 等数字；不加 `REQ` 前缀。例如 `20260926-01-角色权限管理`。
- 单文档与多卡共用仓库内唯一编号。创建前核对已有编号、历史已用编号和目标路径；不覆盖已有需求，不复用已删除编号。改名、修订或迁移不改变编号；已有需求保留原编号和位置。
- 总览固定为 `需求卡总览.md`，不得用 `README.md`、`总卡.md` 等名称代替。
- 子卡固定为 `G<组序号>-T<组内任务序号>-<动作名称>.md`，如 `G01-T01-确认版本接口.md`。两种序号均从 `01` 开始，至少两位，超过 `99` 后继续递增；每组的 T 从 `01` 开始，完整编号唯一且稳定。
- 文件全部平铺，不创建子任务目录、分组目录或组级文档；不得使用 `00-范围核对.md`、`01-公共模块.md` 等编号方式。
- 需求名称与动作名称简短明确；文件名不附加版本、状态或负责人，子卡不重复日期和需求编号。版本写入正文。
- 上面的组数与任务数仅为结构示例。按实际需求展开，不照搬数量；测试样例放项目示例目录，不混入正式需求。

## 需求来源

获授权生成单文档或需求卡后，先按 [Notes 规则](../weetion-doc-archive-agent-notes/SKILL.md#when-to-write-a-note)保存已确认的讨论结论，再生成文档。同一决策已有记录时复用，不另建重复记录。

- 记录需求编号、适用版本、已确认需求、范围边界、取舍理由、否决方案及未决事项；未确认内容单列，不从生成后的卡片反推讨论。
- 总览、每张子卡和单文档都填写“需求来源”，直接链接相关记录与章节并注明适用版本；多个决定列相关记录，子卡不能只链接总览。
- 只有旧卡而缺少原讨论时，明确说明来源缺失并核实，不能把 AI 的二次理解写成用户已确认要求。

<a id="多卡拆分与安排"></a>

## 生成步骤

依次完成以下步骤，先读取所需模板文件，不自行更换顶层章节或改成说明书。

1. **核实需求与入口**：先保存或复用上述需求来源，明确版本、范围、交付结果和验收条件；读取相关代码、调用关系及测试入口。现存路径与符号必须真实，拟新建产物明确标注。能从代码查明的问题先查，关键业务决定不明时先确认。
2. **拆卡并分组**：每卡交付一个可独立验收的主要结果；不同对象及可独立验收的版本分别安排，复杂对象按职责或契约继续拆分。类别只用来分组，不把多个独立对象压成一张类别卡；不按文件数、时长或固定数量拆卡。边界不明时先安排有明确问题、入口和证据要求的调查卡。
3. **安排依赖与组验收**：先确定任务，再编 G/T 号；写清前置产物，依赖必须存在且无环。每组安排集成后的整体回归与组验收，覆盖受影响既有行为；只读审查组核验同版本证据衔接与覆盖。组只组织交付和回归，不强制每组形成独立业务功能。
4. **填充总览与全部子卡**：读取并复制[总览模板](templates/overview.md)和[子卡模板](templates/subtask.md)，替换全部 `{{…}}`，重复实际需要的组、步骤与用例。没有适用内容时填写“无”或说明不适用原因，不留空标题。共享约定只写在总览，具体操作和测试写在子卡。
5. **核对后交付**：按本页检查表及[可执行性检查](references/requirements-review.md)核对原始需求、全部卡片与验收，运行适用文档检查。报告需求目录、总览链接、组数、子卡数、检查结果及未决事项。

有已确认方案时，保留原范围、依赖、接口、默认选择和验收条件；只调整拆分、标题层级及链接。必要补充明确指出，不能把未知项写成默认决定。计划模式只允许规划时按模板组织内容，获得写入授权后再落盘，不借子代理绕过限制。

## 使用已有模板

生成前必须完整读取对应模板。正文结构和字段说明以模板文件为准，不凭记忆重建，不把模板说明原样留在产物中。

| 产物 | 模板文件 | 输出名称 |
| --- | --- | --- |
| 需求卡总览 | [overview.md](templates/overview.md) | `需求卡总览.md` |
| 子需求卡 | [subtask.md](templates/subtask.md) | `G01-T01-动作名称.md` 形式 |
| 单文档计划 | [plan.md](templates/plan.md) | `<需求编号>-<需求名称>.md` |

## 交付前检查

检查全部产物，不以抽样代替完整核对。生成或修订范围内不符合以下规则时，先修正再交付。

- 目录名、总览名和每份子卡名符合本页格式，全部平铺；文件名、H1、总览任务表中的编号与动作名称一致。
- 总览和子卡均按顺序保留“摘要、目录、实施方案、测试与验收、假设与约束”；总览含“总体方案、共享约定、任务安排”，子卡含“开始位置、操作步骤”。
- 所有 `{{…}}` 已填写，无空标题、无效路径或断链；总览每行任务对应一份子卡，每份子卡都在总览中出现，编号无重复，依赖存在且无环。
- 每项原始需求或检查对象都有子卡和验收；每卡有真实入口、可操作步骤、允许修改范围和能拒绝错误结果的判据；正常、关键边界、失败和受影响既有行为均有覆盖或明确的不适用理由。每组包含整体回归与组验收。
- 不填写负责人、实际执行者或模型、执行状态、勾选、进度、实际结果和日志，不另建进度账本，不预列 Skill 清单；执行者按实际任务与项目规则选择 Skill。
- 按需求卡的保存位置调整模板中的相对链接，并检查链接有效性。
- 需求来源可访问，相关章节及适用版本正确；对照来源检查限制、取舍和验收没有遗漏或改义，不能仅检查卡片彼此一致。
- 文档检查与可执行性结论分开报告；模拟、业务验证与工具集成测试分开，不把未运行的验证记为通过。

## 其他入口

仅在对应请求下读取以下材料，生成多卡时无需展开执行流程。

- **单文档计划**：保存一次完整交付且无需独立交接的计划时，使用[单文档模板](templates/plan.md)，输出 `docs/需求卡/<需求编号>-<需求名称>.md`，需求编号仍为 `YYYYMMDD-NN`。分批交付、独立交接或复杂依赖使用需求卡；不能用单文档回避拆分。用户指定的形式不适合时说明原因。
- **只读检查**：按[可执行性检查](references/requirements-review.md)报告问题；不启动业务实施，不因旧命名或标题自动迁移旧文档。
- **按卡执行或恢复**：先读[执行与恢复](references/execution.md)，核对授权、Goal、清单、当前代码与证据；Git 操作遵循[Git 流程](references/git-workflow.md)。单文档一次交付一个本地分支，多卡一组一个本地分支；推送仅由用户人工操作。
