# 计划与需求卡的 Git 交付流程

## 摘要

核对授权 → 同步目标分支 → 本地分支开发与提交 → 本地合并 → 整体回归 → 交接 → 用户人工推送。

## 授权与交付边界

执行前核对已有授权，按下表判断操作与完成范围。

| 项目 | 规则 |
| --- | --- |
| 开始条件 | 明确仓库、远程、既有目标分支、本地操作授权及验证要求；不猜 main/develop，不新增远端目标分支。 |
| 授权 | 保存计划或修改流程不授权 Git 操作；已授权普通提交不逐次询问，高敏感操作按项目规则再次确认。 |
| 默认完成 | 本地合并、最终版本整体回归、约定验收和必要人工确认通过，交接齐全。单文档覆盖整份计划，多卡覆盖所选组。 |
| 远端交付 | 仅用户人工推送既定目标分支；AI、子代理及自动化均不得直接或间接推送，工作分支不上服务器。 |
| 特殊情况 | 用户要求远端交付时，等待人工推送并核实；只读调查或审查按证据交付，不强制 Git 写操作。 |
| 远端规则冲突 | 默认不使用依赖远端工作分支的 MR 流程；有冲突交由用户决定，不修改或绕过保护规则。 |

## 任务组分支与命名

编号取自已确认文档；主题用简短英文、小写字母、数字和连字符。

| 形式 | 本地分支 | 示例 |
| --- | --- | --- |
| 单文档 | 一次完整交付一个分支：`codex/<需求编号>-<主题>` | `codex/20260926-01-device-query` |
| 多卡 | 每组一个分支，同组子卡共用：`codex/<需求编号>-<组编号>-<主题>` | `codex/20260926-01-g01-device-query` |

- 恢复时核对并复用对应分支；同名属于其他工作时不得覆盖。
- 子代理默认在主会话指定范围交付，不自行建分支；隔离须授权，成果仍汇入组分支统一验收。
- 下文“组”对单文档指整份计划，“子任务”指步骤；提交与交接引用需求编号及步骤编号，不额外加组号或按步骤建分支。
- 改为分批交付时，先确认多卡安排和已有成果归属，再调整分支；不自动迁移或删除分支。

## 新组开始前同步

每个新组重新同步，保留上一组未推送成果。

1. 核对分支、工作区、暂存区、运行中的执行者和未推送提交；无关改动妨碍操作时先说明并按授权保护，不清理或夹带提交。
2. 获取指定远程目标分支最新信息并更新本地目标代码；只获取引用不算同步，获取失败须说明，不能记为完成。
3. 保留本地提交：可快进则快进，分叉则核对后按授权合并；不强制覆盖或擅自重写历史。冲突保留双方意图，解决后复验。
4. 从同步后的本地目标分支建本组分支；在会话记录基线，不向需求卡回写实际提交号或进度。

无需先推送上一组；继续前核对需求依赖和实际基线，不能复用过期远程快照声称已同步。

## 子任务提交

以完整、可解释且通过相关检查的改动为提交单位。

- 小且紧密关联的任务可合并提交；不按固定时间或每次编辑提交。
- 只提交本任务改动，提交信息关联完整任务编号。
- 子代理返回改动与对应版本的验证证据；主会话核验后统一暂存、检查、提交。
- 共享工作区不得并发操作暂存区；仅隔离工作区且明确授权时，子代理可自行本地提交。
- 提交成功不等于主会话验收通过。

## 本地合并与组回归

按顺序完成以下步骤，验证最终集成版本。

1. 子任务检查通过后汇入组分支；再核对目标分支变化，必要时更新远程信息、同步本地目标并集成到组分支。
2. 冲突或修复后复跑受影响检查；由主会话按授权合并到本地目标分支。
3. 整体回归覆盖本组改动和受影响既有功能，再完成组验收及必要人工确认；各子任务通过不能替代整体回归。
4. 回归失败：在组分支修复 → 复验 → 提交 → 再合并 → 验证，不宣称完成。

被验证内容在合并前后完全相同且版本依据明确时，可复用有效结果。组完成不代表其他组或整个需求完成；全部需求仍须整体验收。本地组分支不自动删除，清理须另获授权并确认成果完整保留。

## 人工推送与下一组

交接放在会话中，不向需求文档写执行流水账。

- 汇报目标分支、需求及组／步骤编号、已合并提交、未推送提交、验证版本与结果、未解决事项，明确待用户人工推送；可提供操作说明，但不代推。
- 需要确认远端交付时读取实际远程信息；本地合并、准备推送的口头表态或旧远程引用均不能证明已推送。
- 下一组重新执行开组同步，从保留本地成果的最新目标分支创建新的本地组分支。
