# 计划与需求卡可执行性检查

## 摘要

检查单文档计划或多卡需求的覆盖、粒度、可执行性和验收依据。检查通过不证明业务实现正确，也不生成执行状态。

## 何时检查

生成或实质修订后、交付前检查；执行前核对既有结论是否仍适用于当前需求与源码。范围、边界、依赖或验收变化时，只复查受影响部分及覆盖关系。

输入包括原始需求与约束、单份计划或总览及全部子卡、必要源码和规则；已有确认方案时一并核对，不能只用生成文档代替原始要求。单独检查保持只读；已授权创建或修订时可修正范围内问题并复验，不扩大业务或 Git 授权。

从每份文档的“需求来源”读取已确认讨论记录，核对相关章节与适用版本，再检查卡片和验收。旧卡缺少来源时明确报告并核实，不反推讨论结论；存在影响范围或验收的缺口时不能判为可执行。

## 检查步骤

先核对形式与任务边界，再检查全部内容；不能以抽样结论代表整份需求。

单文档检查全部关联步骤及稳定编号，不强制总览、子卡链接或组编号。需分批交付、独立交接或管理复杂依赖时，指出具体拆分理由，不按文件数判断。多卡检查全部子卡、组边界、组末验证及跨卡一致性。

新生成需求卡先按 [Skill 的交付前检查](../SKILL.md#交付前检查)核对目录名、固定总览名、G/T 子卡名、平铺结构、必填章节及占位符；任一不符均须修正。修订已有卡时核对本次授权修改的结构与内容，保留未获授权迁移的既有编号和位置；纯只读检查不因旧命名或旧标题单独阻断。

1. 区分开发、调查、审查或验证任务，从原始需求建立“要求或对象 → 步骤或子任务 → 验收”对应关系，找出遗漏、重复、无依据任务及被类别吞并的独立对象。批量对象从真实来源枚举，保留类型、版本和路径，不按标题计数，也不另建进度账本。
2. 按 R1—R11 核对入口、步骤、依赖和验收，以及文档内部或跨卡的名称、接口、字段、版本与范围一致性。公共机制、调查、最终验收和单一对象均不免检；来源方案的新增、改变或未落实项须单列。
3. 仅凭文档、必要引用和项目规则，推演第一步、关键分支、交付物及失败判据。需猜业务决定、寻找缺失约定或重新拆分整批对象时报告缺口，不自行补全后判通过。
4. 运行适用文档检查，分别报告格式与语义结果；标题、数量、链接或关键词检查不能证明可执行性。

## 判定标准

按任务性质应用并说明不适用项。仅阻断会导致做错、遗漏、无法开工或无法验收的问题，文风偏好不阻断。

| 编号 | 检查什么 | 需要修订的具体情况 |
| --- | --- | --- |
| R1 范围覆盖 | 来源可定位且版本对应，每项已确认要求有任务及验收，增删与排除有依据 | 来源缺失或错版、讨论中的限制与取舍丢失、漏项、夸大覆盖，或检查夹带未授权修复 |
| R2 任务粒度 | 单文档一次完整交付；多卡每卡一个可独立接受或退回的主要结果及检查 | 为减少文件合并独立结果、为凑数量压缩范围，或将无独立结果的小动作拆卡；详见下节 |
| R3 入口真实 | 对象名、版本、文件/符号及测试或资料入口准确，拟新建产物明确标注 | 猜包名、伪造已有路径，或只写“相关代码” |
| R4 步骤可操作 | 对象、动作、检查点、关键边界与异常处理明确 | 仅写“完善、确保正确”，或依赖不可见对话和执行者猜测 |
| R5 交接与依赖 | 前置产物、接口或证据明确，依赖存在且无环，等待有必要 | 只写“完成上一项”、按编号推定依赖、上下游接口不一致，或共享文件/状态的并行写入无安排 |
| R6 可判错验收 | 输入、操作、预期或审查证据标准足以拒绝错误结果 | 仅写“测试通过”、仅信执行者自述，或按实现降低预期 |
| R7 验证与任务匹配 | 正常、边界、失败及受影响行为有入口，环境和真实/模拟边界明确 | 增量冒充全量、Mock 冒充真实模型、缺环境记通过，或要求只读审查零缺陷 |
| R8 交付与集成 | 单文档整体验收；多卡每组有可停止范围，各任务验证后再做合并版本回归 | 类别组替代对象子任务、测试全留最后、单项通过代替整体回归，或强制只读任务建分支合并 |
| R9 结构与文档负担 | 遵循所选模板、输出命名及字段含义；多卡总览可导航，文件名、H1、任务表的编号与动作名一致，共享规则单一来源 | 新卡总览名或 G/T 编号不符、擅建分组目录、缺必填章节、残留占位符、空标题、重复表格/流程、删必要判据，或对单文档强加多卡结构；旧文档只读检查不因旧命名或旧标题阻断 |
| R10 执行边界 | 执行方式、Goal 范围、清单需求、授权、无状态文档、分支映射及人工推送约定一致 | 检查当作执行授权、填负责人/勾选/进度、缺必需清单仍批量执行，或借单文档绕过同步、合并与回归、虚报推送 |
| R11 计划转换一致性 | 来源方案的边界、依赖、接口、默认选择及验收原意保留；未经过计划转换时仍检查讨论记录与卡片一致性 | 漏异常/兼容要求、静默合并任务或改接口/验收、未知项变默认值，或未完整便宣称可执行 |

## 粒度与验收示例

以下用于多卡拆分，也用于判断单文档是否已超出一次完整交付；不把每个步骤机械变成一张卡。

子任务和组内任务均不设数量上限、默认数或目标数；按独立结果及复杂度拆分，不按时长、文件数、行数或操作次数。若职责、输入输出契约、状态生命周期或环境依赖可分别验收，应优先拆分；还须检查无关入口过多或未知项导致再次规划的情况。“一个节点/功能”及详细步骤不能代替粒度判断。

每卡保留自身实现或审查、注释、测试、验收及交接/排除范围，整体核验只负责跨卡契约与覆盖。耦合不清时先缩小范围或有界调查，不能保证任意模型一次完成。

- 跨模块审查：可独立验收的接口或配置分别安排；共享基类、公共机制和覆盖对账单独安排时仍检查复杂度，不在各模块重复承担。
- 功能开发：跨文件但共同交付的行为可在一卡内保留实现与测试；可独立验收且无共同交付必要的结果应拆分，不机械一文件一卡。
- 调查：明确问题、已知入口和应返回的证据或决策建议，不编造答案，也不以“调查全部后自行决定”代替边界。
- 审查验收：声明、运行分支和相关测试均有覆盖证据；发现须有位置、触发条件、契约依据和影响，无问题对象也需证据。允许发现缺陷，不允许漏查；无法验证时按原约定报告缺口或判未满足，不降标准。
- 开发验收：例如输入“ 东 ”只返回名称含“东”的预置对象，非法状态明确失败；“筛选正常”不足以判错。

## 结论与修订

在会话报告“可执行”“需修订”或“缺信息无法判断”，不回写执行状态、不以总分抵消硬缺口。尚未实施的测试未运行，不等于需求设计不合格。

发现须包含规则编号、需求与步骤编号或完整子任务编号、文件位置、缺口、影响和最小修订建议。区分阻断项与建议，说明覆盖、实际检查和未核实项；必要检查未完成时不得无条件判为可执行。

范围内修订后复查受影响条目、依赖与覆盖，保留未解决问题；业务选择或范围变化再确认，不重复索要已有授权或无限复查。检查通过不自动启动 Goal、子代理、业务实施或 Git 操作。

主会话可直接检查。已授权或适用流程要求独立审查时，可向不继承生成对话的子代理提供原始需求、约束、文档路径及必要资料，不透露预期缺陷；子代理只读报告。工具不可用时如实说明仅做主会话自检。
