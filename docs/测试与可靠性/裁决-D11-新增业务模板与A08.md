# 裁决 D11：新增业务模板与 A08

## 摘要

[小凡]，本裁决认定：**R14 必须交付可复用、可实例化的 CRUD 模板，并由它产出代表性模块完成 A08；不要求新增产品级代码生成器或自动生成命令。**人工复制并替换文档中的代码模板可以成立，只有接入原则或步骤说明不能替代模板。架构文档对“现有业务能力”的描述不能取消整改验收要求。

## 六项裁决

裁决将需求义务、现有能力和完成证据分别认定，避免用当前缺少某项能力反推该项要求不适用。

| 问题 | 明确结论 | 可执行判据 |
| --- | --- | --- |
| 1. 是否必须有生成器或模板 | **必须有可实例化模板；不必有可执行生成器。仅按原则手写模块不够。** | 保留模板来源、输入、替换规则和实例化产物，真实接入后完成类型、规范、测试及实际入口验证 |
| 2. 最小可接受形态 | **文档代码模板 + 完整接入清单 + 可复现的真实示例及证据可以满足。** | 模板包含可复制的骨架，清单补齐真实 API、装配、菜单/平台/角色、页面及测试；只生成空目录不够 |
| 3. 无生成器时 A08 如何闭合 | **仍须执行模板实例化和端到端验收，不能删除生成步骤。** | 执行下文证据清单，所有适用门禁通过；ping、编译、菜单可见均不能单独闭合 |
| 4. 代表性模块是否留在交付仓库 | **不要求作为默认生产模块留存；仓库外干净检出验证可接受。** | 模板随框架交付；示例源码或完整实例化材料、测试、补丁及报告必须可移交和复现，不能只留临时路径与成功摘要 |
| 5. 是否包含逐文件 100% | **包含。纳管手写生产实现逐文件 LINE 100%、适用 METHOD/FUNCTION 100%。必须补测试。** | 新模块正式门禁 exit 0，每个适用文件 missed=0，并有行为断言；模板实例化不自动取得生成代码豁免 |
| 6. 文档冲突以谁为准 | **本次以指定原始要求为验收基准；架构自述不构成有效减项。** | 正式开发指南统一解释工程模板与产品生成器的边界，架构链接该指南；若要取消模板要求，必须显式变更 R14/A08 的验收基准 |

## 需求解释与事实纠正

新增业务接入的本质是证明一个新模块能够进入构建、启动、授权、页面映射、真实数据操作和质量门禁。模板还承担另一个义务：让下一位使用者能够重复这个过程。因此，一次手工联通不能同时证明模板可复用、规则相容和完整验收。

### 原始要求如何解释

[原始方案 V2](整改交接-20261004/R01-R17-原始方案V2.txt)有四处相互支持的依据：

1. R14 L329–345 的标题、整改内容和验收均明确包含模板，验收写明“由模板生成一个代表性模块”。这不是只列出现有检查对象而没有交付义务。
2. R02 L72、L77 已列出 CRUD 模板内部相对导入与检查脚本冲突、检查缺少工具却跳过等对象，进一步说明这里关注工程模板和实际检查消费方。
3. L445–449 将模板生成等验证入口列为明确交付物，说明不能在执行时临时省略。
4. A08 L461 规定生成新业务模块并接入系统，L467 要求正常、边界、失败及受影响行为，且禁止用编译代替测试。A08 应与 R14 联读，不能将“生成”孤立解释为任意手写文件即可。

原文没有指定生成器 UI、CLI、数据库反向工程或全自动生成协议。因此，要求自动化生成器会增加原文未规定的能力；允许人工实例化受版本控制的模板不减去“由模板生成”的要求。

### “没有模板”的事实需修正

本次实际读取确认以下资产存在：

| 资产 | 当前作用 | 尚不能据此证明的事项 |
| --- | --- | --- |
| [CRUD 组合模板](../../.agents/skills/weetion-development-web-standards/assets/crud-template.md) | 提供 index.vue、modules/form.vue、data.ts 代码片段，以 `[Module]`、`[module]` 替换业务标识 | 不是可原样编译的完整模块；首段明确要求补 API 类型、请求封装和后端菜单授权 |
| [CRUD 生成流程](../../.agents/skills/weetion-development-web-standards/references/crud-workflow.md) | 定义必需输入、API/页面结构、组件参考、专项检查及人工核对 | 未提供完整后端业务骨架、迁移种子、测试和同候选端到端通过证据 |
| [CRUD 检查器](../../前端代码/basic-framework-admin/scripts/quality/check_crud.py)与[转发入口](../../.agents/skills/weetion-development-web-standards/scripts/check.sh) | 检查模块文件、真实导入边界、应用类型与模块 ESLint | 检查器不是生成器，检查成功也不证明菜单、权限和真实业务已接入 |

在本次检索的脚本和工作区命令中未发现可运行的业务代码生成器。这是限定范围的检索结果，不以它证明所有未检索目录或外部工具都不存在生成器。**本案应表述为“已有前端 CRUD 文档模板，尚缺完整接入模板及验收闭合证据”，而不是“完全没有模板”。**

[管理前端架构](../架构/01-管理前端.md#新增页面与权限)也已给出具体组件映射例子：`views/system/user/index.vue` 对应 `system/user/index`。所以组件地址并非完全只有原则说明；但确实还没有把新模块的菜单行、平台类型、授权、页面地址、迁移和测试汇成一份可照做的完整清单。

### 架构自述是否限定 R14

[总体架构 L32](../架构/00-总体架构.md#系统边界)说代码生成器“不是现有业务能力”，描述的是当前系统提供哪些产品能力。工程模板、技能资料和验收夹具不等于新增一个后台代码生成器业务模块，两者可以同时成立。

该句没有写明撤销 R14、排除文档模板或替换 A08 的完成标准，因此**不构成有效限定或豁免**。若把它解释为“本仓库永远不提供任何工程模板，因此 R14 模板验收不适用”，才与指定原始要求构成实质冲突；这种解释应被否决，不能靠修改架构自述静默降低验收范围。

## 最小模板交付与过度范围

最小交付采用已有文档模板继续完善即可，无需恢复已删除的生成器业务。模板实例化可以由人或智能体完成，但输入、代码骨架和接入步骤必须足以使产物可复现。

| 形态 | 是否足够 | 边界 |
| --- | --- | --- |
| 只写“按分层新增模块、配置权限、跑检查” | 否 | 缺少模板内容和可重复的实例化依据 |
| 可照做清单 + 有完整代码的真实示例 | 有条件足够 | 示例须明确成为可复制模板，提供参数、替换映射及适配步骤；只截图或贴成功日志不够 |
| 文档化模板目录，或 Markdown 内分文件代码骨架 | 可以 | 必须覆盖完整接入并由其产出新模块；占位符、未实现接口和待授权菜单不能留在验收产物里 |
| 只生成空目录的脚本 | 单独不够 | 可作为准备工具；仍须提供模板代码、接入清单、测试及真实验证 |
| 一键生成完整模块 | 可以，但非必需 | 脚本进入索引并有真实消费测试；不得隐式改真实数据库、提交或部署 |
| 后台生成器、数据库反向工程、多数据源管理、模板市场 | 超出本案最小范围 | 原文未要求，不得为闭合 A08 自动扩展成新产品能力 |

接入清单至少应覆盖以下责任；“10 处”可作为调查分类，不能视为所有业务都固定需要修改 10 个文件：

- 后端模块 POM、根聚合 POM、server 依赖和扫描包；Controller、VO、Service、Mapper/DO 等按真实职责组织，跨模块消费存在时才增加 API/DTO。
- 新文件中文职责注释、正常/边界/失败测试和逐文件覆盖率；不提供没有行为断言的“覆盖模板”。
- 业务结构或必需元数据变化使用新的唯一 Flyway 版本，同步当前空库快照；不改已应用版本、不向既有数据库导入重建 SQL。
- 菜单目录、页面、按钮的职责和字段；特别区分 `type` 的目录/菜单/按钮与 `menu_type` 的平台类型，用户、角色与菜单的平台契约一致。
- 权限码、角色菜单和用户角色关联；选择同平台测试身份，不把角色编号 1 当成所有干净环境必然存在的常量。
- 前端 API 类型/请求客户端、views 页面、按钮权限与后端菜单 `component` 的准确映射；当前后端菜单模式不强制新增静态路由。
- 实际模块清单及维护文档；检查命令、作用范围、成功观察、失败排查与自有实验资源回收方式。

代表性例子应是小而完整的业务。例如一张简单实体表，具备列表、新增、编辑、删除、输入校验与权限拒绝，复用既有表单/表格和安全链。**本案的 ping 端点不足以代表所选 CRUD 模板**：它没有检验表单、分页、状态修改、失败后的真实数据及前端消费方。若将来选择非 CRUD 代表模块，必须显式说明为何能覆盖原模板的适用能力并获准调整验收范围，不能在本案默认替换。

## A08 闭合证据与命令

这里列的是**后续验收必须实际执行并留证的判据**，不是本次已经通过的结果。所有安装、构建、数据库写入和服务启动都应在另行建立的仓库外隔离检出中完成；本裁决没有运行这些操作。

### 证据清单

每项证据必须绑定同一个完整候选版本。退出码为 0 是必要条件，仍须核对对象、用例数量和外部结果；只看成功字样或 HTTP 200 不足以通过。

| 编号 | 必需证据 | 通过条件 |
| --- | --- | --- |
| E01 版本与环境 | 原框架提交、工作区补丁/未跟踪源码摘要、模板与规则摘要、工具版本、隔离目录及环境说明 | 新模块源码、测试、SQL、页面均可还原；没有复用个人 node_modules、旧 dist 或旧覆盖率报告 |
| E02 模板实例化 | 模块名/字段/权限等输入、模板来源、替换规则或真实生成命令、全部产物差异 | 能识别产物确由交付模板产生；生成命令若存在须 exit 0；人工实例化提供步骤记录与文件清单 |
| E03 干净工具链 | 锁定安装、内部工具入口准备、真实类型/规范/构建消费记录 | 所有必要命令 exit 0，工具包从当前位置解析，安装跳过或旧绝对路径不能算成功 |
| E04 装配与静态契约 | 构建、边界、接口、CRUD 结构、注释、类型和规范报告 | exit 0；对象包含新模块和新端点，不能只引用本案 622/167 个旧对象的结果 |
| E05 测试与覆盖 | 同候选 Surefire/Vitest、PMD/前端静态证据、逐文件覆盖报告 | 有正数目标用例；适用用例失败/错误/跳过均为 0；纳管实现逐文件 LINE/METHOD 或 FUNCTION 全覆盖，完整性问题为 0 |
| E06 数据与迁移 | 隔离空库安装、既有版本升级、重复迁移与校验、快照结构对比、真实数据断言 | Flyway 各命令 exit 0，历史 State 为 Success；新模块结构、菜单和授权有效，失败不留下部分业务状态 |
| E07 实际入口 | 本次 JAR 与本次前端构建产物启动，真实登录、权限菜单、路由、API 和数据库观察 | 授权用户从菜单进入真实页面并完成 CRUD；API 成功协议与字段正确，数据落库/删除结果可独立确认，不是兜底页或 Mock API |
| E08 失败与权限 | 无权限身份直接请求、新建非法/重复数据、取消、提交失败和授权更新 | 后端拒绝越权且无写入；失败/取消不残留错误状态；按契约重新登录/刷新后权限生效；需要数据范围时增加跨身份读写反例 |
| E09 证据有效与回归 | 同候选报告复核、受影响既有用例、模板与检查冲突的正反例 | exit 0，旧报告/零对象/必需检查跳过不能通过；原文指定的关键回归进入持续检查 |

权限失败必须检查真实 HTTP 状态与响应业务码。请求工具 exit 0 通常只说明完成通信，不能代替结果断言。授权测试应包括**同平台、非内置超管的有权限与无权限身份**：当前权限服务对内置超管还有“同平台权限菜单存在即可”的兜底，因此“角色 1 能调用”不能独自证明角色菜单关联按预期控制普通身份。

权限缓存应通过现有 Service 的失效流程处理；若实验直接写种子 SQL，必须说明如何建立空的独占 Redis 逻辑库或失效对应缓存。“干净 Redis”只能用于本次拥有的隔离资源，不能清空共享服务。授权前 403、授权后成功是有价值的对照，还须记录各次身份、平台、缓存和同版本服务条件。

## 示例留存与持续验证

原文要求完成一个代表性模块的验证，没有要求把 demo 永久装配进生产 server。因此，仓库外干净检出可以作为验收地点；是否保留源码的核心判据是可复核、可重复验证，而不是运行时是否能看到 demo 菜单。

- **必须随框架交付：**模板、参数与替换说明、唯一接入指南和必要检查入口。若模板只存于作者的仓库外目录，框架使用者无法生成模块，R14 不成立。
- **仓库外验证可接受：**保存基准提交、完整补丁及未跟踪文件、测试/SQL/前端源码、实例化记录、工具环境、日志、报告、产物摘要和脱敏行为观察；存储可移交，说明如何取得和重跑。临时目录会被删除、证据只有成功文字、补丁漏掉新文件，均不够。
- **持续验证必须保留关键回归：**R12 明确要求关键回归进入 CI。CI 可以从模板在临时副本实例化示例，不必发布示例服务；只做一次本地实验而永久丢失可运行回归，不能闭合持续工程要求。

如果选择仓库内保留，应按资产归属放置：工程代码模板可在现有 Web 技能 assets 及其配套资料下维护，模块创建/验证脚本归脚本对应类别并登记索引，接入步骤归开发指南。独立验收夹具可在现有 `scripts/tests` 下新增 fixtures 子目录并按本案分类，避免默认加入生产 reactor、生产菜单和发布 JAR。该子目录是建议新增位置，不是当前已经存在或本次已创建的目录。

如果反而选择把示例放到 Java 默认聚合模块、server 依赖和前端生产页面中，它就是实际交付代码：须进入 CI、质量门禁、授权与迁移验证，并明确是否进入发布产物，不能既默认装配又以“示例”排除检查。采用临时实例化夹具时，CI 验证其生成产物，生产交付包含模板而不必包含运行中的 demo。

## 覆盖率裁决

覆盖率要求来自原始 R12、当前测试策略和生效门禁，不能因模块是新建、体积小或由文档模板复制就改变标准。[既有 D9 裁决](裁决-D9-覆盖率口径.md#五项裁决)也保持相同口径，本案不引入例外。

[父 POM 的 quality-gate](../../后端代码/basic-framework-boot/pom.xml)在 verify 阶段绑定 PMD check 和 coverage_gate 的 `--stage full --module ... --require-prepared`。[覆盖率裁决实现](../../scripts/workflow/coverage_gate.py)的 `conclude()` 明确设置逐文件行、方法/函数阈值 100，存在未覆盖文件时 full/release 返回 1；当前机制会独立枚举生产源码，不以文件是否被测试导入决定纳管。

据用户提供的结果，新 Controller 的行、方法均 missed 2/2，目标模块 quality-gate exit 1。**明确认定为必须补测试的验收阻断，不是可以换口径的新模块特例。**必须运行真实 Controller/Service 逻辑并断言结果，还要通过实际 Spring 安全入口观察授权拒绝；直接调用方法的全覆盖测试不能单独证明 `@PreAuthorize` 生效。

纯声明与确有来源的生成物按现有规则单列不适用，不能伪造成覆盖成功。MapStruct 等受识别生成结果与人工复制、人工改写或智能体实例化的业务源码不同；后者一旦作为生产实现进入模块，仍按现行规则纳管。不得将它们移入 generated 目录、补伪造标记、降低阈值、使用平均值、audit 结果或 `-DskipTests package` 抵消失败。

100% 行及方法是必要条件；授权、状态转换等核心可达决策还要有失败和必要分支证据，不因数字达标省去行为验证。本裁决不额外要求全仓所有指令或所有非核心分支 100%。
