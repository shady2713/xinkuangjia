## 问题

作者标签断言具体身份与创作贡献，来源说明断言文件与特定上游内容之间的关系。能够证明来源，不必然能够证明作者身份；必须让检查规则表达这种区别。

[D10 裁决](裁决-D10-作者来源署名.md)要求逐文件核实、保留证据支持的真实作者，不得依据仓库拥有者、当前 Git 用户或许可证版权主体补造作者；同时已经列出“已核实来源但作者未声明”状态。[Java 检查器](../../scripts/code/java/check_staged_java_comments.py)第 694–700 行却仅允许 public 类型以非占位 `@author` 满足 `type-author`。来源证据充分而作者证据不足时，真实信息没有对应的合规表达。

冲突成立于“准确表达事实”与“必须填作者标签”的要求之间，不能靠填一个能过正则的值消解。请求所述“无法通过检查”须作限定：当前检查器实际上会放行某些中性字面量，但这种机械通过不满足 D10 的语义要求。

## 选定方案与理由

采用有证据门槛的 A，允许准确表述“所核实固定版本的对应文件未声明作者”。先保证每项断言与可取得的证据一致，再让规则检查这种表达，不要求为了格式制造身份信息。

在来源判定、类型映射和现存署名复核均通过后，允许撤回无法得到证据支持的具体作者归属，替换为下文来源说明。**这是一项受控撤回，不认定该姓名对应的人未贡献代码、恶意署名或一定误填。** 上游无标签本身不是删除本地真实共同作者的证据。若存在可靠本地原创或共同贡献记录，必须保留准确作者；若出现相反来源、作者或历史记录且无法解释，该项继续阻断。

此处明确补充 D10 的删除标签处理：符合本裁决全部条件时，可以撤回无依据的归属，不要求先证明某个人从未贡献；撤回前后文本和理由必须留证。D10 对真实作者、已知多作者、多来源及冲突项的保护继续有效。作者身份未取得证据时，清单保留缺口，但不再为了 public 类型格式而伪造身份。

| 方案 | 裁定 | 理由 |
| --- | --- | --- |
| A | 采用，并限定为证据绑定的来源状态 | 同时保留可追溯性与身份信息的准确边界 |
| B | 否决作为完成路径 | 长期保留无依据的归属不能通过作者真实性验收；永久阻断也不能被写成完成 |
| C | 否决 | “未声明作者”单独成标签缺少具体来源，且当前正则本已可能放行，容易掩盖证据缺口 |
| D | 作为补证手段 | 不强制全历史检索；只有记录证明版本、内容和署名的关联与连续性时才能恢复具体姓名，不能跨版本拼接署名 |

历史引入版本不明时，A 只通过“固定见证来源声明准确”的局部验收，不证明历史原作者已经找回。D10 的历史核实要求、D4 的许可材料与分发覆盖分别继续验收。

## 确切格式

本裁决直接确定格式，实施方据此固定解析契约。来源说明必须位于对应 public 类型的职责 JavaDoc 正文、所有块标签之前；类型职责仍独立保留。

```java
/**
 * 此处保留当前类型的准确职责说明。
 *
 * 来源：YunaiV/ruoyi-vue-pro @ ac022b15a094cf9cf82903d429b9729e72309da5（该版本未声明作者）
 * 上游文件：此处填写清单中的上游仓库相对文件路径
 * 来源依据：固定见证版本；历史引入版本未核实。
 * 本地修改：此处按实际差异说明本地适配或行为变化。
 */
```

上述路径和修改文字为说明用占位，实施时必须替换为真实内容，不能按示例原样通过。没有本地改动则写“本地修改：无。”；不能把清单中“本轮未改动”直接解释为文件相对上游没有改动。

第一行语法固定为 `来源：<仓库标识> @ <完整提交 SHA>（该版本未声明作者）`。仓库标识为真实上游 URL 对应的 `拥有者/仓库名`，例如 `YunaiV/ruoyi-vue-pro`；本轮提交 SHA 必须使用完整 40 位小写十六进制值，不能使用 `ac022b15`、分支名或浮动标签。仓库完整 URL、固定文件 URL 和原始内容指纹保存在清单中，不在每条注释里重复堆放。

“该版本未声明作者”专指这一固定提交的对应文件，不指整个上游项目，也不等于“作者不存在”。除 `@author` 外，原文件若有可靠的等价作者声明，须如实登记并处理，不能仅因标签检索为空而忽略。版权头及许可证信息按其原有角色保留，不能当作作者姓名。

历史依据行必须与证据一致。当前 174 项使用上述“固定见证版本；历史引入版本未核实。”；确已取得可靠引入记录时改用“来源依据：已核实引入版本。”，并在清单绑定记录。不得虚写“已核实”。

不使用 `@author 未声明作者`、`@author 来源：…`、`@author basic-framework` 或自造的 `@source` 标签代替正文。此例外不填写未经核实的具体人名；存在已核实本地作者时仍按真实角色另行保留，并接受 D10 的逐项证据核验。

嵌套 public 类型必须有自己的职责 JavaDoc 与类型映射；只有证明其对应上游内容也未声明作者，才可使用同一来源。多来源对象逐一列明仓库、提交和路径；任何来源有可靠作者声明都必须保留，不能用一个无作者来源覆盖其他来源。

## 证据要求

沿用 D10 清单的八个字段组和每文件唯一记录，不新建独立可写的“中性署名白名单”账本。既有取证版本按指纹留存，后续更新清单必须保留整改前事实、变更理由及候选最终版本；部署或门禁所需的派生索引只能由该清单生成，不另行手工维护。

| 字段组 | A 例外必须具备的具体证据 |
| --- | --- |
| 本地对象 | `local_path`、`scope`、`baseline_commit`、整改前后原始 SHA-256、准确署名文本与位置；补充 public 类型限定名、嵌套关系、绑定 JavaDoc 及上游类型/片段映射，不能仅凭文件名授权所有类型 |
| 上游定位 | `upstream_repo_url`、`upstream_path`、`upstream_commit`、固定 `upstream_file_url`；注释仓库、SHA、路径与此完全对应，多源分别登记 |
| 上游内容 | `upstream_sha256`、取得时间、可重取固定地址或受控原始快照；复算指纹，检查整个对应文件及相关作者声明，保存无作者标签与无等价声明的检查结论 |
| 历史依据 | `history_basis` 明确见证与引入版本的关系、已知历史及缺口；若发现历史作者或多源冲突，保存并解释，未解决不得通过 |
| 比对依据 | `comparison_inputs`、原始完整差异或足以重生成差异的原始输入、`normalization_rules`、工具版本和指纹；`evidence_route` 严格采用 D10 路线，路线 3 的 `evidence_points` 必须有两个独立且有区分力的具体片段及双方行号，解释本地差异 |
| 作者判断 | `author_status` 为“已核实来源但作者未声明”；`author_reason` 说明为何撤回或保留现存标签、是否存在本地贡献证据、声明适用的类型；`local_modification_facts` 为相对来源的实际修改；`open_gap` 保留历史等未完成项 |
| 许可关联 | 同一适用固定版本的许可证路径、指纹、声明和 D4 关联；不得从版权主体推导作者，不把 D12 当成许可验收 |
| 复核记录 | `review_by`、`review_date`、逐项结论，以及独立复核或针对该项争议的裁决；确认完整源码、最终署名和证据一致，不能只写“见原因与缺口”或拿本文件作为全部项目的通用批准 |

八组是证据契约，不是限制数据只能有当前 36 列。需要类型映射、无作者结论或复核结果的结构化子字段时，在原账本同一字段组内扩展 schema 并明确版本；不得用宽松解析、任意自然语言包含关键词或另一个批准名单替代核验。机器校验负责结构、版本、指纹、映射与结果一致性；有区分力的对应和身份贡献仍需人工判断，不能声称哈希自行证明来源或作者。

当前 174 项须补齐前后变更和最终指纹、逐类型映射、合规的证据路线、现存署名处理理由以及逐项复核，才进入合法例外。登记了一个状态值不等于以上条件已经满足。

## 规则改动的具体要求

实施方应修改 `type-author` 的表达能力与证据核验链路，并保留其他职责、方法、参数、字段等注释规则。以下要求构成方案 A 的实施边界。

1. **建立两条合规路径。** public 类型可由准确的非占位作者标签满足原格式要求，或由本裁决格式加有效逐项来源证据满足 A 例外。原作者格式分支仍不自行证明人名真实，D10 语义验收继续独立执行。缺少职责 JavaDoc 仍报 `type-javadoc`；两条路径都不满足时，继续报 `type-author`，诊断说明缺作者或缺有效来源依据。
2. **防止中性文字走作者分支。** 修改作者识别逻辑，明确拒绝“未声明作者”“来源不明”及本裁决的来源句被塞进 `@author`；不能因为旧占位集合未收录而放行。准确上游多作者、既有真实作者与合法 HTML 作者形式保持兼容。
3. **例外须验证证据，不能只匹配正则。** 读取唯一清单的对应对象，核对最终本地原始字节指纹、固定仓库/提交/路径、上游原始快照指纹及无作者声明结果、类型映射和已完成复核。使用可追溯 schema 校验的结构化结果；单独伪造一条状态记录不能获得通过。清单缺失、未核实、冲突、过期、来源有作者或复核缺口都不得启用例外。
4. **固定证据输入与交付方式。** 不把本机 `.bf-local` 绝对路径写死为规则依赖。门禁应支持显式配置受控的清单与快照位置，报告所用输入指纹，并让 CI、干净检出和交付验收能够取得同一证据。裁决与调查过程仍留在仓库外；如需交付来源材料，只交付可复算的来源数据，不能复制维护会话日志。证据不可读时退出非零并说明原因，不回退到无条件放行。
5. **所有消费者共用契约。** 暂存、工作区和全量入口采用同一证据校验。暂存检查读取暂存源码和该输入绑定的证据版本，不能拿工作区源码或旧指纹代替；工作区检查检查最终未暂存内容，全量检查覆盖干净检出的全部声明。不得改变真实索引来制造通过。
6. **覆盖纯注释变更。** 作者标签、来源说明、绑定 JavaDoc 被修改或删除，即使类型声明行不变，也必须触发该类型检查；清单、快照或类型映射变化时，检查所有受影响对象，不能只检查变动的 Java 声明行。嵌套类型不得漏检。
