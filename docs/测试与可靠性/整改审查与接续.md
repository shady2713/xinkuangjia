#### 工单 0（已修）：字典类型"删除成功"但实际未删除

**修复状态**：已修并验证。`DictTypeMapper.updateToDelete` 与 `updateToDeleteByIds` 改为经 `LambdaUpdateWrapper.set` 显式写入 `deleted` 与 `deleted_time`；`DictMapperMySqlIT` 的两个用例从"断言错误行为"改写为"断言正确契约"，修复前实测 `Expecting value to be true but was false`（红），修复后 9 项全绿；`DictTypeServiceImplTest` 的类注释同步更新。证据：`mvn -pl basic-framework-module-system -am -Dtest='DictMapperMySqlIT,DictTypeServiceImplTest' test` 退出 0，19 项通过。

**遗留（新的 schema 层发现，需迁移决策）**：`system_dict_type` 的 `uk_type` 是 `UNIQUE(type)`，**不含 `deleted`**，因此即使删除标记已正确落库，被删记录仍占用类型编码，用同一编码新建会抛 `Duplicate entry '...' for key 'system_dict_type.uk_type'`（已在 `DictMapperMySqlIT` 用 `updateToDeleteStillBlocksTypeRecreationBecauseUniqueIndexExcludesDeleted` 留档）。

- 改成 `UNIQUE(type, deleted)` 并不够：同一类型被**删除第二次**时会与第一条已删记录（`type, 1`）撞索引而删除失败。稳妥方案需要一并确定"同名类型可反复删除重建"的语义（例如用删除时间戳入索引、或改用物理删除），属迁移设计决策。
- 原始缺陷记录如下，供追溯。


- **位置**：`basic-framework-module-system` 的 `DictTypeMapper.updateToDelete(Long, LocalDateTime)`（第 63-68 行）与 `updateToDeleteByIds(Collection<Long>, LocalDateTime)`（第 77-85 行）。
- **触发路径**：`DictTypeServiceImpl.deleteDictType`（第 128 行）与批量删除（第 155 行）都依赖这两个方法完成删除。
- **实测证据**（随机隔离库 + 真实 Mapper，直查 JDBC）：`deleted=false deletedTime=2024-03-04T05:06:07 visible=true`——`deleted_time` 写入成功，**`deleted` 仍为 0**，随后 `selectByType` 仍命中该记录；批量删除同样。
- **机理**（已独立复核）：`DictTypeDO extends BaseDO`，而 `BaseDO.deleted` 带 `@TableLogic`；MyBatis-Plus 的**实体式** `update(entity, wrapper)` 不把逻辑删除列放进 SET 子句，`update.setDeleted(true)` 被静默丢弃（`deleted_time` 是普通字段所以写成功）。
- **影响**：删除接口返回成功但记录仍出现在分页/列表查询中；`uk_type` 唯一索引仍被占用，同名类型无法重建；回收站与审计无法依据 `deleted` 判定；批量删除同样无效。
- **建议修法**：改用 `LambdaUpdateWrapper` 显式 set，例如
  `update(null, new LambdaUpdateWrapper<DictTypeDO>().set(DictTypeDO::getDeleted, true).set(DictTypeDO::getDeletedTime, deletedTime).eq(DictTypeDO::getId, id))`，
  或保留实体式 update 并追加 `setSql("deleted = 1")`；批量用 `.in(DictTypeDO::getId, ids)`。
- **验收标准**：删除后 `deleted=1`、记录不再被查询命中、同名类型可重建；第八轮新增的真实行为断言需同步改回"标记为真且不可见"。
- **为什么以前没发现**：这两个方法在第八轮之前是 0 覆盖（门禁缺口正来自此），删除语义从未被真实 SQL 验证。

#### 工单 1（高）：多邮箱字段只遮蔽首个地址，其余明文输出

- **位置**：`basic-framework-spring-boot-starter-web` 的 `@EmailDesensitize` 默认正则 `(^.)[^@]*(@.*$)`，见 `EmailDesensitizationHandler`。
- **触发**：单个字段内含多个邮箱，例如 `"example@gmail.com, second@qq.com"`。
- **实测行为**：输出 `"e****@gmail.com, second@qq.com"`——第二个地址完整明文。

- **建议修法**：默认正则改为按地址逐个匹配（如 `([^@\s])[^@\s]*(@[^@\s,;]+)` 配合全局替换），或在处理器中对整段文本做多次匹配替换。

#### 工单 2（高）：整型列表静默截断

- **位置**：`basic-framework-spring-boot-starter-mybatis` 的 `CollectionTypeHandlerUtils.parseIntegerList`（Hutool `StrUtil.splitToInt`）。
- **触发**：分隔文本含超出 `int` 范围的数字，如 `"1,99999999999"`。

- **影响**：`IntegerListTypeHandler` 读出的编号与库中文本不一致且无任何告警，属静默数据失真。
- **建议修法**：解析前用 `Long.parseLong` 校验范围，超范围显式抛 `IllegalArgumentException`（或按字段语义改用 `LongListTypeHandler`）。

#### 工单 3（中）：JSON 附加信息校验强度不足

- **影响**：注解文案"附加信息必须是 JSON 格式"暗示的强度高于实际，畸形配置可落库，直到下游解析才失败。

#### 工单 4（中）：AES 解密专用错误提示不可达

- **位置**：`basic-framework-spring-boot-starter-web` 的 `AesCbcUtils.decryptFromBase64` 第 80 行抛出的"AES 解密数据格式不正确"与第 87–88 行 `catch (Exception)` 在同一 try 块内。
- **触发**：任何 Base64 解码后长度 ≤16 字节的载荷。
- **实测行为**：调用方永远收到"AES 解密失败"，专用提示只能从 `getCause().getMessage()` 读到。

- **验收标准**：新增用例断言长度不足的载荷得到专用提示、密钥不匹配仍为"AES 解密失败"，且错误信息不回显密文。

#### 工单 5（低）：姓名校验不接受含空格的外文姓名

- **位置**：`basic-framework-common` 的 `RealNameValidator` → `ValidationUtils.isRealName`，正则 `^[A-Za-z\u4e00-\u9fa5·]{2,30}$` 不含空格。
- **触发**：`"John Smith"`。
- **实测行为**：判为不合法，提示"姓名必须为 2-30 位中文、英文或中点"。
- **影响**：外文姓名含空格无法录入，属业务可用性口径问题。
- **建议修法**：字符集加入空格（并限制首尾与连续空格），或按业务确认是否只接受中文姓名后再决定是否关闭该工单。
- **验收标准**：新增用例断言 `"John Smith"` 通过、`" John"`/`"John  Smith"`/`"John1"` 仍被拒；中文姓名与中点行为不变。

### 第六轮新增发现

- **测试 import `@vben/node-utils` 会污染该包源码的覆盖率测量（工具侧，重要）**：该包 exports 指向 `dist/index.mjs`，内部用 jiti 装载 `src/index.ts`，同一份源码被二次装载后产生两套不兼容的语句/函数映射，合并后出现"同一函数两条记录、其中一条 0 命中"（实测 `path.ts` 的 `fnMap` 有两条同名 `toPosixPath`，计数 0 与 9）。后果：`date.ts`/`prettier.ts`/`path.ts` 会在源码未改的情况下从 passed 变 failed，同代码两次全量运行出现 193/194 波动。第六轮已在测试侧规避（不 import 该包），连续三次全量稳定在 191。根治要么让 exports 在测试条件下指向 src、要么让 dist 不做 jiti 二次装载，属门禁/工具侧改动。

### 前端门禁的第三类测量缺陷：`import.meta.glob` 展开的懒加载函数进入函数分母

第五轮补测 `apps/web-ele/src/router/access.ts` 时发现。该文件行覆盖已达 26/26、人手写的 4 个函数全部命中，但函数分母变成 **60**，未命中的 56 个全部是 Vite 把 `import.meta.glob('../views/**/*.vue')` 展开后生成的页面懒加载箭头函数（函数名即页面路径，声明行都是第 28 行）。

证据链：

| 实验 | 结果 |
| --- | --- |
| 只跑 `router/index.test.ts`（间接 import 该文件、从不调用 `generateAccess`） | `fnMap=2`、命中 0 |
| 跑真实调用 `generateAccess` 的测试 | `fnMap=60`、命中 4 |

即：**只有函数真正执行，glob 展开的懒加载器才进入分母**。要让这 56 个"被覆盖"，只能逐个 import 全部页面模块（正是"导入不等于被测试"要禁止的做法），或改生产源码去掉 glob。

后果：**任何在函数体内使用 `import.meta.glob` 的应用文件，一旦被真实测试就无法通过门禁**——测得越真实，分母越大。这与前两类同属工具侧归属问题，应在门禁收紧时一并裁决（逐文件"生成代码函数"是否计入分母，或对 glob 展开做归属处理）。

另附一份"高估 SFC 覆盖"的前后对照：`packages/@core/ui-kit/shadcn-ui/src/components/spinner/loading.vue` 在基线里 `fnMap=0`、45/45 行"全覆盖"（从未渲染）；被第五轮的 modal 测试真实渲染后立刻变成 36/45、2/3 的真实失败；补 6 例真实行为测试后恢复 45/45、3/3。
