## 十一、验收调用方式的关键前提：`*IT` 必须显式纳入（2026-10-06）

**这是影响覆盖率分母与"缺口行数"结论的方法学前提，必须在最终验收中固定下来。**

仓库**没有** failsafe 插件，父 pom 也没有给 surefire 增加 `*IT` include；surefire 的默认 includes 只有 `Test*`、`*Test`、`*Tests`、`*TestCase`。因此 `mvn test` / `mvn verify` **不会执行任何 `*IT` 集成测试类**。

后果（实测）：只跑 `mvn test` 时，`AdminBootstrapMain` 的真实建号成功路径（`:67,68,69`）**不可能**被覆盖，该文件会出现 17 个缺口行；而含集成测试的历史快照里它只有 2 个缺口行。同理，`BasicFrameworkWebSecurityConfigurerAdapter` 显示 31/75 行未覆盖、`BootstrapAdminService` 72/94、`OAuth2TokenServiceImpl` 53/119——这些大缺口主要来自**集成测试未运行**，而不是真的缺测试。这正是"当前 release 实跑 72 个失败文件"与"8 文件 / 12 行"两个数字并存的根源。

**固定口径**：后端一切覆盖率结论与最终验收都必须使用 CI release 阶段的同一条命令：

```
mvn -B -ntp -Pquality-audit '-Dtest=Test*,*Test,*Tests,*TestCase,*IT' -Dsurefire.failIfNoSpecifiedTests=false verify
```

**环境前置**：触发器类集成测试（`AdminBootstrapMySqlIT`、`FileUploadMySqlS3IT`、`FileUploadReconcilerMySqlS3IT`）需要 `log_bin_trust_function_creators=1`，测试账号 `bf_ci` 无 `SUPER`/`SYSTEM_VARIABLES_ADMIN`。这是**环境前置条件**而非代码缺陷；验收结束后恢复为 `0`。

**不成立的说法**：把不含 `*IT` 的 `mvn test` 结果当作"覆盖率已达标"或"缺口就是这 12 行"；把含 `*IT` 的旧快照当作当前版本已通过。两者都必须绑定到**同一次**完整运行。

2. **三条断言"因错误的原因通过"**：`verify(mock).getPatternsCondition()` 之所以通过，是因为**测试自己的前置断言 `assertThat(mock.getPatternsCondition()).isNull()` 调用了 mock**，把调用记进交互记录；Mockito **不把 stub 调用计入 verify**（最小实验：stub 后 `verify` → `WantedButNotInvoked`；stub + 1 次真实调用后 `times(2)` → 计数=1）。`verify(mock, never()).getMethodsCondition()` 因替身没被消费而**恒真**；白名单断言全部由真实控制器满足。
3. **L196 在 Spring 6.2.19 下是防御性不可达分支**：`RequestMappingHandlerMapping#getMappingForMethod` 字节码含 `info.mutate().paths("", "/")`，Spring 会把真正无路径的映射补写成 `["", "/"]`；同模块既有 `PermitAllTest` 断言的 `contains("")` 正是该补写产物。即便绕开补写，公开构建器也产不出零模式映射（`PathPatternsRequestCondition.EMPTY_PATH_PATTERN` = `TreeSet(singleton(parse("")))`，`PatternsRequestCondition(new String[0]).getPatterns()` 实测 `size=1`，都是 `{""}`）。**读数陷阱**：空串模式的 `toString()` 是空串，集合打印出来就是 `[]`，与真空集**打印完全相同**——第一版据此误判为 `∅`，后用 `size()`/`getPathPatternString()` 纠正。

**处置：未改任何生产代码**，只改测试类。驱动点从"无人消费的 bean"改到**真实映射注册表**（注册 `RequestMappingHandlerMapping` 子类到生产实际取用的那个 bean 名，子类只暴露 Spring 自己扫描用的 `registerHandlerMethod(...)`，**不覆盖** `getHandlerMethods()`）；替身是 `spy(真实 RequestMappingInfo)`，只用 `doReturn(null)` 覆盖两条路径 getter，处理器是真实 `HandlerMethod`（夹具带 `@PermitAll`）→ 收集器真实遍历到它、`urls` 为空 → **L196 真实执行**。同时**修正自证断言**：状态断言全部放在 `clearInvocations` 之前，`verify` 此后只可能观察到生产调用（`times(1)` 精确计数）；三条原断言保留并加强为 `containsExactly` + `size()==1` + `doesNotContain("", "/", "d9-pathless")`。新增用例把"构建器产不出零模式映射"变成可执行断言。

**L196 真实读数**：`mi=1 ci=0` → **`mi=0 ci=1`**；该方法 **LINE 0/28、BRANCH 0/14（100%）**；目标文件 `lines 75/75 100%`、`methods 13/13 100%`。**变异验证**：删掉该 `continue` → 定向命令退出 1，`NeverWantedButInvoked` 精确落在第 128 行 `verify(..., never()).getMethodsCondition()`（不是 NPE 等副作用）；还原后 sha256 与开工前一致、`diff` IDENTICAL、原文逐字还原、重跑退出 0。
