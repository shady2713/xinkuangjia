## D3 性能预算数值

**性质**：业务预算，必须由有权者决定。执行者只提供实测基线与建议值。

**当前证据**：[性能预算与基线](../性能优化/性能预算与基线.md)；基线文件 [`scripts/perf/budgets/baseline-w7.json`](../../scripts/perf/budgets/baseline-w7.json) 的状态为 `proposed-awaiting-authority`。A12 变异对照已真实执行：把预算收紧后核对以退出码 1 报出 14 项超预算；注入 +120 ms 真实减速后报出 70 项；目标不可达或输入损坏时退出码 2。

**需要决定的问题**

1. 是否接受"3 倍 p95 / 4 倍 p99 + 下限"的绝对预算留量？
2. 回归容差用串行 35%、并发 60% 是否符合可接受的误报代价？
3. 以"8 并发、200–320 次请求"为代表性并发模型、吞吐下限 600 次/秒是否合适？
4. 5000 行用户 + 300 行字典类型是否代表目标业务规模？
5. 预算适用范围：当前绑定单机环回环境，作为 CI 门禁需在目标运行器上重新校准，或改为只看相对回归——选哪一种？
6. 是否把预算核对纳入发布门禁？当前它是独立入口，未接入发布证据链。

**不决定的后果**：R16 的"已确定性能预算"无法宣告成立；预算只能作为建议值，不能作为发布门槛；A12 只能证明"超预算会被拦住"这一机制有效，不能证明预算数值本身被批准。

**建议**：先确认第 5、6 项（适用范围与是否入门禁），因为它们决定是否需要重新校准；第 1–4 项可沿用当前建议值并在目标环境复测后调整。

## D4 许可证与来源声明

**性质**：许可证权利，必须由有权者决定。执行者只提供可核实的证据。

**当前证据**：[上游来源与许可证证据](../部署/上游来源与许可证证据.md)。要点：管理前端保留上游 Vben 的 MIT 许可证文件，与上游 `LICENSE` **逐字节一致**（SHA-256 `26bd1c47…50ee`），版本对应 `v5.6.0`；Java 后端**没有任何**许可证文件、版权声明或第三方声明，但 103 个错误码常量中有 **85 个与 `YunaiV/ruoyi-vue-pro` 逐字节一致**，模块命名、表名前缀、`CommonResult`/`PageResult`/`BaseDO` 形态与权限表达式均一致，包名由 `cn.iocoder.yudao` 整体替换为 `com.basicframework`；仓库内检索 `yudao`/`iocoder`/`芋道`/`若依` 均无命中——**改名完整，仓库里没有任何指向来源的线索**。上游 `ruoyi-vue-pro` 的许可证为 MIT（`Copyright (c) 2021 ruoyi-vue-pro`）。

**需要决定的问题**

1. 是否为仓库根确定许可证？
2. 是否声明 Java 后端派生于 `ruoyi-vue-pro` 并随附其 MIT 声明？
3. 是否需要与上游权利人确认现有派生关系？
4. 交付物（交付包与镜像）是否必须携带许可证与第三方声明？前端如要携带需改打包规则并重新验证。
5. 字体、图标与验证码图片等资源的可分发性由谁核实？
6. 后端构建来源绑定：引入构建信息插件记录提交修订与依赖指纹，还是用运维登记替代？

**不决定的后果**：R17 的"来源与交付能力"在**声明义务**上不成立——MIT 要求保留版权与许可声明，而 Java 后端当前不满足；分发条件未定，交付物是否合规无法判定。

**建议**：至少先完成第 1、2 项（根许可证 + 后端派生声明），这是 MIT 的最低义务；第 4 项影响打包流程，建议一并确认。

## D6 来源验收口径与 113 条已登记阻断

**性质**：验收口径变更。执行者只提供已核实的逐项证据，**不能代为放宽验收条件**。

**当前证据**（全部可复算，命令与退出码见[验收矩阵](R01-R17-验收矩阵.md)第二十二节）：

- 来源索引 `docs/测试与可靠性/来源证据/d12-source-index.json` 共 **186** 条记录；检查器实测 accepted **29** 条记录 / **31** 条声明，已登记阻断 **157** 条记录 / **162** 条声明，硬失败 **0**、未覆盖 **0**、证据不可得 **0**，扫描 Java 文件 **904**。
- [裁决 D15](裁决-D15-已登记阻断与发布门禁.md) 已逐项核实「其他充分路线」：核实范围 **114** 条（81 条未验收来源说明 + 33 条带 `@author` 无来源说明的原阻断项），其中**仅 1 条**（`ApiEncrypt`，路线 2 / `E1-author-only`）证据支持改判为 accepted，**80 + 33 = 113 条客观无法满足任何充分证据路线**；33 条带作者标签者在上游全部历史版本中均无任何作者声明（33/33）。
- 云端 run `37461928496`（`stage=release`）：四个必需作业**全部 success**，门禁汇总仍 **退出 1**、`status=blocked`、**`release_verified=false`**，`applicable_blockers = 162`。

**需要决定的问题**：113 条已登记阻断（以及另 44 条 D12-174 之前就登记的原阻断来源说明）客观无法满足任何充分证据路线，
而 D15 规定「只要适用阻断未解决，发布汇总必须退出 1 且 `release_verified=false`」。
**最终条件⑤（无未解决的适用阻断）对这 113 条客观无法达成。** 请在下列三个选项中择一：

| 选项 | 内容 | 代价 |
| --- | --- | --- |
| (1) | 接受「已登记阻断」为**永久书面限制**，据此**修订条件⑤**（例如改为「除已登记并逐项披露的阻断外无未解决适用阻断」），并把 162 条阻断写入长期交付说明 | 来源关系与作者身份**始终未被证明**；交付物长期携带 162 条已披露缺口，条件⑤不再等价于「来源已核实」 |
| (2) | **授权新证据路线**：把这 113 条降级为「来源不可核实」，**恢复整改前署名或移除来源说明**，使其回到「未核实」的合法状态并退出验收链 | 等于承认这批文件既无已核实来源也无已核实作者；需同步修改检查器、索引与就地标注，并重新走负对照 |
| (3) | **维持现状**：保留 162 条已登记阻断与 `release_verified=false` | 条件⑤与发布门禁对这些条目客观不可达成，`release` 长期为红 |

**推荐项**：**(1)**。理由：它是三者中唯一既承认客观事实、又不把「未核实」伪装成「已验收」的选项；
(2) 会用「退出验收链」换取绿灯，实质是把缺口从账本上移走而不是关闭，与裁决 D15「不要求伪造第二点，也不批准永久登记作为完成路径、
不为通过门禁移除来源说明」相冲突；(3) 等于让发布门禁永久无法转绿。

**阻塞范围**：R13（注释、文档与作者来源）的来源验收部分；R01 / R15 的 `release_verified=true`；
最终条件②与⑤。

**不决定的后果**：云端 release 每次都退出 1 且 `release_verified=false`；113 条在交付说明中只能列在
「未解决阻断/未验收」，D10/D12 的来源义务无法宣告完成。执行者不会因为「客观困难」把它记作通过。

## D7 受控上游快照纳入版本控制或制品

**性质**：许可证权利与交付范围。执行者只提供事实，**不擅自扩大分发范围**。

**当前证据**：

- 来源索引的取回顺序是「受控快照优先 → 固定地址联网取回 → 取不回即拒绝」（见[来源证据说明](来源证据/README.md)）。
  本机与云端都**没有**配置 `JAVA_COMMENT_EVIDENCE_SNAPSHOTS`，报告里 `acceptance.evidence.snapshots = null`——
  **每次都联网按固定提交取回上游内容**。
- 这正是本轮两个已修缺陷的共同诱因：`794e432` 把「上游取不回」误判成「内容不符」，
  `2dbc0d7` 的浅克隆问题也是 A1 契约取不到整改前基线字节所致。两者都已修复，**但诱因（每次联网）依然存在**。
- 离线复核当前**不可行**：未配置显式快照目录时，来源验收无法完成。

**需要决定的问题**：是否把受控上游快照纳入版本控制，或作为 CI 制品/缓存随运行分发？

| 选项 | 内容 | 代价 |
| --- | --- | --- |
| (1) | 纳入**版本控制**（例如放在受控目录并绑定固定提交指纹） | **触发 D4 的上游许可证再分发义务**：把上游文件正文纳入仓库即构成再分发，须先完成 D4 的许可证声明义务 |
| (2) | 仅作为 **CI 制品/缓存**分发，不进仓库 | 同样需要确认再分发范围与保存期限；本地离线复核仍不可用 |
| (3) | 维持现状（只按固定地址联网取回） | 来源验收依赖到 `raw.githubusercontent.com` 的网络可达性；取不回时整轮受控失败（退出 2），CI 结果不稳定 |

**推荐项**：先决定 **(1) 还是 (2)**，但两者都必须**在 D4 之后**执行——先完成根许可证与后端派生声明（D4 第 1、2 项），
再决定快照的分发形式；否则会把一个未声明来源的派生仓库变成再分发上游正文的载体。

**阻塞范围**：R17 的来源与交付能力（与 D4 联动）；来源验收的离线可复核性。

**不决定的后果**：来源验收在每次 CI 运行中依赖外网可达性；一旦限流或不可达，整轮受控失败（退出 2）。
**本轮未 vendored 任何上游快照**，在决定之前也不会自行纳入。

阻断才可能关闭，而那时成立的证据路线是**路线 2 / 路线 1**。
