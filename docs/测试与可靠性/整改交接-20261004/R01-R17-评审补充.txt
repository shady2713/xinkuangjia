[shady]，这次评审有价值，尤其是要求把“统计口径、测试隔离、阶段验收”落实到具体机制。但它仍把**工作量大、当前尚未实现、技术上无法执行**混在了一起。

我的判断是：**V2 需要补充实施细节，但不应直接采用它建议的覆盖率降档、整目录排除，以及两项性能问题的定性。**

**1. 三个“阻断问题”，需要分别判断**

| 评审意见 | 我的判断 |
|---|---|
| G01 修好路径后，所有 PR 必然变红，G02 无法继续 | **推导不成立，但阶段验收机制确实应写得更具体。** |
| 逐文件 100% 导致 G03 不可达 | **没有证据证明不可达，但确实缺少模块级中间交付点。** |
| 生成代码分别统计，现有工具做不到 | **当前配置未实现属实，工具做不到不成立。需要明确配置改造任务。** |

第一条还有一个事实错误：现有 Java 检查器使用的是 `git diff --cached`，只选择暂存变更，随后检查受影响声明。**修正目录不会自动扫描全部 578 个文件。**它给出的 647 条诊断，即便来自一次全量调查，也不能直接套到每次增量检查上。[检查器入口](E:/xiangmu/kuangjiaxin/2026-dev_lj_优化/scripts/code/java/check_staged_java_comments.py:166)

反而有一个更实际的问题应该写进方案：**CI 的普通 checkout 通常没有暂存变更，不能直接调用暂存检查器就认为检查了 PR。**需要明确采用 PR 差异适配、隔离索引，还是独立全量入口，并报告实际对象范围。

我会把整改期间的机制明确成：

- **阶段验收**：验证本阶段约定的改动、回归场景和适用规则。
- **全量合规检查**：持续运行，剩余有效问题继续显示失败。
- **最终交付**：由最终候选版本的全量检查决定，阶段通过不能替代它。

这样可以继续在整改分支推进，同时保持真实的全量未达标状态。

它提出的存量诊断基线可以作为辅助方案，但需要修正两点：

- 基线应在检查器校准后建立，不能拿漏扫状态下的“修复前诊断”作为可靠基线。
- 新增诊断不一定是本次代码新增缺陷，也可能来自规则修复、工具升级或扫描范围扩大，需要归因。

所谓“只减不增”保证的是不增加已定义的问题，**不能证明存量代码已经合规**。

**2. 覆盖率可以分阶段交付，但不能随意换成 90%、70%**

我接受“增加中间验收点”，但不接受它直接给出的数字，原因有三点。

首先，90% 和 70% 没有本项目的测量或风险依据。源码总行数也不是可执行覆盖率分母，不能仅凭四万多行就证明最终目标不可能完成。

其次，它建议 **G01 就让授权、撤销、补偿达到完整覆盖并通过 A03/A04**，却把对应修复安排在 G02。当前撤销行为本来就缺失，正确的回归测试应当先失败。要求 G01 全部转绿，会重新制造它之前批评的依赖问题。

再次，“未覆盖行全部登记为死代码、生成代码或平台限制”漏掉了最常见的一类：**有效但尚未补测的业务代码**。这类代码不能被强行归入其他类别。

更合理的调整是：

- G01 建立环境、覆盖统计和能够暴露缺陷的测试入口。
- G02 修复关键行为，让对应回归转绿。
- G03 按模块划分独立验收单元，记录已达标模块和剩余差距。
- 最终候选仍按确定的纳管范围执行完整标准。

这能增加可交付的中间结果，同时保留最终要求。

**3. “工具侧实现统计口径”值得采纳，具体排除建议不能照搬**

这是这份评审最有价值的补充之一。

Java 当前的 JaCoCo 报告和门禁没有按生成来源分类，需要补充实现。但它建议“给 check rule 加 `*ConvertImpl` 排除”不够准确：

- 当前规则检查的是 `BUNDLE`。
- 规则内部的排除按被检查元素的名称匹配，不能据此从模块分母里减去指定类。
- `report` 和 `check` 是不同执行配置，修改一个不会自动修改另一个。[JaCoCo 0.8.15 检查实现](https://raw.githubusercontent.com/jacoco/jacoco/v0.8.15/jacoco-maven-plugin/src/org/jacoco/maven/CheckMojo.java)

应补充的是：**来源分类清单、报告与门禁一致的统计范围，以及分类遗漏、重叠和误排的测试。**

前端方面，建议直接排除 `shadcn-ui`、`layouts` 整个目录，我不接受。这些目录包含被应用实际消费的工作区源码，例如布局包直接参与应用布局，并已有行为测试。[实际布局消费方](E:/xiangmu/kuangjiaxin/2026-dev_lj_优化/前端代码/basic-framework-admin/apps/web-ele/src/layouts/basic.vue:7)

“来自上游”不能直接等同于“不由本项目维护的外部依赖”。

同样，生成映射代码的测试也不必然没有意义。通过真实字段转换结果验证映射契约，可以发现映射错误；需要避免的是为了覆盖率机械调用方法，却不验证结果。

**4. 两项新增性能问题，核验结果与评审不完全一致**

| 对象 | 已确认的事实 | 尚不能得出的结论 |
|---|---|---|
| 用户批量导入 | 单事务内存在逐行查询和写入；缺少明确的导入行数上限 | “已经实测每 5000 行产生固定次数数据库往返”“批量改写很简单且不会改变行为” |
| 存储统计 | 首次或缓存过期时，同实例并发调用会等待同步采集 | “当前仪表盘每 30 秒调用并造成可用性故障”“可能连续执行 100×3 秒” |

用户导入值得形成明确任务，但评审的查询公式不准确：导入时传入的用户名为空，用户名预校验会跳过；另外还存在其他查询。**Mapper 调用次数也不能未经测量直接等同于数据库往返次数。**

更重要的是，当前导入包含输入顺序、重复用户名、更新已有用户和部分失败处理等语义。批量预检、缓存和批量写入必须先确定这些契约，不能只减少 SQL 数量。[导入实现](E:/xiangmu/kuangjiaxin/2026-dev_lj_优化/后端代码/basic-framework-boot/basic-framework-module-system/src/main/java/com/basicframework/module/system/service/user/AdminUserServiceImpl.java:772)

存储统计则有三个被评审忽略的条件：

- 采集结束后有 60 秒缓存，失败和部分结果也会缓存。
- 每次启动下一页之前检查 5 秒预算，不能直接将 100 页乘以单页超时。
- 当前只找到 API 委托，未找到它所声称的仪表盘轮询消费链。[存储统计实现](E:/xiangmu/kuangjiaxin/2026-dev_lj_优化/后端代码/basic-framework-boot/basic-framework-module-infra/src/main/java/com/basicframework/module/infra/service/monitor/InfraStorageStatisticsService.java:29)

这里的 5 秒也不是严格的整体截止时间，仍值得验证超时和并发边界；但现有证据不足以把它列为已经发生的可用性故障，更不能直接删除锁。

我的处理建议是：**导入规模、查询行为和重复/更新契约可以前置调查；存储统计保留为有明确场景的验证任务，再决定是否改变刷新机制。**

**5. 其余补充，有些成立，有些需要纠正**

| 意见 | 处理判断 |
|---|---|
| Git 测试应自行构造隔离状态 | **采纳细化。** 当前已经使用私有索引和对象库，但部分测试仍依赖真实 `HEAD`；需要补独立仓库场景。 |
| 临时仓库无法识别错误目录变异 | **不成立。** 固定真实布局作为输入，要求发现预置违规；目录常量变错后漏扫，独立断言自然会失败。 |
| A11 只能在 CI 实现 | **不成立。** 工作区可以绑定输入内容摘要，索引可以绑定文件模式、路径及 blob 标识；无需先有提交 SHA。 |
| 跨模块是否使用 API DTO 尚待决定 | **已有项目规则。** 跨模块通过提供方 API 与 DTO，不需要重新作为开放问题讨论。 |
| 模块内是否共用 VO 应明确 | **采纳。** 应给出条件，不能因在同一模块就把所有依赖整体豁免。 |
| 改密应有明确默认策略 | **采纳明确策略，但重新签发当前会话不是唯一安全选择。** 撤销全部会话并重新登录也是可选方案。 |
| 许可证决策、版本矩阵应前置 | **采纳明确依赖。** 尤其会影响源码纳管范围及工具链验证的部分。 |
| 进度不足时自动砍范围 | **不采纳为默认行为。** 当前没有明确期限或预算，不能据此主动缩减你要求的质量目标。 |

A11 的确需要新增报告机制，但不能因现有命令没有输出提交 SHA，就断言技术上不可实现。Git 本身就支持按文件内容计算对象标识；最终证据还应包含工具、配置、范围及实际输入快照。[Git 内容标识说明](https://git-scm.com/docs/git-hash-object)

项目现有的[模型边界规则](E:/xiangmu/kuangjiaxin/2026-dev_lj_优化/.agents/skills/weetion-development-java-standards/references/api-controller-model.md)也已经明确了跨模块 API/DTO 要求。模块内复用模型是否合理，应结合 HTTP、Job、Consumer 等实际调用方判断，不能直接把 36 个文件全部豁免。

另外，V2 已经写明未决策略阻断对应实现。因此，“当前会话策略待确定”并不授权执行者自行保留全部会话；这个批评指出了可以进一步收敛的设计选择，却不是当前已经存在的未定义运行行为。

**我建议下一版只做以下针对性补充：**

1. 明确阶段验收、全量报告和最终合并/发布的关系，并规定 CI 如何取得实际检查对象。
2. 将 G03 拆成模块级验收单元，不凭空引入 70%、90% 阈值。
3. 为覆盖率分类增加具体配置、报告和反误排验收。
4. 明确隔离 Git 场景与本地输入快照机制。
5. 把模型复用条件、改密默认策略、版本矩阵和来源决策收敛清楚。
6. 给导入与统计分别安排符合证据强度的调查、测试或修复任务。

本轮只读核验了当前代码和配置，并运行了一个内存路径选择反例：正确目录识别 1 个对象，错误目录识别 0 个，独立预期能够识别回归。未修改项目，未重新运行完整覆盖率、数据库测试或性能压测。
