**一、整改目标与范围**

目标是建立一套能够持续执行、能够拒绝错误结果的工程体系，使框架的代码、配置、文档、模板和交付行为保持一致。

最终达标必须同时满足：

- 纳管范围明确，检查没有漏扫、静默跳过或错误排除。
- 已确认的行为缺陷完成修复，并有能识别回归的测试。
- Java、Vue、TypeScript 和辅助脚本符合明确且相互一致的规范。
- 安装、初始化、登录、授权、业务操作、升级和构建产物经过实际验证。
- 未完成、未运行、环境阻断和合理不适用能够被明确区分。
- 不能用覆盖率、测试数量、文档数量或某个总评分抵消实际缺陷。

范围按以下口径确定：

| 对象 | 纳管方式 |
|---|---|
| 实际装配的 Java 模块、发布的前端应用及其本地依赖包 | 纳入代码规范、行为测试、构建和适用覆盖率要求 |
| 仓库内保留并由本项目修改、维护的上游代码 | 核实来源后纳管，不能仅以“来自上游”为由整体免检 |
| 构建、检查、初始化、迁移、部署和模板生成脚本 | 纳入相应静态检查与行为测试 |
| 外部依赖包 | 固定来源和版本，检查依赖风险并验证集成契约；不计入本项目源码覆盖率分母 |
| 生成代码 | 检查生成来源、配置、可重复生成结果和实际消费行为；不直接修改生成结果 |
| 未装配模块、示例和平台专属代码 | 明确是否发布、由谁消费、在哪套环境验证；不得静默遗漏 |

特别区分：

- MapStruct 的手写映射声明、表达式和默认方法，需要验证映射契约。
- MapStruct 生成的实现，不等同于手写生产代码。
- DTO/VO 的纯类型声明与其中的手写校验、转换逻辑，应分别统计。
- 当前仓库只有一次初始提交，不阻碍后续差异检查、重命名测试和分支保护；恢复历史不是整改前置条件。

**二、17 项整改内容**

1. **R01：定义统一的质量判据与完成条件**

   **入口：**根目录 `AGENTS.md`、质量汇总脚本、测试策略和未来 CI 汇总任务。

   **整改内容：**

   - 分别定义“单项完成”“阶段验收通过”“允许合并”“允许发布”“框架全量达标”。
   - 检查结果至少区分：通过、失败、未运行、环境阻断、合理不适用。
   - 缺环境、超时、预期有对象却扫描到零个、引用旧版本报告，都不能计为通过。
   - 报告关联实际源码版本、配置、工具版本、检查范围及执行结果。
   - 合理不适用必须说明对象、理由和替代验证；不能只写一个 `skip`。
   - 存量诊断可以登记用于治理，但原始诊断及全量未达标状态必须保留，禁止自动扩大基线。

   **验收：**

   使用真实入口验证正常通过、实际违规、漏失环境、错误扫描范围、陈旧报告和合理不适用。预期依据来自任务契约及独立对象清单，不能直接复用检查器自己的错误路径常量。

   检查器功能验收通过，不等于被检查代码全量通过。

2. **R02：统一规则、配置与模板的实际约束**

   **入口：**根规则、项目 Skills、Java POM、ESLint、Prettier、各质量脚本和 CRUD 模板。

   首批处理对象如下：

   | 对象 | 整改要求 |
   |---|---|
   | Java 检查器仍引用旧目录 | 与实际工程路径统一，并用真实路径验证 |
   | `.env` 检查遗漏实际后端目录 | 修正匹配范围，验证强制纳入暂存时也能拒绝 |
   | 应用代码禁止导入自己的 `#/api/*` | 按真实架构修正规则，保留共享包不得反向依赖应用的约束 |
   | CRUD 模板使用合法相对导入，检查脚本却拒绝全部 `../` | 区分模块内部导入与违规跨层导入 |
   | 父 POM 覆盖率默认值为零 | 明确现状、目标及生效范围，不能把报告生成当成覆盖率阻断 |
   | PMD 注释与实际规则配置不一致 | 修正描述及真实规则；不能为了匹配文案而新增忽略项 |
   | TypeScript 源配置关闭 `no-explicit-any` | 核对最终生效配置，定义禁止范围及必要边界例外 |
   | Prettier 使用 `endOfLine: auto` | 与项目适用的 LF 要求、平台脚本例外及 Git 属性一致 |
   | CRUD 检查缺少工具或配置时跳过 | 必需环境缺失应明确阻断，不得输出成功 |

   **验收：**

   每条规则有真实消费方、合法样例和违规样例；合法结构可以通过，实际越界能够拒绝。规范要求机器检查的内容必须接入有效入口。

   “简单方法使用精确单句职责注释”继续保留，它与准确注释要求并不冲突。

3. **R03：修订开发流程及失败返回路径**

   **入口：**原开发流程图、开发指南、任务执行约定。

   **整改内容：**

   - 在实现前明确输入、输出、权限、失败行为、资源生命周期和验收场景。
   - 在运行检查前确认对象范围、环境和检查入口有效。
   - 失败后先分类，再返回对应环节：

     | 失败类型 | 返回位置 |
     |---|---|
     | 需求或权限语义不清 | 需求与验收定义 |
     | 接口、依赖或生命周期设计错误 | 设计方案 |
     | 实现错误 | 实现 |
     | 测试错误或断言不足 | 测试设计 |
     | 检查器漏扫、误报 | 检查机制 |
     | 环境不可用 | 环境准备与阻断报告 |

   - 实现、配置或相关输入变化后，使受影响的旧验证证据失效。
   - 每批包含集成后的回归，不能把各子项曾经通过拼成整批通过。
   - Git、远程交付和部署按已有授权范围执行。

   **验收：**

   用一次需求歧义、一次真实缺陷、一次检查器误判和一次环境缺失演练流程，能够走到正确处理位置，并保留真实结果。

7. **R07：建立 Vue 与 TypeScript 代码质量基线**

   **入口：**前端 ESLint、TypeScript 配置、应用源码及共享包。

   **整改内容：**

   - 先完成工具包构建，再核对 TS、Vue、测试文件的最终生效规则。
   - 治理无依据的 `any`、强制断言、非空断言和检查抑制。
   - 外部输入在边界进行校验或收窄，不能依靠类型声明假设运行时输入可信。
   - 确认 loading、空数据、失败、重复提交、取消及组件卸载后的行为。
   - 统一请求、错误转换、权限判断和状态更新的消费方式。
   - 共享组件的 props、事件、插槽和副作用契约保持一致。
   - 规则例外精确到必要边界，并有理由和验证，不能整体关闭规则。

   **验收：**

   类型检查、Lint、相关单元测试和浏览器场景通过；延迟响应、快速切换页面、重复点击和失败重试不会产生错误状态或重复副作用。

8. **R08：统一接口契约与数据模型边界**

   **入口：**实际 Controller、请求与响应模型、前端 API 封装、转换器。

   **整改内容：**

   - 按真实端点建立输入、输出、身份、权限、错误及消费者对应关系。
   - 统一分页、时间、金额、标识符、枚举、空值及部分成功语义。
   - 核实 HTTP 响应是否确实使用合适的响应模型。
   - 对敏感字段采用明确的输出范围，验证列表、详情、导出和错误响应。
   - 类型生成或接口文档从明确来源产生，避免多份手工契约长期分叉。
   - 改动公开接口时同步消费方，并明确兼容或迁移路径。

   **验收：**

   使用真实请求和序列化结果验证契约；错误输入、越权对象、空结果和敏感字段泄露都有拒绝或断言。

9. **R09：建立受控初始化与数据库迁移机制**

   **入口：**初始化 SQL、用户密码处理、部署说明及后续迁移入口。

   **整改内容：**

   - 分离数据库结构、必要基础数据、示例数据和运行记录。
   - 建立一种明确的迁移机制，记录版本及校验信息；选型结果必须验证现有 SQL 和支持的数据库版本。
   - 已执行迁移不可原地修改，后续变更通过新迁移表达。
   - 新库初始化和已有数据库升级采用不同入口。
   - 提供受控的管理员初始化方式，使用实际登录链路要求的密码协议。
   - 初始化工具拒绝错误目标、重复覆盖已有有效账号及不满足前置条件的数据库。
   - 初始化、迁移及恢复过程不在日志或仓库中保留真实凭据。
   - 涉及本次安全修复的数据结构变化，迁移与修复在同批完成。

   **验收：**

   在隔离数据库验证空库安装、重复执行、已有版本升级、中断失败和备份恢复；新安装与升级结果满足相同目标契约。

   不允许向已有数据库自动导入重建型 SQL。

10. **R10：明确安全策略并修复具体缺口**

   **入口：**认证服务、用户服务、OAuth2 令牌服务、短信服务、文件入口和 Web 配置。

   本项拆成独立可验收的任务：

   | 任务 | 整改设计 | 关键验收 |
   |---|---|---|
   | R10-A 分享登录 | 建议默认关闭；保留时定义签发资格、票据存储、有效期、使用次数、撤销和尝试限制 | 关闭时拒绝；过期、撤销、禁用用户、重放及并发消费按契约拒绝；成功权限不超出绑定账号 |
   | R10-B 管理平台注册 | 建议默认关闭；需要开放时明确账号类型、审批或初始权限 | 默认匿名注册拒绝；开放模式不能指定高权限身份或获得未授予角色 |
   | R10-C 改密与会话撤销 | 建议管理员重置、短信找回撤销全部旧会话；个人改密至少撤销其他会话，当前会话保留或重建策略待确定 | 旧访问令牌、刷新令牌及并发刷新按策略失效；不能仅删除一份缓存便声称撤销完成 |
   | R10-D 短信尝试限制 | 保留现有安全随机码、发送频控、期限和原子消费；补充验证端失败次数及请求限制 | 错误次数达到阈值后拒绝；过期拒绝；并发不能重复消费；发送限制保持有效 |
   | R10-E 文件使用资格 | 按头像、业务附件、文件管理区分资格、对象归属和配额 | 匿名拒绝写入；无资格账号拒绝；合法头像上传不受误伤；对象越界或配额超限拒绝 |
   | R10-F CORS | 接通环境变量与实际属性，明确生产允许源；按真实认证方式决定 credentials | 允许源通过；未知源浏览器跨域访问受限；配置覆盖有效；不把 CORS 当服务端授权 |
   | R10-G 权限与数据范围 | 覆盖平台、角色、部门和对象归属，核查列表、详情、导出、批量及替代入口 | 服务端拒绝越权；不能仅依赖页面隐藏或前端路由限制 |

   **组合验收：**

   - 新注册无角色账号访问“仅要求登录”的接口。
   - 改密、刷新、退出并发发生。
   - 账号禁用后继续使用已有会话。
   - 上传、登记、读取、删除由不同账号执行。
   - 权限收回后继续使用已经打开的页面和直接请求。

   当前证据支持这些任务进入整改范围，不把所有议题统一标成已经可利用的同等级高危漏洞。

11. **R11：修复账号切换与文件一致性**

   **入口：**前端认证 Store、动态路由构建与重置逻辑、文件服务。

   **账号切换：**

   - 明确动态路由、菜单、权限状态及异步请求属于哪一轮登录会话。
   - 清理旧账号增加的路由以及根路由中的残留子节点。
   - 阻止旧会话的迟到请求更新新会话状态。
   - 不能只增加一次 `resetRoutes()` 调用，而不核对动态路由实际持有关系。

   **文件一致性：**

   - 核实对象路径唯一性，避免同名、同时间上传覆盖其他对象。
   - 对象上传成功而数据库写入失败时，按明确所有权执行补偿。
   - 数据库提交结果不确定时先核对状态，不能盲删可能已经登记成功的对象。
   - 补偿失败需要可恢复记录和重试机制，不能仅忽略异常。
   - 定义删除及批量删除部分失败时的状态与重试行为。
   - 普通数据库事务不能被当成数据库与对象存储的原子事务。

   **验收：**

   A 账号退出后 B 登录，不残留 A 的路由、菜单或迟到更新；注入上传、写库、提交结果不确定和删除失败，验证不会误删已有对象，剩余不一致能够被识别并恢复。

12. **R12：前置测试设施，并建立覆盖与断言要求**

   本项分为“最小设施建设”和“业务场景补齐”，不能全部排到业务修复之后。

   **最小设施建设：**

   - 为 MySQL、Redis、对象存储建立可重复的隔离测试环境。
   - 测试自行创建数据、对象及命名空间，并在失败时清理。
   - 提供真实服务启动、认证身份、权限数据和失败注入入口。
   - 固定时钟、外部供应商等不可控边界；需要验证的真实业务链路不得被整体 Mock。
   - 关键回归进入 CI，不能只保留一次性本地脚本。

   **覆盖率与行为要求：**

   | 对象 | 要求 |
   |---|---|
   | 纳管的手写可执行生产代码 | 最终逐文件行覆盖率及适用的方法/函数覆盖率目标为 100%；按实际工具定义分母 |
   | 授权、状态转换、撤销、补偿等核心决策 | 可达决策分支完整覆盖，并有失败、并发和异常场景 |
   | DTO/VO 内手写校验和转换逻辑 | 纳入覆盖与契约测试 |
   | 纯类型声明、工具识别的生成代码 | 分别统计，不伪造无意义测试填充数字 |
   | 平台专属实现 | 在对应受支持平台运行，不能靠其他平台跳过代替验证 |

   覆盖率只是必要证据之一。关键保护还须有定向反例或变异验证，例如移除权限检查、撤销动作、补偿动作后，对应测试必须失败。

   未覆盖代码需要判断是缺测试、死代码、生成结果还是确有平台限制，不能直接删除保护逻辑来追求数字。

   **验收：**

   覆盖报告包含应纳入但从未被测试导入的文件；核心错误实现能够导致测试失败；既有合法业务行为保持通过。

13. **R13：治理注释、文档与作者来源**

   **入口：**注释规范、注释检查器、模块 README、开发及部署文档。

   **整改内容：**

   - 先校准误报，再按模块处理有效诊断。
   - 所有显式方法有准确职责说明；简单方法允许精确单句。
   - 公共接口和复杂方法按实际行为说明参数、返回、异常、副作用和边界。
   - 不机械复制方法名、堆砌模板或虚构异常来通过检查。
   - 现有作者信息按上游源码、发布版本和可靠记录核实，不能批量替换为仓库所有者。
   - README、配置示例、脚本说明与实际可运行入口保持一致。
   - 框架分发遵守现有规则，不引入无关的维护历史 Notes。

   **验收：**

   自动检查通过，并完成修改范围的语义复核；读者可按文档启动、验证和使用对应能力。历史诊断数量只是调查数据，不能直接作为真实缺陷数量或固定验收答案。

14. **R14：统一工具链、检查入口与生成模板**

   **入口：**脚本索引、根 Hook、前端 Lefthook、工作区构建工具及 CRUD 模板。

   **整改内容：**

   - 固定工具和依赖版本，验证干净环境安装、工具包构建及检查调用顺序。
   - 区分纯检查、格式修复、暂存和提交行为；质量检查不隐式修改提交内容。
   - 统一根 Hook 与前端 Hook 的职责，避免重复执行、相互覆盖或隐式暂存。
   - 新增和变更的检查、集成测试、迁移入口同步进入脚本索引。
   - 模板生成的模块要连接真实 API、注册入口和消费方。
   - 修复模板与检查脚本之间的规则冲突。
   - 检查缺少必需工具或配置时明确失败。

   **验收：**

   在干净环境完成依赖安装、内部工具构建和检查；由模板生成一个代表性模块，通过类型、规范、测试及实际入口验证。

15. **R15：建立 CI、质量汇总与合并保护**

   **入口：**拟新增的 GitHub Actions 工作流、现有各类检查命令和仓库保护设置。

   **整改内容：**

   - 第一阶段接入 CI 骨架，分别运行脚本测试、文档、Java、前端和必要集成检查。
   - 后续接入构建产物、迁移、浏览器及性能验证。
   - 前端开发约束与覆盖率检查必须实际接入，不能因为已有 `quality:verify` 就假定全部包含。
   - 汇总任务检查预期任务是否真正运行以及对应结果，不能把必需任务的跳过当成功。
   - 使用明确、稳定且不冲突的检查名称。
   - 配置适当的工作流权限，避免不可信 PR 获得不必要的写权限或凭据。
   - 在最终检查具备可满足的通过条件后，配置必需检查和分支保护。
   - 单人维护不能把 Agent 自检写成人工独立审批，也不能设置无法履行的审批要求。

   **验收：**

   受控的测试失败、必需任务跳过、构建失败及检查器失效能够阻止质量汇总通过。候选修复提交通过后可以正常进入合并流程。

   远程设置调整属于后续实施动作，本次方案更新没有执行这些操作。

16. **R16：建立性能与资源约束**

   **入口：**性能文档、代表性业务链路及后续基准测试入口。

   **整改内容：**

   - 先确定受支持环境、数据规模、并发模型和代表性场景。
   - 测量登录、权限加载、分页查询、文件操作及前端关键路径。
   - 根据实际需求制定绝对预算和回归预算，不能只看“比上次快”。
   - 关注响应分位数、数据库查询数量、内存、连接和其他资源释放。
   - 检查 N+1、无界查询、重复请求、资源泄漏和不可控重试。
   - 保留必要诊断信息，并验证敏感信息不会进入日志。

   **验收：**

   同一场景、环境和数据集下可重复测量；超过已确定预算会失败；结果对应实际构建版本。

   首轮性能预算和验证属于本次整改的交付条件，不能全部推迟为“以后持续优化”。

17. **R17：验证框架复用、来源与交付能力**

   **入口：**项目 README、构建与部署入口、上游声明和业务项目使用方式。

   **整改内容：**

   - 在范围定义阶段核实上游来源和分发约束，交付前形成一致的许可证与必要声明。
   - 不在权利来源不清楚时任意指定根许可证。
   - 从干净环境演练创建业务项目、配置、初始化、启动、增加一个功能及升级。
   - 明确公共 API、配置和数据库结构的兼容范围与废弃策略。
   - 产物能够关联源码版本、依赖和构建信息。
   - 交付说明区分应用产物与环境专属配置。
   - 持续检查门禁误报、测试不稳定和规则失效，但不能用放宽规则代替修复原因。

   **验收：**

   使用实际交付产物完成复用和升级演练；必要来源声明完整；没有依赖开发机残留文件、未记录配置或手工补丁。

**三、实施依赖与批次**

批次表达交付顺序，具体任务只等待自己真正需要的前置产物。已确认的安全修复不需要等待全部注释治理完成。

| 批次 | 工作内容 | 阶段验收条件 |
|---|---|---|
| G00：范围与规则 | R01 判据、R02 冲突清单、R03 流程、R17 来源调查，明确相关业务策略 | 对象范围、验收口径和待决事项明确；下游任务不需要猜测关键行为 |
| G01：可信检查与最小测试设施 | R04、R14 工具入口、R12 最小设施、R15 CI 骨架 | 真实违规能够被检查器拒绝；关键修复具备可运行的测试入口；全量存量问题仍如实报告 |
| G02：关键安全与行为 | R10、R11、相关 R08 契约及 R09 初始化/迁移 | 已定位问题有回归测试；关键失败、并发和组合调用链通过 |
| G03：完整代码基线 | R05—R08 其余内容、R12 场景补齐、R13、R14 模板 | 纳管范围满足既定静态规范和测试要求，没有靠遗漏对象通过 |
| G04：产物、性能与复用 | R09 升级恢复验证、R16、R17 安装复用及兼容验证 | 实际产物在干净环境可安装、运行、升级，并满足已确定性能预算 |
| G05：最终集成与交付 | R15 最终汇总和适用保护设置，全部相关文档与整体回归 | 同一最终候选版本完成全部必需检查，未完成项不被包装成全量通过 |

每批必须安排集成后的整体回归。G01 的“检查器功能验收通过”不要求把后来暴露的所有历史代码问题同时修完，但这些代码检查仍应显示其真实失败结果。

默认采用整改分支分批推进、最终候选全量验收的方式。存量基线仅辅助识别和治理问题，不替代最终标准。

| A06 | A 退出、B 登录，A 的请求随后返回 | B 的状态不被 A 的结果污染 |
| A07 | 对象上传成功、写库失败或结果不确定 | 按契约补偿或对账，不误删其他对象 |
| A08 | 生成新业务模块并接入系统 | 实际入口可用，各项适用检查通过 |
| A09 | 空库安装与已有版本升级 | 均达到预期结构及业务契约 |

| A11 | 修改后仍引用旧验证结果 | 证据版本校验拒绝 |
| A12 | 性能超过确定的预算 | 对应性能检查失败 |

正常、边界、失败和受影响既有行为均需覆盖。模拟结果不能冒充真实服务验证，编译成功不能冒充测试通过。
