## 署名政策与否决理由

署名首先回答代码来自谁；本地修改记录回答本项目改变了什么。普通修改、包名替换、格式化、注释补齐或提交代码，不会使来源作者变成本地提交者。项目内 [Java 作者规则](../../.agents/skills/weetion-development-java-standards/references/java-comments.md#作者)和 [Web 作者规则](../../.agents/skills/weetion-development-web-standards/references/web-comments.md#作者)也要求保留真实作者，不因普通修改覆盖或自动追加。

| 选项 | 裁决 | 理由与实施边界 |
| --- | --- | --- |
| A：核实后恢复上游，原创保留 | **采用** | 每个结论绑定来源和内容证据，直接满足 R13。保留上游已有的准确作者集合与角色，不把所有派生文件一概写成芋道源码 |
| B：全部改成 basic-framework，集中声明 | **否决全量替换** | 中立名称仍未回答现有作者真实性，还会抹掉真实上游或原创作者。集中声明可承担来源与许可信息，但不能抵消不真实的文件署名；即使其许可材料完备，也不能据此通过 R13 |
| C：上游与本地双重署名 | **不作为默认政策** | 未核实本地贡献即追加会把修改者暗示为共同原创者，也违背既有“普通修改不自动追加”的规则。有可靠共同创作或独立新增贡献记录且标签含义清楚时，可以逐项保留真实共同作者；不能仅因有本地 diff 就统一追加 |
| D：其他做法 | **作为 A 的配套** | 建立逐文件来源清单及本地修改说明；多源合并按片段列来源。集中许可材料由 D4 落地；它不是 A 的替代选项 |

派生文件保留核实的上游 `@author`。本地修改用中文“本地修改”说明职责变化，可链接到来源清单或可验证提交；只有身份与贡献都可核实时才写修改者姓名，不能从当前 Git 配置反推历史修改者。不要求写流水账，也不因本轮改署名就把本轮工具加成作者。

确属原创且现有作者可信时保持原样。上游没有作者标签时，不凭项目名称、仓库拥有者或最新提交者补造作者；记录“所核实版本未声明作者”及来源。如果已有本地署名也无法证实，不作猜测性替换，该项保持未核实并阻断相关作者验收。移除不实标签必须有其确为误填的证据、明确来源记录及对适用注释规则的处理，不能用删除所有标签绕过问题。

## 派生判定粒度与判据

以**本地文件**为登记和整改单位，以**实际保留的内容及其历史**为判断单位。一个文件合并多个上游文件、从其他文件抽出方法或移动类时，继续追踪对应片段；路径改变不改变来源。下列是工程来源核实的证据标准，不凭方法名相同作法律权利归属判定。

| 状态 | 可执行认定条件 | 处理 |
| --- | --- | --- |
| 已核实派生 | 满足下方任一充分证据路线，且作者声明可定位 | 恢复对应来源作者；逐项说明本地修改；多源保留全部已核实来源 |
| 已核实原创 | 有可信的本地创建过程、设计/任务及内容形成记录，能排除对应记录中的导入或复制；已解释相似候选 | 保留或纠正为证据支持的实际作者。仅“上游没搜到”不足 |
| 已核实来源但作者未声明 | 来源可核实，但对应版本无作者信息或无法支持具体人名 | 保留准确来源，不编造人名；单列作者缺口及适用规则的验收状态 |
| 未核实或冲突 | 只有候选相似、历史缺失、署名不一致且无法确定适用版本等 | 不改成猜测的作者；登记阻断项；继续核实相关发布版本、历史或其他可靠来源 |

充分证据路线如下，审查者必须能复算和读取原始材料：

1. **直接来源记录：**可靠导入记录、发布源码清单或可核验的历史补丁，绑定上游固定版本与本地文件；实际内容比对支持记录，没有相反证据。单独一个本地提交者名字不够。
2. **内容一致：**完整文件字节一致，或仅经明确列出的包名/模块名映射、换行和空白变换后，实质代码一致。保留原始文件与完整 diff；不能先消除业务常量、控制流、字符串等差异再宣称一致。
3. **明显改编：**固定上游文件与本地文件存在多处非通用的业务结构、数据模型/错误码组合、控制流顺序或独特注释对应；逐项定位对应片段并解释本地差异。至少提供两个相互独立的有区分力的对应点，不能把相邻的通用 getter 算作两个；内容过短无法满足时，需要路线 1 或其他独立可靠历史证据。

同路径、同类名、同方法名、类似 CRUD、框架约定、通用算法和相似率仅用于找候选，不能单独判派生。没有“相似率达到某百分比就恢复作者”的政策；明显改编的差异很大也可能保留来源，短小公共惯用写法高度相似也未必能确定来源。

优先核实实际引入时的上游提交或发布源码；标签须解析到提交 SHA。只有当前上游见证时，必须说明历史版本不确定，核对相关历史中内容与署名的连续性，或取得可靠引入材料，才能把该署名认作恢复目标。若暂时只能证实当前见证署名，可记录其事实，但不能写成“已恢复历史原作者”或据此关闭有冲突的项。

## 逐条证据要求

**每条署名变更和每条“核实后保持不变”的判断都必须有清单记录。** 同一批可共享上游快照、许可证和比较工具，但每个文件必须独立关联到自己的判断；仅有仓库级 NOTICE 或“来自芋道”一句话不够。

| 字段 | 必须保存的内容 |
| --- | --- |
| 本地对象 | 仓库相对路径；生产/测试/前端等范围；调查基线提交；整改前与候选最终原始字节 SHA-256；署名行及整改前后准确文本 |
| 上游定位 | 来源仓库完整 URL、文件路径、固定提交 SHA、固定文件 URL；发布标签若使用则同时保存解析后的 SHA；多源逐一登记 |
| 上游内容 | 实际取得的原始字节 SHA-256、获取时间、可重取地址或受控留存快照；被判断片段的行号/范围和署名位置 |
| 历史依据 | 已知的引入提交/发布源码或可靠导入记录；未知时明确写不确定、见证版本与历史的关系、尚缺材料 |
| 比对依据 | 原始完整 diff 或可重生成的比较输入；逐项列明规范化规则、脚本/工具版本；方法或片段对应以及仍保留的上游内容；相似分数仅作辅助 |
| 作者判断 | 状态、采用证据路线、为何保留/恢复这些姓名；本地修改事实与身份依据；冲突及未决原因。不得从 MIT 版权主体直接推导 JavaDoc 作者 |
| 许可关联 | 同一适用上游版本的许可证路径与指纹、版权和许可声明，关联到 D4 的材料与分发覆盖；本条不决定本地权利归属 |
| 复核记录 | 人工语义复核的负责方、日期、结论；独立复核者或来源争议的裁决记录；证据输入与最终文件是否一致 |

作者文字、指纹、URL、固定版本和内容对应缺一，不能仅凭“长得像”改姓名。URL 指向 `master`、无内容指纹、只比较头注释、只保留统计或没有处理来源冲突，都不能作为完整通过证据。内容指纹证明取得了哪份内容，不自行证明谁创作或谁有权许可。
