# 裁决 D9：覆盖率口径与不可达登记

## 摘要

小凡，本裁决**不接受将现有 12 行全部登记为不可达并据此放行的方案 A**。其中 5 行已在独立 JVM 中构造出带结果断言的执行路径；另外 2 行属于当前 JaCoCo 探针不能观测真实入口执行，不能称为生产代码不可达。即使只豁免行，当前门禁仍会因 `AdminBootstrapMain.main` 的方法覆盖缺口失败。

替代验收口径保持：**纳管手写实现逐文件 LINE 100%、适用 METHOD/FUNCTION 100%，并且核心可达决策分支完整覆盖**。不新增不可达豁免，不修改报告计数，不删除防御行为；通过有效补测和必要的等价可测性重构消除缺口。本裁决没有实施生产代码或门禁变更，也不签发发布通过结论。

裁决日期：2026-10-06。核实仓库：`/home/weetion/桌面/kuangjia/repo`；分支：`codex/framework-remediation`；读取时 HEAD：`c00d62184ab94c8eed65969778045048f7048595`。

裁决依据是原始验收契约、当前实现和可复核证据。测试数量与构建成功不能抵消覆盖缺口，也不能使错误的不可达分类成立。

| 问题 | 裁决 | 直接后果 |
| --- | --- | --- |
| 1. 是否接受方案 A 对这 12 行逐行豁免 | **不接受原样方案 A** | 不授权新增豁免或使 release 变绿；可保留逐行登记作为诊断证据 |

## 原始契约与证据范围

原始方案规定两类互补义务，不能把它们合并成“行级与分支级二选一”。本裁决也不将历史成功快照当作当前构建成功。

### 原始契约

[原始方案 V2](整改交接-20261004/R01-R17-原始方案V2.txt)的 R12 实际位于 L281–309，核心要求在 L297–305：手写可执行生产代码逐文件行及适用的方法/函数覆盖率目标为 100%；授权、状态转换、撤销、补偿等核心决策的可达分支完整覆盖；生成代码分别统计；关键保护需要能识别错误实现的定向反例或变异验证。

A01–A12 实际位于 L454–465：尤其 A02 拒绝缺失或过时报告，A11 拒绝修改后引用旧验证结果；L467 还要求覆盖正常、边界、失败及受影响既有行为，并禁止模拟结果冒充真实服务验证。

## 替代验收与落地路径

替代方案保留原有阈值和纳管范围，改变测试能力及代码组织。当前不能在“源码完全不变、报告计数不变、绝不新增豁免”的前提下直接将 release 判为通过。

1. 对上表 5 行补正式防御测试。替身只作用于依赖边界，真实判断、返回、抛错与资源管理必须执行；断言精确错误分类、输出或白名单。不能整体 Mock 被测业务方法，也不能把“有 assert 语句”当作断言有效的充分条件。
2. 对结构上没有合法输入的短信与文件类型兜底，将原有防御行为提取到有明确输入契约的内部校验方法。短信保留配置摘要脱敏、错误日志与拒绝；文件保留上传白名单、内容 MIME 校验与未知后缀 false。该路径可以用既有白盒测试手法验证，不能扩大允许类型或制造新的对外配置开关。
3. 脱敏兜底也可以选择合并“无注解”与“未匹配处理器”的原文输出落点，保留兜底语义；是否优于故障注入取决于最终设计。不得为覆盖数字取消脱敏或允许敏感字段无条件原样输出。
4. 数据权限反射处理保持失败透传和上下文生命周期。若工具不能按既有生成规则识别该片段，就将反射元数据取得与失败透传组织为内部可测边界，以异常输入验证传播；不需要制造 OOM 或破坏 JDK 类。
5. 入口退出采用内部可替换的终止动作，例如指向 `System::exit` 的终止函数引用。单元验证真实 main 传出的退出码，真实子进程验证默认终止动作仍退出。不能只新增一个仍以 `System.exit` 结尾的包装方法，把同一个探针问题转移到新文件。
6. 每项重构先评审正常、失败、安全和生命周期行为是否等价，再用最终编译产物核对行与方法探针。以上是设计路径，**尚未实施，不保证未构建的设计已经达到覆盖率**。
7. 在同一最终候选重新运行适用测试、完整 reactor 质量检查及 release 门禁；同时验证核心可达分支和 A01–A12 所要求的反例。不得用本次诊断实验或旧成功日志替代最终验收。

这条路径不删除防御行为、不跳过失败、不扣除纳管手写行、不降低阈值。重构允许减少重复落点，但必须保留原保护及异常契约；仅合并行、搬动行号或格式化以改变覆盖计数不属于有效整改。

## 入口探针的认定与取舍

本次认可的是当前编译产物与 JaCoCo 0.8.15 组合的观测限制。它不表示 main 没有执行，也不证明所有未来编译器、覆盖工具或重构方式都无法记录入口。

独立读取 javap：main 的 offset 0 开始计算 `System.exit` 参数，offset 18 调用 System.exit，offset 21 为 return；行号表是 L30→0、L31→21。使用本地 JaCoCo Analyzer 重跑逐探针分析，得到**只有 probe 1 覆盖 L30/L31**；当前 class ID 为 `488245109611755787`、大小 5715 bytes，与指定证据一致，当前 exec 对应此 ID 的探针总数为 58。

真实退出在该 return 之前终止 JVM；SecurityManager 抛异常也不会执行 return。保存证据中只有经过 main 的子 JVM 命中了终端读取行；仓库进程测试同时断言退出码和固定分类。这些证据足以推翻“只要子进程带 agent 就能把 main 计成已覆盖”的旧判断。

“全部探针置真”只验证计数映射，不是运行证据；本次逐探针分析也只在内存构造分析数据，未写回 exec。禁止将这些合成命中并入正式报告。

**裁决取舍：**若只要求真实入口行为，现有子进程断言具有价值，单凭探针缺口不能指称生产功能缺陷。但本案同时禁止新增豁免且要求逐文件适用方法 100%，因此为了满足该验收条件，必须实施可测终止接缝；本次不授权执行此生产修改。接缝不得暴露为环境配置或公开开关，测试必须隔离并恢复终止动作，保留缺配置、终端输入及真实退出的进程级回归。

若未来改采独立执行证据纠正测量，则应单列为“探针观测限制”，不能混入语义不可达；还必须独立裁决 main 的 METHOD 缺口。**只豁免两行而未处理方法缺口，release 仍应失败。**
