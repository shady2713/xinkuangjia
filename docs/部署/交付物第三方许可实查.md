# 交付物第三方许可实查

## 摘要

本文按**交付物本身**盘点第三方组件与许可证文本，而不是按依赖声明推断，并把读不到的缺口用可核验来源补齐。三个工具分工明确：[license_inventory.py](../../scripts/license/license_inventory.py) 只读交付物与本机缓存、读不到就记 `unknown`；[resolve_component_metadata.py](../../scripts/license/resolve_component_metadata.py) 在**显式允许联网**时按权威来源核实坐标与许可证标识并逐条记录来源；[generate_third_party_notices.py](../../scripts/license/generate_third_party_notices.py) 把核实结果生成为随交付物分发的 `THIRD-PARTY-NOTICES` 与许可证正文目录。

本轮实测结论：**后端 192 个第三方组件的坐标与许可证声明已 100% 确定**（上一轮有 57 个读不到、56 个无坐标），**后端 JAR 随包 1 份 THIRD-PARTY-NOTICES + 111 份许可证正文**（上一轮 0 份），**前端交付包 256 个条目、随包 2 份许可材料**（上一轮 0 份），前端产物入口分块已带许可横幅。**仍有 4 条声明需人工或法务确认，本文不代做判断**；本项目自有代码的许可仍待有权者决定。

## 盘点与核实口径

| 环节 | 事实来源 | 读不到时 | 理由 |
| --- | --- | --- | --- |
| 盘点 | 交付物本身：后端 `basic-framework-server.jar`、前端 `.cache/release/前端交付包.zip` | 记 `unknown` 并单列 | 依赖声明只说明"打算带什么"，交付物才说明"实际带了什么" |
| 坐标（第一优先） | 构件内 `META-INF/maven/**/pom.properties`，且 `artifactId-version` **与包内文件名对齐** | 转下一级来源 | 聚合打包的构件内部带多个模块的 `pom.properties`，不对齐的那份不是构件自身 |
| 坐标（第二优先） | 本机 `~/.m2` 中同名构件唯一命中，且与包内构件 **SHA-256 逐字节一致** | 转下一级来源 | 只认字节一致的内容，不按文件名猜 groupId |
| 坐标（第三优先） | Maven Central 检索接口唯一命中 groupId，且下载的构件与包内构件 **SHA-256 逐字节一致** | 记为坐标未确定 | 同上 |
| 许可证标识 | 本机 POM 的 `<licenses>`；本机无结论时用 Maven Central 同坐标 POM 与父 POM | 留空并写明原因 | 许可证推断属合规判断，不属于事实盘点 |
| SPDX 标识符 | 优先按 POM **自己声明的许可证 URL** 映射，URL 缺失时才按名称原文；未登记的写法一律留空 | 列入"需人工确认" | 不用"看起来像"去套标识符 |
| 许可证原文 | 构件自带文本 → SPDX 官方清单固定 tag `v3.26.0` 的标准文本 → 只登记条款地址 | 明确写"原文未随包提供" | 绝不代写条款 |

复现命令（仓库根，输出目录在仓库外）：

```bash
# 1) 盘点：只读交付物
python -B -X utf8 scripts/license/license_inventory.py --jar <JAR> \
  --frontend-archive <交付包.zip> --lockfile <pnpm-lock.yaml> --out <仓库外目录>/license-inventory.json
# 2) 核实：--allow-network 才会访问 Maven Central 与 SPDX，逐条记录来源
python -B -X utf8 scripts/license/resolve_component_metadata.py --jar <JAR> --allow-network \
  --cache-dir <仓库外目录>/net-cache --additional-evidence scripts/license/known_license_evidence.json \
  --out <仓库外目录>/license-metadata.json
# 3) 生成随包材料：离线运行，先核对报告与构件的第三方闭包摘要一致
python -B -X utf8 scripts/license/generate_third_party_notices.py \
  --metadata <仓库外目录>/license-metadata.json --jar <JAR> \
  --out-dir 后端代码/basic-framework-boot/basic-framework-server/target/generated-license-materials
```

第 3 步必须在**发布打包之前**执行：`pom.xml` 只在 `target/generated-license-materials` 存在时把材料打进 JAR，
**漏执行不会让构建失败，只会退回"零份许可材料"**。正因如此，发布链另有一道按交付物实际字节裁决的独立门禁：

```bash
# 后端：核对交付 JAR 的实际闭包与材料是否一致（不生成、只裁决）
python -B -X utf8 scripts/license/verify_license_materials.py \
  --jar 后端代码/basic-framework-boot/basic-framework-server/target/basic-framework-server.jar --require-prepared
# 前端：核对产物与交付压缩包的实际字节、材料条目与本次构建分块引用的包是否一致
cd 前端代码/basic-framework-admin && pnpm quality:license:gate:release
```

完整发布顺序见[构建离线部署包说明](构建离线部署包说明.md#license-materials)。

## 核实中发现并修复的工具缺陷

两处缺陷都会让盘点结果**失真**，本轮已修复并补了反例用例。

**(1) 无 XML 命名空间的历史 POM 被整体漏读。** `org.apache.xmlbeans:xmlbeans:5.3.0` 在 Maven Central 上的 POM 根元素是裸
`<project>`，原实现按 `{http://maven.apache.org/POM/4.0.0}licenses` 精确匹配，读不到它的 `<licenses>`，
于是把"我们没读出来"记成了"上游没声明"。修复后两个工具都按元素**本地名**查找。
反例用例：`test_pom_without_namespace_still_reads_licenses`、`test_pom_parent_is_read_without_namespace`。

**(2) 聚合打包构件的坐标被取成内部模块的坐标。** `org.ehcache:ehcache:3.10.9` 是聚合 JAR，内部带 11 份
`META-INF/maven/**/pom.properties`（`org.ehcache.modules:ehcache-107`、`ehcache-api`、`ehcache-core`、`ehcache-impl`、
`ehcache-xml`、`org.ehcache:sizeof`、`org.terracotta:*` 等），**唯独没有它自己的**；按首条取坐标会得到
`org.ehcache.modules:ehcache-107:3.10.9`，这是错的。修复后只有 `artifactId-version` 与包内文件名对齐的那份才被采信，
全量 204 个构件实测：5 个含多份 `pom.properties`，其中 4 个按文件名唯一对齐，只有 `ehcache-3.10.9` 落到本机仓库字节比对，
确定为 **`org.ehcache:ehcache:3.10.9`**。许可证结论不变（Apache-2.0），**坐标变了**。
反例用例：`test_pom_properties_must_match_component_file_name`、`test_shaded_jar_without_own_properties_is_not_guessed`。

## 后端随包许可材料

**生成方式（两步，都不修改任何既有许可声明）**：

1. `resolve_component_metadata.py --allow-network` → 产出核实报告 JSON：每个组件的坐标、版本、坐标来源与证据、
   许可证声明来源、沿父 POM 链的每一段（坐标、来源、URL、SHA-256）、SPDX 标识符与映射依据、需人工确认项、
   构件自带文本条目与 SPDX 标准文本。
2. `generate_third_party_notices.py`（**离线**）→ 读报告与 JAR，先用**第三方构件闭包 SHA-256** 核对一致性，
   再把材料写进 `--out-dir` 的 `META-INF/` 下。

**打包方式（最小 Maven 改动）**：`basic-framework-server/pom.xml` 增加一个 `<resources>` 目录
`${project.build.directory}/generated-license-materials`（同时显式保留原有 `src/main/resources`）。
`spring-boot-maven-plugin:repackage` 会把 `BOOT-INF/classes` 下的 `META-INF/**` 提升到可执行 JAR 根目录，
因此材料最终落在 **`META-INF/THIRD-PARTY-NOTICES`** 与 **`META-INF/licenses/*.txt`**，交付方拿到 JAR 即可见。
该目录不存在时 Maven 静默跳过、不阻断既有构建；漏生成不会报错，只会退回零份材料。

**材料内容**：每个组件给出坐标、版本、包内条目、坐标来源与证据、上游声明原文（名称 + URL + distribution）、
SPDX 标识符、许可证原文位置（构件自带文本 → `licenses/<摘要>.txt`；或 SPDX 标准文本 → `licenses/<摘要>.txt`；
都没有就写"原文未随包提供"并列出条款地址），需人工确认项逐条列出；末尾单列自有模块坐标并注明"许可待有权者决定，本文件不作授予"。
文件开头固定写明"本文件不构成合规结论，也不代表任何许可选择已获批准"。

**闭包摘要（自证机制）**：材料里记录的是**第三方构件闭包 SHA-256**（只由 192 个第三方构件自身的 SHA-256 决定）。
之所以不用产物摘要，是因为材料被打进 JAR 后产物摘要必然变化；之所以排除 12 个自有模块，是因为它们每次重新构建
字节都不同，算进来就永远核对不上。核对方可直接从 JAR 重算核对：

```bash
python -B -X utf8 - <<'PY'
import hashlib, re, zipfile
z = zipfile.ZipFile("后端代码/basic-framework-boot/basic-framework-server/target/basic-framework-server.jar")
third = [n for n in z.namelist()
         if n.startswith("BOOT-INF/lib/") and n.endswith(".jar") and "basic-framework" not in n]
calc = hashlib.sha256("\n".join(sorted(hashlib.sha256(z.read(n)).hexdigest() for n in third)).encode()).hexdigest()
text = z.read("META-INF/THIRD-PARTY-NOTICES").decode()
print(calc == re.search(r"第三方构件闭包 SHA-256：([0-9a-f]{64})", text).group(1))
PY
```

本轮实测：材料内 `0afc815e7fe3cf2e5f55421427ccd55c5f40ba58cb611c2f3573dbbbd38909ea`，
从交付 JAR 的 192 个第三方构件重算得同一值，**一致**。

## 前端随包许可材料

上一轮 `internal/vite-config/src/plugins/license.ts` 导出了横幅插件但**未在任何 Vite 配置注册**，产物入口分块顶部没有横幅。
本轮补齐三件事：

| 改动 | 文件 | 说明 |
| --- | --- | --- |
| **注册插件** | `internal/vite-config/src/plugins/index.ts` | 在 `loadApplicationPlugins` 中按 `condition: options.isBuild` 注册；开发服务不产出静态资源，也不该反复写许可证文本 |
| **横幅的许可行不再硬编码** | `internal/vite-config/src/plugins/license.ts` | 许可行取自应用 `package.json` 自身声明的 `license` 字段，标签由 `License:` 改为 `Declared License:`；清单未声明时写"未在包清单中声明（待有权者决定）"，**不在代码里硬编码任何许可证** |
| **产物自带许可材料** | `internal/vite-config/src/plugins/third-party-notices.ts`（新增） | 按**本次产物实际引用的模块**生成 `THIRD-PARTY-NOTICES` 与 `licenses/*.txt` |

**为什么用构建期模块表而不是锁文件**：锁文件登记的是全部已解析依赖（含构建期与开发期），不等于交付物包含的组件；
插件改用 Rollup 输出的分块模块表反推运行期闭包，只有真正进入产物的第三方包才会被登记。这同时补上了上一轮"静态产物无源码映射，
无法证明包含哪些第三方运行期代码"的缺口。

本轮实测：产物包含 **92 个第三方包**（`vue`、`element-plus`、`axios`、`dayjs`、`zod`、`@ctrl/tinycolor` 等），
每个给出包名、版本、`package.json` 声明的许可证、声明作者与仓库、安装位置、许可证原文位置；
包清单未声明的（如 `zod-defaults@0.1.3`）如实写"包清单未声明"，不套用看似合理的许可证。
许可证正文按内容摘要去重后 **66 份**写入 `licenses/`。

**`LICENSE` 的性质**：`apps/web-ele/dist/LICENSE` 逐字取自工作区根目录已有的 `前端代码/basic-framework-admin/LICENSE`
（`MIT License` / `Copyright (c) 2024-present, Vben`），是**继承自上游工作区的许可证文本，只覆盖继承来的前端代码，
不覆盖本项目新增代码**；材料正文中对此有明确说明。把该文件随包分发**不等于**为本项目自有代码选择了 MIT。

**横幅实测**：入口分块 `js/index-*.js` 顶部已带

`Declared License: MIT` 来自 `apps/web-ele/package.json` 已有的 `"license": "MIT"` 字段（上游继承，全工作区 38/38 个包清单同值），

<a id="release-gate"></a>

## 许可材料发布门禁

**为什么需要这道门禁**：许可材料的生成是可选前置步骤。`pom.xml` 的 `<resources>` 在
`target/generated-license-materials` 不存在时**静默跳过**，构建照样 `BUILD SUCCESS`，交付物只是退回零份材料；
前端同理，材料没生成时既有质量命令链仍会通过。**漏生成此前不会让任何东西失败**，这正是要补的缺口。

门禁按**交付物实际字节**裁决，**不生成、也不补写任何材料**——材料缺失只能由前置步骤解决，
门禁只负责拦住缺失。两道门禁的判定项：

| 门禁 | 判定项 | 事实来源 |
| --- | --- | --- |
| `scripts/license/verify_license_materials.py` | `notices-present`、`closure-digest`、`component-count`、`entry-coverage`、`coordinates`、`own-modules`、`license-texts`、（`--require-prepared` 时）`prepared-state` | 交付 JAR 的 `BOOT-INF/lib` 实际条目、`META-INF/THIRD-PARTY-NOTICES` 与 `META-INF/licenses/` 的实际字节、构件内 `pom.properties` |
| `前端代码/basic-framework-admin/scripts/quality/license_materials_gate.py` | `notices-present`、`license-origin`、`declared-count`、`package-resolution`、`license-texts`、`chunk-closure`、（`--require-prepared` 时）`delivery-archive` | 产物目录与交付压缩包的实际字节、本次构建的分块模块表、工作区已安装包清单 |

**两处"独立"是刻意的**：

1. 后端的坐标核对不读材料里的自述，而是读**构件自身**的 `pom.properties`（仍按 `artifactId-version` 与文件名对齐，
   聚合件不采信内部模块坐标）。192 个第三方构件中 135 个能自证并逐条核对一致，其余 57 个如实计为"包内无法自证"，
   不冒充已核对。
2. 前端的 `chunk-closure` 不读材料里的包名，而是读**本次 Rollup 分块模块表**（`.cache/build-record/license-closure.json`，
   只在构建缓存目录、不随交付包分发），由门禁**自己**的模块标识解析实现重算包集合。压缩后的静态产物已不保留模块标识，
   产物字节本身无法反推闭包，因此闭包只能在构建期留痕；门禁与生成器不共享这段解析代码，任一方解析错都会立刻暴露。

**接入位置**：`ci_gate.RELEASE_CHECKS` 的 `backend-license-materials` 与 `frontend-license-materials`，
在 CI 中分别位于 `backend` 与 `frontend` 作业的**发布阶段**，是 `release-backend.json`／`release-frontend.json`
的必需检查项；缺少任一项，`门禁汇总` 作业会直接拒绝发布证据。前端另有 `quality:license:gate` 已接入 `quality:verify`。
`release_verified` 仍为 false，本轮没有、也不试图改变这一点。

**本轮实测读数**（同一最终提交，后端 `mvn -o -Pquality-audit verify` 与前端 `build:recorded` + `release:pack` 的产物）：

| 项 | 后端 | 前端 |
| --- | --- | --- |
| 被测交付物 | `basic-framework-server.jar`，455 个条目 | `.cache/release/前端交付包.zip`，255 个产物文件 + `交付清单.json` |
| 实际依赖闭包 | `BOOT-INF/lib` 204 个构件（第三方 192 + 自有 12） | 分块模块表反推 92 个第三方包 |
| 材料登记条数 | 192（与实际闭包一致） | 92（与分块实际引用一致） |
| 随包材料 | `META-INF/THIRD-PARTY-NOTICES` 1 份 + `META-INF/licenses/` 111 份 | `THIRD-PARTY-NOTICES` + `LICENSE` + `licenses/` 66 份 |
| 门禁结论 | 8 项全部通过 | 6 项全部通过（`--require-prepared` 下 7 项） |

**门禁不裁决的一处事实（如实记录）**：后端 `META-INF/licenses/` 下 111 份正文里，有 15 份没有被材料条目引用。
成因是生成器把构件内**全部**许可证类文本都收进了正文目录，而渲染时只引用核实报告里登记过的那部分。
多出来的正文不是缺材料，也不影响分发义务，但属材料内部不一致；本轮门禁不据此判失败，也未修改生成器口径，
如实登记待后续处理。

## 上游快照的分发义务

仓库已按 D7 授权纳入最小固定上游证据快照（`ruoyi-vue-pro@ac022b15…`，MIT）。本轮核对结论不变：

| 问题 | 结论 | 依据 |
| --- | --- | --- |
| 快照是否属于最终交付物的一部分？ | **不属于** | 后端 JAR 与前端交付包都不含快照目录，也不含上游 LICENSE 原文 |

| 交付物侧的上游来源声明 | 仍缺 | 后端随包材料只登记第三方组件；**上游派生代码的来源与许可声明仍未随包分发** |

**必须说清的一点**：MIT 要求"在所有副本或实质性部分中保留版权声明和许可声明"。

本轮补齐的是**第三方**许可材料，**上游来源声明仍需有权者决定是否随包分发**。
