# 自有代码许可决策材料

> **此决定属有权者，本轮未代定。** 本文只登记事实、划清边界并列可选方案。**没有**给全库贴 MIT，**没有**新建 `LICENSE` 文件，**没有**修改任何现有许可声明。本文不是决定，也不是决定的默认值。

## 摘要

仓库当前**没有根许可证**：后端 904 个 Java 文件、全部 POM、`README.md` 与 `AGENTS.md` 都没有 Java 侧许可声明；而管理前端**已经有 MIT 声明**——一个与上游逐字节一致的 Vben MIT `LICENSE` 文件，外加 38 个 `package.json` 中的 `"license": "MIT"`。同一仓库内两种状态并存，本身就是需要决定的事实。

派生的范围是可核实的：后端有 186 个逐字节保留的上游文件（`ruoyi-vue-pro`，MIT），前端整个工作区继承自 `vue-vben-admin`（MIT，5.6.0）。派生的**义务**与自有的**权利**是两件事，需要分别决定。

## 派生与自有的边界

边界依据仓库内已有的可核实证据（[上游来源与许可证证据](上游来源与许可证证据.md)与[来源证据索引](../测试与可靠性/来源证据/README.md)），**本轮不新增判断，只做归纳**。

### 确定属上游派生的部分

| 对象 | 证据 | 规模 |
| --- | --- | --- |
| Java 后端的框架骨架 | 上游 `ruoyi-vue-pro@ac022b15…` 的 186 个文件逐字节保留在证据快照中，哈希清单逐条登记；`ErrorCodeConstants` 的 103 个错误码常量中 **85 个与上游逐字节一致**；模块命名、表名前缀、`CommonResult`/`PageResult`/`BaseDO` 形态、`@ss.hasPermission` 权限表达式均与上游一致，仅包名由 `cn.iocoder.yudao` 替换为 `com.basicframework` | 186 个上游文件，408 823 字节 |
| 管理前端整个工作区 | `LICENSE` 与上游 main 分支逐字节一致；`apps/web-ele` 为 `@vben/web-ele 5.6.0`、`license: MIT`，与上游标签 `v5.6.0` 完全一致；各工作区包与内部包同为 `@vben/* 5.6.0`；工作区内 `@vben/*` 全部通过 `workspace:*` 链接本地源码 | 整个 `前端代码/basic-framework-admin`（38 个包） |

**上游许可**：两者都是 MIT —— `ruoyi-vue-pro/LICENSE`（`Copyright (c) 2021 ruoyi-vue-pro`）与 `vue-vben-admin/LICENSE`（`Copyright (c) 2024-present, Vben`）。

### 明确属仓库自有的部分

| 对象 | 依据 |
| --- | --- |
| 三个 starter 与全部整改新增的 Java 代码 | 不在上游 186 个文件清单内；模块坐标为 `com.basicframework:*`，上游为 `cn.iocoder.yudao:*` |
| 整改轮次新增的前端代码与测试 | `apps/web-ele/src/**` 中整改新增/修改的文件不在上游 5.6.0 标签对应内容内 |
| `scripts/**`、`docs/**`、`数据库文件/**`、`.github/**`、`.githooks/**`、`AGENTS.md`、`README.md` | 仓库自身的管理与工程设施，上游无对应物 |
| 12 个本地基线文件（`本地基线/`） | 是本仓库整改前提交 `f13229e0…` 的文件，不是上游文件 |

### 边界上无法机械判定的部分

- **前端工作区内被修改过的上游文件**：既包含上游派生内容，又包含本仓库的改动。MIT 允许修改并再分发，但「一个文件里哪些行是自有的」目前**没有**任何逐行归属记录。
- **是否构成「实质性部分」**：由权利方判断，不由工具判断。

## 可选方案

以下四类方案**并列**，不排序、不推荐、不预选。

### 方案 A：保持现状，不新增任何声明

| 项 | 内容 |
| --- | --- |
| 做法 | 不新建 `LICENSE`，不补后端来源声明，不动前端已有的 MIT |
| 后果 | 前端继续以 MIT 事实上声明（含自有代码，意图未确认）；后端继续无任何声明，派生作品的 MIT 义务**仍未履行**；交付物依旧不含任何声明，R17 的分发缺口原样保留 |
| 适用场景 | 明确暂不外发、只在内部使用；或需要先完成法务评估再定 |
| 风险 | 只要对外分发一次，就同时面临「自有代码无声明」与「派生作品未保留上游声明」两个缺口 |
| 需要谁决定 | 权利人 |

### 方案 B：为仓库自有代码选定一个许可证，并声明后端派生关系

| 项 | 内容 |
| --- | --- |
| 做法 | 新建根 `LICENSE` 声明自有代码条款；在后端补充来源声明（指明派生自 `ruoyi-vue-pro`、MIT）并随 JAR/镜像分发上游 LICENSE 与 NOTICE |
| 后果 | **履行**上游 MIT 的「在所有副本或实质性部分中保留版权声明与许可声明」义务，关闭 R17 的分发缺口；同时把自有代码置于所选条款之下（MIT 允许闭源分发，Apache-2.0 额外要求专利授权与变更说明，GPL 类会要求衍生作品同许可，**差异很大**） |
| 适用场景 | 计划对外分发或交付客户；需要让接收方能合法使用 |
| 风险 | 一旦选定即不可逆地影响下游；条款选择需与商业策略一致；前端已有的 MIT 需与之对齐或显式说明差异 |
| 需要谁决定 | 权利人；涉及条款法律含义时需法务 |

### 方案 C：只声明第三方部分，自有代码继续不声明

| 项 | 内容 |
| --- | --- |
| 做法 | 交付物中随附**第三方**许可证汇总与上游声明；仓库根仍不声明自有代码条款 |
| 后果 | 解决了「随包第三方许可材料」这一项，但**不解决**派生作品的 MIT 保留声明义务；自有代码对外分发时，接收方仍无使用授权 |
| 适用场景 | 自有代码确定不对外提供、只作为内部框架使用，但交付物需要交代第三方构成 |
| 风险 | 容易被误认为「许可问题已解决」；MIT 的保留声明义务与第三方清单是两件事 |
| 需要谁决定 | 权利人 |

### 方案 D：逐目录差异化声明

| 项 | 内容 |
| --- | --- |
| 做法 | `前端代码/basic-framework-admin` 保持 MIT；`后端代码/` 增加后端来源与许可声明；`scripts/`、`docs/` 等按需各自声明 |
| 后果 | 声明与实际来源结构对齐度最高；但引入多套条款后，任何跨目录的组合发布都要逐套核对义务，且前端「MIT 覆盖自有代码」这一既成事实仍然存在 |
| 适用场景 | 不同目录归属不同主体、或部分目录计划以不同条款对外提供 |
| 风险 | 维护成本最高；`package.json` 的 `"license": "MIT"` 与新增的目录级声明可能不一致，需要同步机制 |
| 需要谁决定 | 权利人 |

### 各方案的共同前提

无论选哪一个，以下事实都不由本方案决定、需要单独处理：交付物是否随包携带许可证文本（现打包规则不接受无扩展名文件）、57 个组件的许可证元数据离线不可核实、5 个字体与图像资源来源未登记。详见[交付物第三方许可实查](交付物第三方许可实查.md#gaps)。

2. **没有**新建 `LICENSE`、`NOTICE` 或任何许可声明文件。
3. **没有**修改任何现有许可声明——前端 `LICENSE`、38 个 `package.json` 的 `"license": "MIT"`、`license.ts` 的模板，全部保持原样。
4. **没有**修改前端打包规则以让许可证文件进入交付包。
5. **没有**下载或补写任何第三方许可证文本到仓库。
6. **没有**替权利方选择方案 A/B/C/D 中的任何一个。

本轮对该问题做的唯一实质工作，是把事实查清楚并写成本文；**决定权仍在有权者手中**。
