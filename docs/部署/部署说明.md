# basic-framework 服务器部署

## 摘要

在构建机生成Java JAR、管理前端dist和运行镜像，在目标服务器安装或复用MySQL、Redis、MinIO，再运行Java、前端与HTTPS入口网关。本文提供Linux服务器的独立容器安装路径，不依赖个人开发目录或本地Compose；已有中间件可按对应配置复用。上游来源与许可证证据另见[上游来源与许可证证据](上游来源与许可证证据.md)；分发前的声明义务尚未落实，不能把本文的安装步骤当作已通过合规评审。

## 环境与交付基线

先确认Linux发行版、CPU架构、磁盘容量、Docker版本及外部访问域名。以下容器方式要求目标已安装可用Docker Engine；安装命令随操作系统选择，不能把某个系统的安装包用于其他发行版。断网服务器按[离线部署包](构建离线部署包说明.md)先准备安装资源。

| 组件 | 当前依据与要求 |
| --- | --- |
| JDK / Maven，构建机 | 编译目标Java17；兼容JDK、Maven3.8+；先用java -version和mvn -version核对 |
| Node / pnpm，构建机 | Node >=20.19.0；pnpm packageManager固定10.28.2，使用已有锁文件 |
| Java运行 | 当前Dockerfile使用eclipse-temurin:21-jre；不修改源码编译目标 |
| 前端运行 | 当前Dockerfile使用nginx:1.27-alpine；生产路径/admin/，hash路由 |
| MySQL | 框架使用8.x；安装示例mysql:8.0.46，版本变化须检查SQL与驱动兼容 |
| Redis | 安装示例redis:7.4.10-alpine；项目未固定补丁版本，换版本须复验 |
| MinIO / mc | 本文使用固定镜像摘要；对应MinIO RELEASE.2025-09-07T16-13-09Z、mc RELEASE.2025-08-13T08-35-41Z |
| 网络 / 数据 | 容器独立内网、数据库和对象持久卷、备份位置、真实TLS证书及域名 |

目标服务器运行应用镜像时无需Maven、Node或pnpm。示例固定镜像按linux/amd64使用；其他CPU架构须取得匹配镜像并独立验证。正式包登记镜像摘要和平台，不以可变标签代替版本证据，也不自动升级既有中间件。

## 构建应用

构建机使用同一源码版本完成后端与前端验证，再装配镜像。以下SOURCE_ROOT由部署者设为源码根，RELEASE为本次发布标识。

```bash
export RELEASE=your-release
cd "$SOURCE_ROOT/后端代码/basic-framework-boot"
mvn -q -Pquality-gate verify
docker build -t "basic-framework-backend:$RELEASE" basic-framework-server

cd "$SOURCE_ROOT/前端代码/basic-framework-admin"
pnpm install --frozen-lockfile
pnpm check:type
pnpm test:unit
pnpm build:ele
docker build -t "basic-framework-admin:$RELEASE" apps/web-ele
```

门禁与构建任一步失败就停止交付；其他适用前端检查按[脚本索引](../开发指南/脚本使用索引.md)执行。JAR为 `basic-framework-server/target/basic-framework-server.jar`，前端dist为 `apps/web-ele/dist`。前端 `pnpm build:docker` 串联构建与镜像装配，默认标签basic-framework-admin:local仅用于该脚本，正式交付另打版本标签。

[Java Dockerfile](../../后端代码/basic-framework-boot/basic-framework-server/Dockerfile)的构建上下文是server模块；[前端Dockerfile](../../前端代码/basic-framework-admin/apps/web-ele/Dockerfile)的上下文是apps/web-ele，两者只复制已有产物，不在目标机编译源码。记录JAR/dist/镜像及SQL的SHA-256和版本，实际秘密不打包。需要跨机器传送镜像时使用docker save/docker load，见离线说明。

## 准备目录与配置

在目标服务器准备独立发布目录。以下/opt路径与域名是布局示例，应替换为现场位置；RELEASE须与构建机一致。

```bash
export DEPLOY_ROOT=/opt/basic-framework
export RELEASE=your-release
install -d -m 700 "$DEPLOY_ROOT/config" "$DEPLOY_ROOT/backup"
install -d "$DEPLOY_ROOT/release" "$DEPLOY_ROOT/gateway"
docker network create basic-framework-net
```

已存在同名网络时先检查是否属于本框架，不重复创建或删除其他网络。将本次SQL放入release/basic_framework.sql，把应用镜像导入目标。配置文件在仓库外管理，以受控编辑器填写，chmod 600限制秘密文件访问。

创建config/mysql.env，以下密码字段必须填入现场生成的非空值，空值不能用于首次初始化：

```dotenv
MYSQL_DATABASE=basic_framework
MYSQL_USER=framework
MYSQL_PASSWORD=
MYSQL_ROOT_PASSWORD=
```

创建config/minio.env，填写现场MinIO管理凭据，不复用其他项目秘密：

```dotenv
MINIO_ROOT_USER=
MINIO_ROOT_PASSWORD=
```

创建config/redis.conf，替换占位密码；配置文件不会由应用自动生成：

```text
bind 0.0.0.0
protected-mode yes
appendonly yes
dir /data
requirepass <现场Redis密码>
```

Java的config/backend.env按[环境样例](../../后端代码/basic-framework-boot/.env.example)填写真实值。下面列出同容器网络方式的关键参数，密码与中间件配置一致，域名替换为现场站点：

```dotenv
SERVER_PORT=48080
SPRING_PROFILES_ACTIVE=prod
DB_HOST=basic-framework-mysql
DB_PORT=3306
DB_NAME=basic_framework
DB_USERNAME=framework
DB_PASSWORD=
REDIS_HOST=basic-framework-redis
REDIS_PORT=6379
REDIS_DATABASE=0
REDIS_PASSWORD=
MINIO_ENDPOINT=http://basic-framework-minio:9000
MINIO_ACCESS_KEY=
MINIO_SECRET_KEY=
MINIO_BUCKET=basic-framework
MINIO_SECURE=false
MINIO_REGION=us-east-1
MINIO_PUBLIC_URL=https://admin.example.com/files
ADMIN_UI_URL=https://admin.example.com/admin/
SERVER_FORWARD_HEADERS_STRATEGY=native
TRUSTED_PROXY_REGEX=(?!)
CORS_ALLOWED_ORIGIN=https://admin.example.com
```

没有独立从库时移除DB_SLAVE_*覆盖值，未提供的配置会回退主库；有从库时设置实际容器可达地址。已有MySQL/Redis/MinIO时将对应地址改为现场值，不再运行下文安装容器。容器127.0.0.1指容器自身；宿主机服务地址不能直接照搬到容器。

数据库新装、版本升级和备份恢复按[独立迁移流程](数据库初始化与迁移.md)执行，不由应用启动触发。CORS_ALLOWED_ORIGIN已绑定为逗号分隔的精确HTTP(S)来源，不能填通配符或URL路径，留空关闭跨域。Quartz默认配置未接入JDBC JobStore，infra_job表不等于QRTZ调度持久化。

TRUSTED_PROXY_REGEX默认不信任代理。部署时列出实际受控代理源地址，例如固定内网地址的正则 `172[.]18[.]0[.]2|172[.]18[.]0[.]3`，并限制后端只接受这些代理访问；两层代理必须都登记。`.env`按Java properties解析，正则用 `[.]` 避免反斜杠被不同环境文件解析方式吞掉。禁止framework转发模式、空规则或宽泛信任所有来源；未配置正确时短信IP预算会按直接连接的代理地址计算。

### `.env` 与 `--env-file` 的键名规则（同一份样例，两种语义）

`config/backend.env` 与开发机的 `.env` 使用同一份[环境样例](../../后端代码/basic-framework-boot/.env.example)，但读取方式不同，键名规则也不同：

- 开发机 `.env` 由 `optional:file:.env[.properties]` 按 **Java properties** 导入，只认两类键：① `application.yaml` 中带 `${大写键}` 占位符的键（`SERVER_PORT`、`DB_NAME` 等）；② 与 Spring 属性同名的小写键（`server.port`、`logging.level.com.basicframework`、`basic-framework.captcha.enable`）。两类之外的键被静默忽略：实测 `SPRING_DATASOURCE_URL` 指向不存在的库仍能启动，`LOGGING_LEVEL_COM_BASICFRAMEWORK=DEBUG` 得到 0 行 DEBUG，`.env` 同时写 `SERVER_PORT=48091` 与 `server.port=48092` 时应用在 48092 启动。
- `docker run --env-file` 把每一行注入为**真实进程环境变量**，由 Spring 宽松绑定解析，同一个属性可用 `basic-framework.captcha.enable`、`basic-framework_captcha_enable`、`BASICFRAMEWORK_CAPTCHA_ENABLE` 三种写法（实测都生效），`.env` 里无效的 `SERVER_FORWARD_HEADERS_STRATEGY` 在这里生效；真实进程环境优先级高于 `.env` 与 `application.yaml`。

上线前用[验收](#验收与故障排查)一节核对实际生效端口、数据源与日志级别；不能只看配置文件内容判断配置已生效。

## 已删除配置键与迁移说明

固定上游版本 `ruoyi-vue-pro` 的短信验证码属性带有 `beginCode`、`endCode` 两个取值字段，本框架已删除它们，验证码长度与取值上界固定在 `SmsCodeServiceImpl` 的常量上。因此下面两个键**不再有任何落点**：

| 旧键 | 新的取值来源 | 是否有替代配置键 |
| --- | --- | --- |
| `basic-framework.sms-code.begin-code`（上游前缀形态：`yudao.sms-code.begin-code`） | `SmsCodeServiceImpl` 的验证码长度与取值上界常量 | **没有** |
| `basic-framework.sms-code.end-code`（上游前缀形态：`yudao.sms-code.end-code`） | 同上 | **没有** |

删除前这两个键可以配置验证码取值范围；删除后无论配置成什么值都不会生效。旧部署配置不会因为携带它们而启动失败，也不会报绑定错误，只在启动日志里留下一条 `WARN`：

```text
WARN c.b.m.s.c.SmsCodeDeprecatedKeyReporter -- [reportRemovedKeys][检测到已删除的短信验证码配置键 basic-framework.sms-code.begin-code：该配置已移除且不生效，验证码长度与取值上界固定在 SmsCodeServiceImpl 的常量上，没有替代配置键，请从部署配置中删除]
```

迁移动作：

1. 从 `config/backend.env`、外部 `application.yaml`、`--env-file` 与命令行参数中删除上述键。留着无害，但会让每次启动都产生一条 `WARN`，掩盖真正的启动告警。
2. 不要把验证码取值范围重新做成配置项。当前取值范围是生成器常量，改成可配置会扩大配置面，需要单独的架构裁决。
3. 升级不依赖第 1 步：携带旧键的环境照常启动。只有在排查「改了配置没反应」时，才用这条 `WARN` 把原因指向已删除的键。

`WARN` 的检测按属性是否存在判断，YAML、system properties、环境变量（含 `BASIC_FRAMEWORK_SMS_CODE_BEGIN_CODE` 这类大写下划线写法）与命令行参数都会被命中；**唯一不在检测范围内**的写法是在 YAML 里把键名写成驼峰 `beginCode`——请统一使用上面列出的全小写连字符键名。

## 安装中间件与初始化数据库

以下命令只用于新的独立实例；已有库与数据卷不得用初始化流程重建。MySQL、Redis和MinIO不发布公网端口，只由应用内网或HTTPS网关访问。

联网安装默认使用下列已核验的镜像摘要；离线安装时先按离线说明将MINIO_IMAGE和MC_IMAGE设置为包内版本标签。本节只在变量尚未设置时采用默认值。

```bash
export MINIO_IMAGE="${MINIO_IMAGE:-minio/minio@sha256:14cea493d9a34af32f524e538b8346cf79f3321eff8e708c1e2960462bd8936e}"
export MC_IMAGE="${MC_IMAGE:-minio/mc@sha256:a7fe349ef4bd8521fb8497f55c6042871b2ae640607cf99d9bede5e9bdf11727}"
docker run -d --name basic-framework-mysql --restart unless-stopped --network basic-framework-net --env-file "$DEPLOY_ROOT/config/mysql.env" -v basic-framework-mysql-data:/var/lib/mysql mysql:8.0.46 --character-set-server=utf8mb4 --collation-server=utf8mb4_unicode_ci
docker run -d --name basic-framework-redis --restart unless-stopped --network basic-framework-net -v basic-framework-redis-data:/data --mount "type=bind,source=$DEPLOY_ROOT/config/redis.conf,target=/usr/local/etc/redis/redis.conf,readonly" redis:7.4.10-alpine redis-server /usr/local/etc/redis/redis.conf
docker run -d --name basic-framework-minio --restart unless-stopped --network basic-framework-net --env-file "$DEPLOY_ROOT/config/minio.env" -v basic-framework-minio-data:/data "$MINIO_IMAGE" server /data --console-address :9001
docker logs basic-framework-mysql
docker exec -it basic-framework-redis redis-cli --askpass PING
docker logs basic-framework-minio
```

MySQL日志出现ready for connections，Redis输入现场密码后返回PONG，MinIO日志无初始化错误，再继续。MySQL镜像的MYSQL_*只在空数据目录生效，改env不会重置已有账号密码。

先核对目标和空库状态，不在已有库导入整库快照：

```bash
docker exec -it basic-framework-mysql mysql -uroot -p
```

在MySQL交互界面输入现场root密码，执行：

```sql
USE basic_framework;
SELECT DATABASE(), @@hostname, @@port, VERSION();
SHOW TABLES;
```

退出客户端后，在可访问此实例的受控运维环境注入迁移凭据，按[空库安装](数据库初始化与迁移.md#空库安装)执行固定版本的 Flyway 命令。容器内地址与宿主地址不能混用；迁移入口须能连接已核实的同一库。新装无管理员账号，由[一次性初始化命令](数据库初始化与迁移.md#创建首个管理员)创建；用户、角色与菜单的平台必须匹配认证入口，不在 SQL 中添加默认口令或手工重设密码。已有库改走显式升级与恢复流程。

用临时mc容器交互创建桶和策略，凭据通过mc交互提示填写，避免进入命令参数或终端历史：

```bash
docker run --rm -it --network basic-framework-net --entrypoint /bin/sh "$MC_IMAGE"
```

在临时容器内执行，先完成alias交互，再建桶：

```sh
mc alias set framework http://basic-framework-minio:9000
mc mb --ignore-existing framework/basic-framework
mc anonymous set download framework/basic-framework
mc stat framework/basic-framework
exit
```

当前文件服务生成长期公开URL，桶因此允许公开下载，不能保存私人文件。生产可用MinIO管理工具建立限定桶的业务凭据后填入backend.env，不必长期让应用使用管理账号；密钥和策略同步验证。浏览器直传还需可达endpoint与桶级CORS，默认server上传不依赖浏览器到内网S3 endpoint。单文件、日预约预算、签名头、登记与补偿边界见[文件上传协议](文件上传协议.md)。

## 启动Java与管理前端

Java与前端加入同一网络，后端名称必须和前端模板的basic-framework-backend一致。

```bash
docker run -d --name basic-framework-backend --restart unless-stopped --network basic-framework-net --env-file "$DEPLOY_ROOT/config/backend.env" -v basic-framework-backend-logs:/basic-framework-server/logs "basic-framework-backend:$RELEASE"
docker logs --tail 100 basic-framework-backend
docker run -d --name basic-framework-admin --restart unless-stopped --network basic-framework-net "basic-framework-admin:$RELEASE"
docker logs --tail 100 basic-framework-admin
```

先确认Java Started，再运行前端，避免Nginx上游DNS尚不存在。日志默认在Java工作目录logs，容器卷负责保留，轮转和备份另行配置。两个应用不发布主机端口，由下一节网关提供入口。

直接运行JAR是另一种部署方式：工作目录放置受控.env，使用 `java -Dfile.encoding=UTF-8 -jar basic-framework-server.jar`，配置地址改为进程可达的中间件地址。若前端容器代理宿主机Java，加入 `--add-host basic-framework-backend:host-gateway`，并确认宿主机监听与防火墙。两种方式二选一，不能在相同端口重复启动。

生产构建VITE_BASE=/admin/、hash路由；运行配置从docker/app.config.js覆盖到站点根_app.config.js，API默认/admin-api，值对浏览器可见，禁止秘密。构建参数变更需重建dist，运行参数变更需更新配置制品并刷新页面。内层[Nginx模板](../../前端代码/basic-framework-admin/apps/web-ele/docker/nginx.conf)仅代理管理API与OAuth2，不包含旧媒体、AI、泛/api或App API。模板仅接纳http/https转发协议及1至65535的十进制端口，其他值回退自身连接；外层网关必须覆盖这些头，不能直接转发用户伪造值。

## 配置HTTPS网关

取得真实域名和证书，将fullchain.pem与privkey.pem放在受控config/tls目录。下列域名只是示例，必须替换；私钥权限限制并独立保管。

将下面内容写入gateway/default.conf。公开/files路径转发到MinIO桶路径，恰好与MINIO_PUBLIC_URL及代码自动补桶名一致；只有批准公开的数据使用此路径。

```nginx
server {
    listen 80;
    server_name admin.example.com;
    return 301 https://$host$request_uri;
}
server {
    listen 443 ssl;
    server_name admin.example.com;
    ssl_certificate /etc/nginx/tls/fullchain.pem;
    ssl_certificate_key /etc/nginx/tls/privkey.pem;
    client_max_body_size 33m;
    location /files/ {
        proxy_pass http://basic-framework-minio:9000/;
        proxy_set_header Host $http_host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_buffering off;
    }
    location /system/oauth2/ {
        access_log off;
        proxy_pass http://basic-framework-admin:80;
        proxy_set_header Host $http_host;
        proxy_set_header X-Forwarded-Host $http_host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Port $server_port;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
    location / {
        proxy_pass http://basic-framework-admin:80;
        proxy_set_header Host $http_host;
        proxy_set_header X-Forwarded-Host $http_host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Port $server_port;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

在网关配置与证书就位后，先做语法校验，再启用80/443入口：

```bash
docker run --rm --network basic-framework-net --mount "type=bind,source=$DEPLOY_ROOT/gateway/default.conf,target=/etc/nginx/conf.d/default.conf,readonly" --mount "type=bind,source=$DEPLOY_ROOT/config/tls,target=/etc/nginx/tls,readonly" nginx:1.27-alpine nginx -t
docker run -d --name basic-framework-gateway --restart unless-stopped --network basic-framework-net -p 80:80 -p 443:443 --mount "type=bind,source=$DEPLOY_ROOT/gateway/default.conf,target=/etc/nginx/conf.d/default.conf,readonly" --mount "type=bind,source=$DEPLOY_ROOT/config/tls,target=/etc/nginx/tls,readonly" nginx:1.27-alpine
```

已有80/443网关时复用其站点配置，不另起冲突容器；只把上述应用、文件路径和转发头并入实际代理。确保仅受信网关能访问内层前端与Java，不能直接相信公网客户端提供的X-Forwarded头。证书续期、入口防火墙、访问日志保留与上传大小由现场维护。

## 验收与故障排查

访问现场域名的/admin/，先检查资源和接口，再验收业务。不要把401响应当作认证成功，也不把端口存在当作全栈健康。

```bash
curl -I https://admin.example.com/admin/
curl -I https://admin.example.com/_app.config.js
docker logs --tail 100 basic-framework-backend
docker logs --tail 100 basic-framework-admin
docker logs --tail 100 basic-framework-gateway
```

_app.config.js应禁止缓存，静态资源路径匹配/admin/；生产构建产物实际请求 `/admin/_app.config.js`，内层模板对站点根路径与该路径都返回 `Cache-Control: no-store`，验收时不要只检查 `/_app.config.js`，否则会漏掉用户实际命中的分支。通过页面完成验证码、现场账号登录，检查/admin-api/system/auth/get-permission-info返回code=0及用户、角色、菜单和权限码。用未授权账号验证关键操作拒绝；用允许类型的测试文件验证上传、元数据列表和返回URL读取。短信、OAuth2与定时任务按现场配置另验，JAR或静态构建不会自动证明这些链路可用。

| 现象 | 优先定位 |
| --- | --- |
| Java配置绑定失败 | backend.env空值、引号、实际变量名、MinIOsecure布尔和region |
| 数据库认证/表错误 | 应用账号、库名、导入版本与主从地址 |
| 网关502 | 容器网络、上游名称、JavaStarted和前端Nginx日志 |
| 登录401/403或菜单缺失 | Token、平台类型、角色授权、组件映射与权限缓存 |
| 文件URL打不开 | MINIO_PUBLIC_URL与/files代理、桶公开策略、对象是否存在 |
| HTTPS重定向或回调错误 | 现场域名、ADMIN_UI_URL、证书与逐层X-Forwarded头 |
| 上传413或存储失败 | 两层网关限制、文件白名单、MinIO容量和桶权限 |

记录真实版本、命令、用例数量、失败、跳过和未验项。本文的安装步骤是部署操作规范，不代表已经在客户服务器安装验收。

## 停止升级与恢复

升级先保留旧镜像与配置，数据库结构或数据变化单独设计迁移。容器重启不重新初始化数据卷，不能通过删除卷升级应用。

停止应用用docker stop对应gateway、admin、backend容器；仅在确认本次实例身份后替换应用容器，保留中间件卷。升级顺序为备份、数据库兼容变更、装配新应用、验收；失败切回兼容镜像与配置。

数据库备份先进入本框架MySQL容器，交互输入密码：

```bash
docker exec -it basic-framework-mysql sh
mysqldump -uroot -p --single-transaction --routines --events --triggers --result-file=/tmp/basic-framework-before.sql basic_framework
exit
docker cp basic-framework-mysql:/tmp/basic-framework-before.sql "$DEPLOY_ROOT/backup/basic-framework-before.sql"
sha256sum "$DEPLOY_ROOT/backup/basic-framework-before.sql"
```

备份期间不并发改表结构，SQL备份含用户和令牌，受控保存。恢复先在隔离库验证；真实恢复前停止写入、确认目标，再docker cp备份入容器，用交互MySQL的USE目标库与SOURCE备份路径恢复。旧JAR回退不能替代数据库恢复，数据库导出不能恢复MinIO对象。

MinIO按现场备份策略保留对象、元数据与存储策略，在隔离桶校验恢复后再用于真实故障。不要对卷执行删除或清空作为排障。无数据库、对象与配置恢复证据时，只能说明应用版本可切回，不能承诺完整数据回滚。
