# basic-framework 离线部署包

## 摘要

在联网构建机准备Java与前端产物、应用与中间件镜像、目标缺少的运行资源和部署说明，在断网服务器导入并运行。目标不下载依赖、不编译源码；开发缓存不作为安装包。框架没有统一离线安装器，按实际包组织并逐项验收。

## 确定目标基线

先采集目标Linux发行版、版本、CPU架构、内核、Docker安装情况、容量、已有MySQL/Redis/MinIO与入口网关。没有系统和CPU信息就不能选择离线安装包或声明镜像兼容。

Java编译目标17，运行Dockerfile为eclipse-temurin:21-jre；前端为nginx:1.27-alpine，Node >=20.19.0与pnpm10.28.2只用于构建机。中间件安装基线及运行步骤见[服务器部署](部署说明.md)。固定镜像示例按linux/amd64使用，ARM64或其他平台需要取得对应镜像并独立验证，不把标签相同作为兼容证据。

## 交付包内容

按本次目标选择资源；已有兼容服务可登记复用，缺少资源必须在包内准备齐全。

| 内容 | 完成条件 |
| --- | --- |
| Docker离线安装资源 | 目标尚未安装时包含系统/CPU匹配的Engine、containerd、CLI及完整系统依赖，验证离线安装 |
| 应用镜像 | 本次basic-framework-backend与admin运行镜像，来自同源码版本和验证结果 |
| 中间件镜像 | 未复用时包含MySQL、Redis、MinIO、mc；TLS网关Nginx镜像 |
| JAR / dist | 按交付方式收集；应用镜像已包含产物时可不重复作为启动资源，但保留版本与哈希 |
| 第三方许可材料 | 后端先执行 `scripts/license/resolve_component_metadata.py` 与 `scripts/license/generate_third_party_notices.py`，产物 `META-INF/THIRD-PARTY-NOTICES` 与 `META-INF/licenses/` 随 JAR 分发；前端由生产构建自动写入 `LICENSE` 与 `THIRD-PARTY-NOTICES`。缺材料由[许可材料是发布强制步骤](#license-materials)的门禁拦截。核对口径见[交付物第三方许可实查](交付物第三方许可实查.md)；上游来源声明是否随包分发仍待有权者决定 |
| SQL | 目标版本、空库初始化与已有库升级边界明确，不混入客户真实数据或有效令牌 |
| 配置模板 | DB/Redis/MinIO、前端运行配置、网关示例；密码与私钥保持现场受控注入 |
| 部署说明与清单 | 实际包目录、启动停止、备份恢复、验证命令；逐文件SHA-256与镜像身份/平台 |

生产证书、真实.env、日志、上传文件、依赖缓存与个人备份不混入通用包。业务数据备份另行管理。框架不需要模型、GPU/NPU、Python服务、转码、媒体或当前未装配的RabbitMQ。

## 构建与镜像导出

联网构建机先执行服务器部署文档的Java/前端构建和门禁，装配最终应用镜像，再导出运行资源。第三方许可材料是发布**强制步骤**，见[许可材料是发布强制步骤](#license-materials)：漏生成会让发布链失败，不是退回零份材料。以下RELEASE须与本次发布一致，输出目录为本次新建交付目录。

```bash
docker image inspect "basic-framework-backend:$RELEASE" "basic-framework-admin:$RELEASE"
docker save -o application-images.tar "basic-framework-backend:$RELEASE" "basic-framework-admin:$RELEASE"
docker tag minio/minio@sha256:14cea493d9a34af32f524e538b8346cf79f3321eff8e708c1e2960462bd8936e "basic-framework-minio:$RELEASE"
docker tag minio/mc@sha256:a7fe349ef4bd8521fb8497f55c6042871b2ae640607cf99d9bede5e9bdf11727 "basic-framework-mc:$RELEASE"
docker save -o middleware-images.tar mysql:8.0.46 redis:7.4.10-alpine nginx:1.27-alpine "basic-framework-minio:$RELEASE" "basic-framework-mc:$RELEASE"
sha256sum application-images.tar middleware-images.tar
```

执行前确保所有指定镜像已取得且平台正确；不从docker save失败结果生成成功清单。应用镜像包含基础层，导入后无需再拉基础镜像；单独JRE或Nginx镜像不能替代已经装配应用的镜像。

按registry摘要直接导出时，归档可能没有可恢复的名称；docker load不能保证保留原registry RepoDigests。这里先给核验过的镜像加本次交付标签，并按标签导出。清单保留原registry摘要、平台和归档SHA-256，目标使用包内标签运行。

清单登记源码版本、JAR/dist/SQL哈希、镜像标签/摘要/平台以及实际质量结果。整个包的文件清单和哈希一致；Windows可执行文件不能作为Linux运行资源。Docker离线安装依赖由目标发行版决定，不能只提供一个通用deb或rpm就声明支持所有服务器。

## 许可材料是发布强制步骤

Maven的`<resources>`在目录不存在时静默跳过，**打包本身不会因为缺材料而失败**，交付物只会退回零份许可材料。因此发布链不能只依赖打包顺序，必须有一道按交付物实际字节裁决的独立门禁。本框架的发布命令按下列顺序执行，缺任何一步都会以非零退出结束。

后端：先生成材料、再打包、最后实查。生成步骤绑定的是**上一次打包产出的JAR**（要读它的第三方构件闭包），所以必须打两次包；第二次打包才把材料带进交付物。

```bash
cd 后端代码/basic-framework-boot
# 变量取绝对路径：第 3 条命令会先 cd 回仓库根，相对路径到那时已失效
# （与 CI 把 SERVER_JAR/MATERIALS/METADATA 全写成 ${{ github.workspace }} 绝对路径同理）。
SERVER_JAR="$PWD/basic-framework-server/target/basic-framework-server.jar"
MATERIALS="$PWD/basic-framework-server/target/generated-license-materials"
# 第 1 次打包：不带材料，用它的真实依赖闭包生成材料
./mvnw -B -ntp -DskipTests package
python -B -X utf8 ../../scripts/license/resolve_component_metadata.py \
  --jar "$SERVER_JAR" --allow-network --cache-dir /tmp/license-net-cache \
  --additional-evidence ../../scripts/license/known_license_evidence.json \
  --out /tmp/license-metadata.json
python -B -X utf8 ../../scripts/license/generate_third_party_notices.py \
  --metadata /tmp/license-metadata.json --jar "$SERVER_JAR" --out-dir "$MATERIALS"
# 第 2 次打包：材料进入交付物
./mvnw -B -ntp -Pquality-audit verify
# 实查：材料缺失、与闭包不符或被篡改都返回非零退出
cd ../..
python -B -X utf8 scripts/license/verify_license_materials.py --jar "$SERVER_JAR" --require-prepared
```

前端：许可材料由生产构建写入产物，交付压缩包打包后再实查一次，确保真正发出去的那份带着材料。

```bash
cd 前端代码/basic-framework-admin
pnpm build:recorded
pnpm release:pack
pnpm release:verify
pnpm release:smoke
pnpm quality:license:gate:release
```

两道门禁的判定口径：

| 门禁 | 入口 | 核对对象 | 失败情形 |
| --- | --- | --- | --- |
| 后端 | `scripts/license/verify_license_materials.py --jar <JAR> --require-prepared` | 交付JAR的`BOOT-INF/lib`实际条目、`META-INF/THIRD-PARTY-NOTICES`与`META-INF/licenses/`的实际字节 | 缺材料、条数与实际闭包不符、坐标与构件自述不符、正文摘要不符、正文不是文本、准备目录与JAR内材料不是同一份 |
| 前端 | `前端代码/basic-framework-admin/scripts/quality/license_materials_gate.py`（`--require-prepared` 追加交付压缩包核对） | 产物目录与交付压缩包的实际字节、本次构建的分块模块表、工作区已安装包清单 | 缺材料、条目数与分块实际引用的包不一致、坐标在工作区不存在、许可证声明与包清单不符、正文摘要不符 |

**许可证正文的取材口径**：生成器只收编"名字像许可证文档**且**内容确实是文本"的构件内条目。
上游类库里大量类文件恰好以 `LICENSE`/`NOTICE`/`COPYING` 开头（`LicenseMixin.class`、
`LicenseManager*ServiceMetadata.class`、`Notice.class`、`Copying*.class` 等），只按文件名前缀收编
会把第三方**编译产物**原样写进 `META-INF/licenses/`；这棵目录同时是 Maven 的 `<resources>`，
会被复制进 `basic-framework-server/target/classes`，JaCoCo 扫描该目录时按类文件魔数把它们当成真类分析，
覆盖率报告随即出现第三方包名，发布链被 `report-source-unmanaged` 卡死。
因此取材必须同时校验文件名与内容，`verify_license_materials.py` 的 `license-texts` 也把"正文确实是文本"
纳入判定：条款目录里混进编译产物时发布链直接失败。

**两道门禁都不生成、也不补写任何材料**：材料缺失只能由上面的前置步骤解决，门禁只负责拦住缺失。核对的计数口径见[交付物第三方许可实查](交付物第三方许可实查.md)；两项门禁在CI中分别位于backend与frontend作业的发布阶段，是发布证据的必需项，缺项会被门禁汇总拒绝。

## 目标安装与断网验收

在与目标兼容且禁止在线拉取的环境实际验证制品，不仅检查目录存在。

```bash
sha256sum -c checksums.sha256
docker load -i application-images.tar
docker load -i middleware-images.tar
docker image inspect "basic-framework-minio:$RELEASE" "basic-framework-mc:$RELEASE"
export MINIO_IMAGE="basic-framework-minio:$RELEASE"
export MC_IMAGE="basic-framework-mc:$RELEASE"
docker image inspect "basic-framework-backend:$RELEASE" "basic-framework-admin:$RELEASE"
```

checksums.sha256必须是本次全部交付文件的实际清单；不靠空清单证明通过。镜像导入后检查标签、摘要和平台，再按[服务器部署](部署说明.md)准备私有配置、安装中间件、授权数据库初始化/升级、运行Java和前端、配置HTTPS网关。

所有docker run命令在镜像名称前加入 --pull=never，例如 `docker run --pull=never ... "$MINIO_IMAGE" ...`，缺少制品时立即失败。保持上述MINIO_IMAGE和MC_IMAGE变量，服务器部署说明不会用默认在线摘要覆盖它们。

验证静态资源、运行配置、验证码登录、权限与菜单、关键拒绝路径、文件上传/登记/公开读取，以及本次使用的调度handler。断网环境检查无外部资源下载；短信和第三方OAuth2可能依赖外网，按业务提供内网替代或列明限制，不能随核心服务离线可用而宣称全部业务离线通过。

目标不执行Maven、pnpm或docker build补缺失制品。Docker缺失时先离线安装并验证Engine；配置、证书和密码由负责人受控提供，不在模板写固定秘密。完成停止、保留卷、应用版本恢复与隔离数据恢复验证后记录实际结果；没有测试的恢复项明确列为未验证。
