# 性能预算与基线

## 摘要

本文记录一次可重复的性能基线：在隔离环境、固定数据集和固定负载下测量登录、权限加载、分页查询、字典与用户 CRUD、文件上传及 8 并发分页，保留完整原始样本、数据库语句数和资源指标，并据此提出绝对预算与回归预算。预算数值尚未由有权者确认，`scripts/perf/budgets/baseline-2026-10-07.json` 的状态为 `proposed-awaiting-authority`，不能当作已批准的发布门槛。测量范围只覆盖后端 HTTP 链路；浏览器渲染、真实网络和容器运行时开销不在本次结论内。

读数按**源码身份**（Git 修订 + 源码内容摘要）绑定被测版本，理由与可复现性证明见[构件绑定](#binding)；`baseline-w7.json` 是 2026-10-05 的历史轮次，只作留档。

<a id="measurement-card"></a>

## 测量卡

| 字段 | 本次取值 |
| --- | --- |
| 目标与约束 | 主要指标为端到端毫秒（p50/p95/p99）与单次动作的数据库语句数；不可退化指标为资源驻留、线程与文件描述符不随迭代无界增长 |
| 用户动作与完成点 | 一次动作对应一个管理端操作并读取完整响应体；时间从发出请求到读完响应，不含浏览器渲染 |
| 输入与状态 | 固定合成数据集；每场景丢弃 10 次预热迭代，并在正式测量前丢弃一整轮遍历以消除冷 JIT 成本 |
| 环境 | 单机环回，应用与中间件同机；JVM `-Xms512m -Xmx1024m`，`SPRING_PROFILES_ACTIVE=prod` |
| 时间 | 计时包含服务端处理、数据库与对象存储往返、序列化与传输；不含客户端 MD5 与浏览器执行 |
| 资源 | 采样被测进程的 `VmRSS`、线程数与文件描述符数量；峰值与场景前后快照分别记录 |
| 判定 | 绝对预算核对 p50/p95/p99、语句数与并发吞吐；回归预算核对相对参考基线的增量和已验证噪声下限 |
| 行为 | 每个场景都要求业务码为 0；出现失败请求时该场景不允许给出通过 |
| 前置条件 | 关闭图形验证码；提高文件上传日预算以便重复测量 |
| 排除项 | 图形验证码校验、浏览器渲染与交互、真实网络、容器运行时开销、TLS、跨机数据库 |

<a id="environment-and-dataset"></a>

## 环境与数据集

测量在一台 20 vCPU、62 GiB 内存的 Linux 主机上完成，应用与 MySQL 8.4.10、Redis、MinIO 均在本机环回地址。应用使用 `prod` 配置启动并由独立的 JAR 进程提供服务；被测源码版本见预算文件中的 `applies_to.build`（Git 修订与源码内容摘要），被测构件的字节摘要与大小另记在报告 `build.jar_sha256`，只作「这次跑的是哪个 JAR」的观测值。

数据集由 `scripts/perf/seed_dataset.py` 生成，全部为固定常量：5000 行合成用户（`perf_user_%06d`，平台类型与登录入口一致）和 300 行合成字典类型。工具在写入前先删除同前缀的历史合成行，因此可重复执行；用户名与字典编码受唯一约束约束，软删除行仍占用编码，每次测量使用本次运行独立的探针前缀。

<a id="how-to-run"></a>

## 如何复现

测量分两轮：延迟轮在常规日志级别下运行，避免调试日志干扰计时；语句数轮打开 MyBatis DEBUG 日志，按迭代时间窗统计请求线程的语句执行。两轮结果由合并入口合成同一份报告后再判定。

```bash
python -B -X utf8 scripts/perf/seed_dataset.py --database <库名> --confirm-database <库名>
python -B -X utf8 scripts/perf/measure_endpoints.py --username <账号> --jar <JAR 路径> \
  --app-pid <JVM 进程号> --warmup-passes 1 --out 延迟报告.json
python -B -X utf8 scripts/perf/measure_endpoints.py --username <账号> --app-log <应用日志> \
  --samples 60 --warmup 5 --concurrency 1 --out 查询数报告.json
python -B -X utf8 scripts/perf/merge_reports.py --latency 延迟报告.json --sql 查询数报告.json --out 合并报告.json
python -B -X utf8 scripts/perf/source_identity.py --root . --json
python -B -X utf8 scripts/perf/perf_budget.py --report 合并报告.json --budgets scripts/perf/budgets/baseline-2026-10-07.json
```

`measure_endpoints.py` 默认按仓库根现场计算源码身份（`--source-root` 可指定别处，`--git-revision` 可显式给出修订）；`source_identity.py` 可以单独查看本次工作区会被绑定的源码身份。管理员口令通过环境变量 `BF_PERF_ADMIN_PASSWORD` 注入，不进入命令行参数、报告或日志；数据集脚本的数据库凭据同理。命令与退出码见[脚本使用索引](../开发指南/脚本使用索引.md#perf-checks)。

串行场景的 p95 相对偏差不超过 15.5%，多数低于 10%。并发端点的分位数波动达 51%，其吞吐更稳定（1225、1194、1405 次/秒，偏差约 9%），因此并发场景以吞吐下限判定，分位数只作观察。

资源指标取三次遍历的进程快照：启动后驻留内存约 0.86 GiB，稳定态 1.36–1.41 GiB，峰值 1.41 GiB（JVM 上限 1024 MiB 堆）；结束时线程 141–145、文件描述符恒为 131。单场景前后对比中，文件描述符增长恒为 0，线程波动不超过 5，驻留内存随迭代增长但随 1 MiB 上传场景出现最大 5.3 MiB 的增长，未观察到无界保留。

**结论性判断：** 基线内没有出现 N+1 或语句数随页深增长的情况（第 1 页与第 500 页均为 10 条语句），上传链路每次动作 2 条语句，登录 8 条语句。

<a id="budget-proposal"></a>

## 预算建议

预算分为绝对预算与回归预算，两者同时判定，避免只回答“比上次快”。

- **绝对预算**：`p50 ≤ 3×实测 p50`、`p95 ≤ 3×实测 p95`、`p99 ≤ 4×实测 p99`，并设下限（p50 20 ms、p95 25 ms、p99 40 ms）。参考值取三次遍历的最坏观测。下限用于亚 10 ms 端点：这类端点的绝对值很小，机器调度与文件系统抖动会占很大比例，直接按倍数收紧会产生与代码无关的失败；同时 3 倍留量仍能拦住数量级级别的真实退化。
- **回归预算**：`p95`/`p99` 相对参考基线允许 35% 增量（并发场景 60%，理由见波动数据），并额外校验预算不低于“参考基线 × 1.20”的已验证噪声下限，防止把预算定在噪声里。
- **语句数预算**：`sql_queries_median` 与 `sql_queries_p95` 取实测值的 1.4 倍向上取整，用于识别 N+1 与无界查询。
- **并发预算**：`min_throughput_per_second` 取三次最低吞吐的一半（600 次/秒）。
- **资源预算**：峰值驻留内存不超过 2 GiB，结束时线程与文件描述符不超过 300；单场景文件描述符增长不超过 0、线程增长不超过 32。

依据强度说明：绝对值来自本机实测，只在本文件 `applies_to` 声明的环境、JVM 参数、数据规模、并发模型与负载下成立。更换机器、运行时、数据规模或部署形态后，参考基线和绝对预算都要重新校准；把时间倍率套用到资源量或跨环境套用同一组绝对值都不成立。

<a id="binding"></a>

## 构件绑定

预算必须能证明「这组读数来自被校准的那份代码」，否则阈值比较没有意义。绑定方式在 `perf-budget/v2` 起改为**源码身份**：`git_revision`（Git 提交）与 `source_sha256`（源码内容摘要），方法标识 `git-source-id/v1`，范围标识 `backend-build-inputs/v1`。

**为什么不再按构件字节摘要绑定。** Maven 重建出来的 JAR 不可复现：同一提交在不同机器或不同时刻重建就得到不同 SHA-256。实测同一提交在云端运行器与本机分别得到 `c0a94da8…` 与 `71371e1b…`，因此按 `jar_sha256` 绑定会让 `build-mismatch` 在任何一次干净检出的 CI 上必现——它只能证明构建机换了，不能证明代码变了。`perf-budget/v1` 的该字段因此退役：`perf_budget.py` 见到以 `jar_sha256` 绑定或仍按 v1 结构提交的预算会直接以退出码 2 拒绝，并说明迁移方式，不会静默当成「无需核对构件」。

**可复现性。** 摘要由 `scripts/perf/source_identity.py` 计算：

| 性质 | 做法 |
| --- | --- |
| 与检出方式无关 | 只读文件内容，不读文件时间戳、不读构建产物、不依赖 Git 索引 |
| 与遍历顺序无关 | 纳入范围的文件按路径的 UTF-8 字节排序后逐项摘要 |
| 覆盖未提交改动 | 范围是 `后端代码/basic-framework-boot` 下的实际文件内容，新增、修改、删除、改名都改变摘要 |
| 排除构建噪声 | `target/`、`logs/`、`.git/`、`node_modules/` 及 `.class`/`.jar`/`.log` 等不参与摘要，重新打包不会让绑定失效 |

因此：同一份内容在任何干净检出上得到同一个摘要（可复现），改动任意一个字节立即得到不同摘要（是真绑定，不是常量）。

**两类绑定问题必须分开。** 判定按 `kind` 分列，处置不同：

| 情形 | `kind` | 退出码 | 含义与处置 |
| --- | --- | --- | --- |
| 绑定方法或范围不同 | `build-binding-mismatch` | 1 | 两次测量口径不可比，先统一口径 |
| 提交或源码摘要与预算声明不同 | `build-mismatch` | 1 | 测的不是被校准的那份代码，读数不能用于判定，重新校准而不是改代码 |
| 报告没有给出绑定证据 | `build-binding-missing` | 1 | 证据缺口，不算通过 |
| 预算自身声明不出可复现的绑定 | 配置错误 | 2 | 预算不可用；必须回填绑定后重新校准 |
| 绑定成立、其它指标超限 | `over-budget` / `regression-budget` 等 | 1 | 正常超标处置，结论里不会混入绑定项 |

**当前受控预算仍不可用作门禁。** `baseline-2026-10-07.json` 的 2026-10-07 校准发生在含未提交改动的工作区，当时未登记 HEAD，因此无法回填 `git_revision` 与 `source_sha256`；文件把绑定置为 `binding_state: unbound-pending-recalibration` 并保留退役的旧绑定值与原因。此时 `perf_budget.py` 返回退出码 2，而不是通过。重新校准与批准是下一步，需要目标环境，本轮不代为决定。

`ci_gate.py` 在发布链上再复核一次：性能结论必须带 `binding` 段、绑定方法为 `git-source-id/v1`、且实测提交等于本次发布的提交，否则拒绝发布证据。

<a id="verdict"></a>

## 超预算失败判定

`scripts/perf/perf_budget.py` 只消费“实测报告”和“受版本控制的预算文件”，不发请求、不读环境变量，因此同一对输入必然得到同一结论。退出码 0 表示全部满足，1 表示存在超预算或证据不足，2 表示报告或预算本身不可用。判定覆盖以下情形，任何一项都不能被当成通过：

| 情形 | 判定类型 | 说明 |
| --- | --- | --- |
| 任一场景缺失 | `scenario-missing` | 预算声明覆盖的场景必须在报告中出现 |
| 样本为空 | `not-measured` | 未执行测量不等于满足预算 |
| 存在失败请求 | `request-errors` | 失败样本不能作为延迟证据 |
| 缺少语句数或资源证据 | `sql-not-measured`、`resource-not-measured` | 预算要求该项证据时缺失即失败 |
| 构件绑定与预算声明不一致 | `build-mismatch`、`build-binding-mismatch` | 测的不是被校准的那份代码，数字不能用于判定 |
| 报告缺少构件绑定证据 | `build-binding-missing` | 没有绑定就无法证明来源，不算通过 |
| 预算未声明可复现的构件绑定 | 配置错误（退出码 2） | 预算不可用，须回填绑定并重新校准 |
| 负载或并发度不一致 | `workload-mismatch`、`concurrency-mismatch` | 条件不可比时数字无效 |
| 预算低于已验证噪声下限 | `budget-below-noise-floor` | 阈值落在噪声里属于预算不可用 |

### 退出码 2 也产出判定结论

真实缺陷（run 37777276336）：判定以退出码 2 结束时 `perf_budget.py` 只往标准错误写一行字，标准输出为空。被 `run_baseline.py` capture 成 `verdict.json` 后得到的是 0 字节文件，上传的 `perf-budget-verdict` 与 `perf-baseline-raw-reports` 制品里没有任何判定结论；日志里那句「无法读取」又掩盖了真正的原因（当时预算是 `binding_state: unbound-pending-recalibration`，即尚未在目标环境重新校准这一合法状态）。读日志的人分不清是预算待校准、是报告坏了、还是判定脚本崩了。

现在退出码 2 在 `--json` 下同样输出与正常判定同一结构的结论文档，`run_baseline.py` 再把它整段回显到日志，制品与日志读到的是同一份字节。结论新增两段：`exit_code` 与 `unavailable`。**退出码本身不变**：2 仍然是 2，既不改写成 0，也不折叠成 1。

`unavailable` 段把三类情形分列，`status` 为 `unavailable`（不是 `passed`），`checked` 为 0（一次也没有判定，不拿预算声明的场景数充数），`findings` 为空但**空 finding 不等于通过**；`binding.matched` 固定为 `null` 并附 `compared: false`，因为比较从未发生，写成 `true` 等于凭空造出一条绑定成立的结论。

| `category` | `kind` | 含义 | 结论里写明的处置 |
| --- | --- | --- | --- |
| `budget-binding-unbound` | `budget-binding-unbound` | 预算声明不出可复现的构件绑定 | 写出 `binding_state`；需要在目标环境重新校准，并把实测 `git_revision` 与 `source_sha256` 回填到 `applies_to.build` 后重跑；在此之前既不是通过也不是不通过，而是无法判定 |
| `report-invalid` | `report-unreadable`、`report-not-json`、`report-schema-unsupported`、`report-shape-invalid` | 输入报告不可读、不是合法 JSON、schema 不受支持或缺必需字段 | 指出是报告而不是预算；由合并步骤重新产出报告，不得手工编辑或改写 `schema` 绕过校验 |
| `budget-invalid` | `budget-unreadable`、`budget-schema-unsupported`、`budget-shape-invalid` | 预算文件本身不可读、schema 不受支持或缺必需字段 | 指出实际声明的是哪个 schema 以及迁移到 `perf-budget/v2` 的字段；退出码 2 时本预算不是门禁依据 |

`run_baseline.py` 的兜底话术本身也曾有第二个可观测性缺陷：文件不存在、文件存在但内容不是合法 JSON、文件可解析但结构不是判定结论，三者过去都打印同一句「无法读取」。现在逐类分开（「不存在」/「为空」/「不是合法 JSON」/「顶层不是对象」/「缺少 findings 列表」），读日志的人不必回到源码猜。

<a id="negative-controls"></a>

## 变异对照

A12 要求“性能超过确定的预算必须导致对应检查失败”。以下对照均在隔离环境执行，没有修改被测产品代码。

| 对照 | 注入方式 | 结果 |
| --- | --- | --- |
| 预算收紧 | 把 10 个场景的 p50/p95/p99 预算收紧到 25%，其余条件不变 | 退出码 1，14 项问题，全部为 `over-budget` |
| 真实变慢 | 在环回地址插入转发代理，对每次响应增加 120 ms 固定延迟 | 退出码 1，70 项问题，覆盖 `over-budget`、`regression-budget` 与吞吐下限 |
| 目标不可达 | 把被测地址指向未监听端口 | 退出码 2，未生成报告 |
| 缺少凭据 | 不注入管理员口令 | 退出码 2 |
| 场景无样本 | 把合并报告的样本列表清空 | 退出码 1，10 项 `not-measured` |
| 预算文件损坏 | 写入非法 JSON | 退出码 2 |
| 绑定不符 | 把预算绑定的 `git_revision` 或 `source_sha256` 改成别的值 | 退出码 1，`build-mismatch` |
| 绑定证据缺失 | 从报告的 `build` 段删掉 `source_sha256` | 退出码 1，`build-binding-missing` |
| 只改构件字节摘要 | 改写报告的 `jar_sha256`，源码身份不动 | 不影响判定：它已不是绑定依据 |
| 改一个源码字节 | 在受测源码树里改一个字节再算摘要 | 摘要改变，绑定确实生效 |
| 预算按旧方式绑定 | 预算里放 `jar_sha256` 或仍用 `perf-budget/v1` | 退出码 2，给出迁移说明 |
| 预算未在目标环境重新校准 | 直接用受控的 `baseline-2026-10-07.json`（`binding_state: unbound-pending-recalibration`）判定 | 退出码 2，结论文件写出 `budget-binding-unbound`、当前 `binding_state` 与重新校准的处置 |
| 输入报告不是合法 JSON | 把报告写成 `{不是 JSON` | 退出码 2，结论文件写出 `report-invalid` / `report-not-json` |
| 预算 schema 不受支持 | 把预算的 `schema` 改成 `perf-budget/v9` | 退出码 2，结论文件写出 `budget-invalid` / `budget-schema-unsupported` 与具体 schema |

判定逻辑的单元对照位于 `scripts/tests/test_perf_budget.py`，覆盖上述类型以及预算文件自身结构（状态、覆盖范围、p95 不低于 p50、p99 不低于 p95）与源码摘要的可复现性。注入延迟的对照工具为 `scripts/perf/fault_proxy.py`，只用于本地负对照证据，禁止用于交付或联调环境。

<a id="decisions"></a>

## 待有权者确认

以下事项属于业务预算决定，本轮的数值只是建议：

1. **绝对预算的数量级**：是否接受“3 倍 p95 / 4 倍 p99 + 下限”的留量。留量越小越容易拦住小幅退化，也越容易在换机器或换运行时后误报。
2. **回归容差**：串行场景 35%、并发场景 60% 是否符合可接受的误报代价；如需收紧，需要先在目标运行器上重复校准并重新确认噪声。
3. **并发口径**：是否以“8 并发、200–320 次请求”作为代表性并发模型，以及吞吐下限 600 次/秒是否合适。
4. **数据规模**：5000 行用户 + 300 行字典类型是否代表目标业务规模；规模变化后基线必须重测。
5. **预算适用范围**：本预算绑定单机环回环境。如要作为 CI 门禁，需要先在目标运行器上重新校准，或改为只看相对回归。
6. **是否纳入发布门禁**：已接入，接法与红绿读数见[发布门禁接入](#release-gate)。仍待有权者决定的是预算数值本身与其适用范围，不是接入方式。

<a id="release-gate"></a>

## 发布门禁接入

门禁按第三方许可材料实查的既有范式接入，共三处，缺一即拒绝发布证据：

| 位置 | 内容 |
| --- | --- |
| `scripts/workflow/ci_gate.py` 的 `RELEASE_CHECKS` | 新增 `backend-performance-budget`，计数方式 `perf_count` |
| `.github/workflows/ci.yml` 的 `backend` 作业发布阶段 | 新增「发布阶段后端性能预算实查」：真实测量一次，把 `verdict.json` 复制为 `perf-budget.json` |
| `release-backend.json` 生成步骤 | 读回 `perf-budget.json` 的状态与实测场景数，写进检查清单 |

判定分两层，互不替代：

- **测量判定**由 `scripts/perf/perf_budget.py` 给出，退出码 0 满足、1 超预算或证据不足或绑定不符、2 输入不可用；
  超预算、未测量、证据不可比、绑定不符在结论里分列为不同 `kind`，不会混为一类；结论的 `binding` 段记录期望与实测的源码身份。
- **权威判定**由 `ci_gate.py` 给出：它不读报告，只按受版本控制的
  `scripts/perf/budgets/baseline-2026-10-07.json` 独立复核「用的是哪一份预算、
  这份预算是否已获有权者批准、实测覆盖了多少场景、读数是否绑定本次发布的提交」。

**当前预算是红不是绿，而且红在两处。** 一是受控文件状态为 `proposed-awaiting-authority`、`approved_by` 为 `null`，因此即使测量判定通过、计数一致，`ci_gate.py` 也会以 `性能预算未获有权者批准，不能作为发布门槛` 拒绝发布证据并退出 1；二是该文件的构件绑定尚未回填（见[构件绑定](#binding)），`perf_budget.py` 本身就会以退出码 2 拒绝判定。两处都是正确且预期的行为：提案不是门槛，未绑定的读数也不是证据。门禁**不提供任何豁免开关或默认放行**，`--maintenance` 也不改变 release 的拒绝语义
（已实测）。要让 release 转绿，需要在目标环境重新校准、由有权者把源码身份与批准写回受控预算文件本身。

<a id="gaps"></a>

## 覆盖缺口

- 未测量浏览器渲染、首屏交互与前端资源加载；现有前端入口只提供构建体积分析与业务端到端，不构成浏览器性能门禁。
- 未测量真实网络、TLS、跨机数据库与容器运行时开销；A10 的容器验证只确认可用性，没有计时。
- 图形验证码被关闭，登录链路不含验证码校验成本；验证码接口本身未纳入预算。
- 未做长时间稳定性或内存泄漏压测；本次只观察单轮内的资源增长与回落。
- 未覆盖短信、OAuth2、定时任务与批量导入等链路。
- 并发场景的逐次语句数无法归属，只报告窗口总量；请求互相重叠时不能给出每次动作的语句数分位数。
