# 性能调查与证据

<a id="summary"></a>

## 摘要

通过当前实现、真实用户路径和可比较的测量判断性能优化是否成立。本页维护证据口径与结论边界；基准组织、资源测量和门禁校准见[性能基准与回归门禁](性能基准与回归门禁.md)。

<a id="authority"></a>

## 当前依据与历史线索

先明确目标版本、生产入口、实际消费方及已有测试，再核对相关变更的最终差异。PR 正文、评审建议和旧报告可以提供线索，但不能独立证明当前实现。

| 证据类型 | 可以支持的结论 | 必须保留的边界 |
| --- | --- | --- |
| 当前实现与本次测量 | 指定版本、负载和环境中的行为与开销 | 记录准确版本、环境、方法及原始结果 |
| 历史已合并实现 | 当时采用的机制与取舍 | 核对是否仍存在，不能默认沿用旧数字 |
| 未合并或被替代提案 | 候选假设及落选原因 | 不将提案当作现行实现或重新引入的授权 |
| 作者报告与估算 | 指定条件下的报告或预测 | 标明来源、时点与是否实测，不伪装成本次证据 |

<a id="endpoints"></a>

## 完成点与比较范围

先确定本次主要指标及不可退化指标，例如以峰值内存为目标，同时保持约定延迟、吞吐和正确性；不默认所有优化都以耗时下降为目标。指标的单位、方向、代表性负载、允许波动和判定依据须明确，不能在结果不利时临时更换目标或放宽约束。

从用户实际执行的动作确定完成点，例如请求返回、任务结果持久化、首次可交互或停止后资源全部释放。起点、终点、输入和必须完成的工作相同，前后结果才可比较。

组件测量用于归因，受影响真实路径的测量用于验证目标收益及不可退化约束。宣称端到端延迟改善时须有独立端到端实测，不能用阶段耗时之和替代，也不能把可能重叠的归因收益相加。CPU、内存或容量优化须在代表性负载中验证对应指标，并核对相关延迟、吞吐和行为约束；延迟未下降不能单独否定资源收益。排除网络、数据库或外部服务时列明，结论只代表已覆盖范围。

冷态与热态、首次升级与后续重开、只读与可写操作分别标注。解析后丢弃的结果不能与经过校验且保持可用的结果直接比较。完成后仍存活的对象和资源也是比较条件。

在本框架选择测量入口时，可按下表定义代表性场景。路径与权限条件由真实接口决定，负载数据使用专用测试库和测试桶；表中不是已经运行的基准或默认预算。

| 场景 | 完成点与负载 | 不可退化约束 |
| --- | --- | --- |
| 用户分页 | [UserController](../../后端代码/basic-framework-boot/basic-framework-module-system/src/main/java/com/basicframework/module/system/controller/admin/user/UserController.java) 的 `/system/user/page` 返回；固定记录分布、查询条件、页大小、身份和并发 | 结果/总数与权限一致，SQL 次数、尾延迟和数据库负载不超约定 |
| 服务端文件上传 | [FileController](../../后端代码/basic-framework-boot/basic-framework-module-infra/src/main/java/com/basicframework/module/infra/controller/admin/file/FileController.java) 的 `/infra/file/upload`；固定大小/类型，区分接口返回与 URL 实际可读 | 文件内容、元数据、可读性及失败补偿保持正确；计入存储和网络边界 |
| 管理表格交互 | 真实浏览器提交筛选到结果可操作；固定可见记录数和字段量，区分接口等待与界面更新 | 数据正确、交互可用，隐藏或分页操作没有推迟必要工作 |
| 前端交付资源 | `pnpm build:analyze` 的报告用于归因；生产站点另测首次加载、缓存后加载与交互 | 相同配置与入口，不以分析分块大小冒充浏览器响应时间 |

<a id="hypotheses"></a>

## 从现象形成可证伪假设

按观察到的延迟、CPU、分配量、保留内存、发生频率及证据置信度排序。每个候选指出真实消费方、疑似重复工作和最小可证伪干预；代码看起来复杂、大文件或未使用缓存都不足以认定瓶颈。

历史经验用于提出问题：是否过早展开紧凑数据、重复校验或复制、无界保留、过度订阅、反复扫描，或把未使用界面的工作提前执行。是否采用缓存、流式处理或延迟初始化，仍由当前所有权、信任边界、取消和释放语义决定。不要照搬历史身份注册表、缓存键或其他实现。

优先验证一个因果因素，再同时检查聚焦场景与相关端到端路径。吞吐、尾延迟和资源消耗存在取舍时明确报告，不能用单一最优指标概括收益。

<a id="conclusions"></a>

## 验证结论与停止条件

功能证据独立于性能计时，具体原则见[通用测试原则](../测试与可靠性/通用测试原则.md)。按目标项目实际契约验证受影响的输出、顺序、持久化、错误、取消、并发及资源释放；禁止通过跳过必要工作制造加速。刻意引入的可见差异须在已约定范围内并独立验证，不能仅用性能收益证明行为变更合理。

建立或修改性能回归判定时，须在隔离环境运行原始实现或受控负对照，确认失败来自目标开销；不能破坏用户工作区或发布故意引入的回归。无法安全建立对照时说明原因、替代证据与缺口，不声称已证明门禁有效。纯调查按实际证据说明现象与假设；比较优化前后时须保留基线、样本可比性和行为验证，不自动要求新建门禁或故意修改生产代码。已有门禁的执行及证据适用条件见[基准文档](性能基准与回归门禁.md#verdict)。

调查结论说明现象、假设、证据和缺口；优化结论补充目标指标及不可退化指标的前后绝对值、适用比率、行为验证和取舍；门禁建设额外报告预算依据及负对照的实际失败原因。各类结果均列出负载、准确版本与环境、完成点、资源语义、原始结果位置、实际检查和排除项。区分本次实测、仍适用的复用证据、历史报告与估算；基线或必要环境缺失时记录缺口，不编造优化前数字。未运行、失败和未知不能表述为通过，本地结果不能单独证明 CI 稳定。

保留负载定义、分析假设、采用及否决的方案、测量依据、取舍及验证缺口。原始样本保存在对应测量产物中，验证结论给出可定位引用；不得把框架维护流水账写入业务使用指南。

目标收益无法在代表性负载中复现或证据仍无法与噪声区分、不可退化指标超出约定、维护成本超过收益，或必要行为及资源语义无法解释和验证时，停止采用该候选并记录依据。延迟目标须有对应端到端收益；资源目标按实测资源改善和相关约束判断，不能仅因延迟没有下降就否决，也不能因资源改善而忽略不可接受的典型或尾部负载退化。仍需补测的候选标为待验证，不声称收益成立；进一步测量须在约定范围和资源预算内，后续问题单独评估。提交、发布和平台反馈等边界由[性能技能的交付规则](../../.agents/skills/weetion-speed-up-perf/SKILL.md#deliver-a-bounded-reviewable-result)维护。
