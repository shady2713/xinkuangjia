# 性能预算校准（2026-10-07）

## 摘要

本文是对 R16「性能与资源约束」的校准记录。核实结果是：仓库**已经存在**一份性能预算与基线文档及其预算文件，但验收矩阵仍把 R16 记为「无证据」，两者互相矛盾；目标环境只有 OS/JDK/中间件版本被规定，**数据规模、并发模型与负载定义没有规定**，本轮按既有基线的口径沿用并显式标注为待确认前提。

本轮在真实隔离环境（真实 MySQL 8.4.10、Redis、MinIO、真实后端 JAR、真实 HTTP 入口）完成三次完整遍历，得到 10 个场景的分位、语句数、资源与吞吐读数，并据此提出预算数值与退化门禁阈值。**所有数值都是建议，状态为待批准；本轮没有批准任何预算，也没有把任何阈值接入发布门禁。**

## 目标环境判定

仓库文档**已经规定**的部分（见[服务器部署](../部署/部署说明.md#环境与交付基线)与[离线部署包](../部署/构建离线部署包说明.md#确定目标基线)）：

| 维度 | 文档规定值 |
| --- | --- |
| 编译目标 | Java 17；构建机需兼容 JDK、Maven 3.8+ |
| Java 运行镜像 | `eclipse-temurin:21-jre` |
| 前端运行 | `nginx:1.27-alpine`；Node >= 20.19.0；pnpm 10.28.2（仅构建机） |
| MySQL | 框架使用 8.x；安装示例 `mysql:8.0.46` |
| Redis | 安装示例 `redis:7.4.10-alpine`；项目未固定补丁版本 |
| MinIO / mc | 固定镜像摘要；对应 MinIO `RELEASE.2025-09-07T16-13-09Z`、mc `RELEASE.2025-08-13T08-35-41Z` |
| 目标平台 | 固定镜像示例按 `linux/amd64`；其他架构须独立验证 |

仓库文档**没有规定**的部分（缺失前提，本轮不凭空假定）：

1. **数据规模**：没有规定生产用户量、字典类型量、单表行数上限。本轮沿用既有基线的 5000 合成用户 + 300 合成字典类型，来源是上一轮的测量口径，不是业务目标。
2. **并发模型**：没有规定在线用户数、峰值 QPS 或线程池规模。本轮沿用既有基线的「8 并发 × 40 次/线程」。
3. **业务目标 SLO**：没有规定对外承诺的 p95/p99、错误率上限或资源上限。R16 原始要求里「绝对与回归预算」需要业务目标才能定，本轮只能给出**从实测推算的建议值**。
4. **部署形态**：没有规定生产是裸 JAR 还是容器、是否多副本、是否跨机数据库。本轮全部为**单机环回**测量。

因此本轮校准只在下列基准环境说明下成立：

> **基准环境说明（2026-10-07）**：单机环回，Linux x86_64，20 vCPU / 62 GiB RAM，MySQL 8.4.10、Redis、MinIO 与被测后端同机运行于 `127.0.0.1`；后端以 `SPRING_PROFILES_ACTIVE=prod`、`-Xms512m -Xmx1024m` 运行；数据集为 5000 行合成用户 + 300 行合成字典类型；**测量期间同机有其他并发任务**（`load average` 观测区间 4.3–8.1）；被测构件为 `basic-framework-server.jar`，SHA-256 `1765ba01d60a232521f996255508c2c72d071f109cf56289526bd5c6ed4f2f0a`（132 923 937 字节），该 JAR 于 2026-10-07 12:54 由**含未提交改动**的工作区打包。

### 结构性结论

- **没有出现 N+1**：分页首屏与第 500 页同为 10 条语句，上传链路每次动作 2 条，登录 8 条，字典分页 7 条。

## 可重复性与噪声下限

三次遍历的 p95 相对偏差（`(max-min)/min`）：

| 场景 | p95 偏差 | 判定 |
| --- | --- | --- |
| user-crud | 1.1% | 稳定 |
| auth-login | 2.5% | 稳定 |
| dict-type-crud | 13.3% | 在 20% 内 |
| user-page-deep | 13.6% | 在 20% 内 |
| user-page-shallow | 13.8% | 在 20% 内 |
| permission-info | 14.3% | 在 20% 内 |
| file-upload-1m | 23.8% | 超出 20% |
| user-page-shallow-concurrent-8 | 26.2% | 超出 20% |
| dict-type-page | **46.5%** | 显著超出 |
| file-upload-64k | **53.3%** | 显著超出 |

**结论一：既有预算文件声明的 `noise_floor.p95_relative = 0.2` 在本机不成立。** 亚 10 ms 的端点（`dict-type-page` 4.0–5.9 ms、`file-upload-64k` 2.6–5.2 ms）在共享机器上受调度与文件系统抖动影响，分位数本身就不稳定。任何低于 50% 的 p95 回归容差都会在这两个场景上误报。

**结论二：FD 增长并非恒为 0。** 既有文档记录「文件描述符增长恒为 0」，本轮三次实测分别观察到 0、1、2 的增长。这不是内存泄漏证据（结束时 FD 三次都是 131），但足以说明在有并发负载的机器上，`max_fd_growth = 0` 会产生无法消除的红灯。

<a id="proposal"></a>

## 预算建议

候选预算文件：[baseline-2026-10-07.json](../../scripts/perf/budgets/baseline-2026-10-07.json)，`status = proposed-awaiting-authority`、`approved_by = null`、`supersedes = baseline-w7.json`。

### 建议规则

1. **绝对预算**：`p50 ≤ ⌈3×实测 p50⌉₅`（下限 20 ms）、`p95 ≤ ⌈3×实测 p95⌉₅`（下限 25 ms）、`p99 ≤ ⌈4×实测 p99⌉₅`（下限 40 ms）。参考值取三次遍历的最坏观测；下限用于亚 10 ms 端点，避免把机器抖动算成代码回归。
2. **回归预算**：逐场景 `relative_tolerance = max(35%, 该场景实测 p95 偏差向上取整到 5%)`；并发场景固定 60%。
3. **噪声硬下限**：`noise_floor.p95_relative = 0.55`，即实测最大值 53.3% 向上取整。判定器据此拒绝低于噪声下限的 p95 预算，避免把阈值定进噪声里。
4. **语句数预算**：实测值的 1.4 倍向上取整。
5. **吞吐下限**：三次最低吞吐的一半（1069.4 / 2 = 534.7），取 500 次每秒。
6. **资源预算**：峰值驻留 ≤ 2 GiB；结束时线程 ≤ 300、FD ≤ 300；单场景线程增长 ≤ 32；**单场景 FD 增长 ≤ 4**。

### 建议数值与依据

| 场景 | 参考 p95 | 预算 p50 | 预算 p95 | 预算 p99 | 回归容差 | 依据 |
| --- | --- | --- | --- | --- | --- | --- |
| auth-login | 55.1 | 155 | 170 | 230 | 35% | 实测最坏 55.1 ms 的 3 倍为 165 ms；实测偏差 2.5%，35% 是覆盖口令哈希与 JWT 签发路径抖动的余量 |
| permission-info | 6.1 | 20 | 25 | 40 | 35% | 3×6.1 = 18.3 ms，低于 20 ms 下限，按下限取值 |
| user-page-shallow | 7.8 | 20 | 25 | 40 | 35% | 3×7.8 = 23.4 ms，低于下限，按下限取值 |
| user-page-deep | 9.9 | 25 | 30 | 45 | 35% | 3×9.9 = 29.7 ms → 30 ms；与首屏同为 10 条语句，深页没有额外成本 |
| dict-type-page | 5.9 | 20 | 25 | 40 | **50%** | 3×5.9 = 17.7 ms 低于下限；容差取实测偏差 46.5% 向上取整 |
| dict-type-crud | 22.1 | 60 | 70 | 125 | 35% | 3×22.1 = 66.3 → 70 ms；4×30.9 = 123.6 → 125 ms |
| user-crud | 65.9 | 190 | 200 | 305 | 35% | 3×65.9 = 197.7 → 200 ms；4×76.1 = 304.4 → 305 ms；实测偏差 1.1%，余量充足 |

## 相对既有预算的变更

候选文件不修改 `baseline-w7.json`；下表逐项列出差异，便于逐条批准或驳回。

| 字段 | `baseline-w7.json` | 候选 | 变更理由 |
| --- | --- | --- | --- |
| `applies_to.build.jar_sha256` | `673f1623…` | `1765ba01…` | 旧值指向的构件已不在工作区，用当前构件测量必然 `build-mismatch` |
| `applies_to.environment` | 「20 vCPU / 62 GiB RAM / MySQL 8.4.10 …」 | 同上 + 补记「测量期间同机有其他并发任务」 | 共享机器是噪声来源，必须写进适用范围 |
| `noise_floor.p95_relative` | 0.20 | 0.55 | 三次实测最大偏差 53.3%；20% 在本机会持续误报 |
| `resources.max_fd_growth` | 0 | 4 | 实测 0/1/2；旧值来自单机安静环境 |
| 9 个场景的 `p50/p95/p99` | 见文件 | 按新实测重算 | 参考基线随之更新 |
| `dict-type-page.relative_tolerance` | 0.35 | 0.50 | 实测偏差 46.5% |
| `file-upload-64k.relative_tolerance` | 0.35 | 0.55 | 实测偏差 53.3% |
| `file-upload-1m.relative_tolerance` | 0.35 | 0.35 | 不变，实测偏差 23.8% 由噪声硬下限兜底 |
| 9 个场景的 `sql_queries_*` | 见文件 | **完全不变** | 语句数零偏差 |

**关于 `max_fd_growth` 的说明**：这是本轮唯一一处把阈值调宽的变更，因此单独列出。旧值 0 的依据是「单机安静环境下三次实测恒为 0」；本轮在同机有并发任务的条件下复测出现 1–2 的增长，而三次结束时 FD 都是 131，未见泄漏。**若无权者不认可共享机器的条件，应保留 0 并把该指标移出共享运行器的门禁**；本轮不代替该决定。

**关于上表第一行的更正（2026-10-08）**：本轮把「换一个构件 SHA-256」当作绑定问题的解法，这个方向是错的。`1765ba01…` 与 `673f1623…` 的差别不在代码，而在于 JAR 字节本身不可复现：同一提交在不同环境重建就得到不同摘要。绑定方式已改为源码身份，见下节；本轮记录的数值仍然有效，只是不能再用构件摘要来声明「这组读数对应哪份代码」。

## 构件绑定迁移（2026-10-08）

| 项 | 值 |
| --- | --- |
| 动机 | 构件字节摘要不可复现：同一提交实测 `c0a94da8…`（云端运行器）与 `71371e1b…`（本机），按它绑定会让 `build-mismatch` 在任何一次干净检出的 CI 上必现 |
| 新绑定 | `git-source-id/v1`：Git 修订 + `backend-build-inputs/v1` 范围的源码内容摘要 |
| 结构版本 | 预算与判定结论升到 `perf-budget/v2`；旧值与退役原因保留在预算文件的 `binding_migration` 与 `applies_to.build.retired_binding` |
| 阈值与容差 | **未改动**。本节只换绑定方式，不放宽任何预算、容差或下限，也不新增豁免 |
| 授权状态 | **仍是 `proposed-awaiting-authority`**，`approved_by` 仍为 `null` |

判定按 `kind` 分开两类绑定问题：`build-mismatch` / `build-binding-mismatch`（测的不是被校准的那份代码）与 `build-binding-missing`（报告根本没给绑定证据），两者都判失败；预算自身声明不出可复现绑定时以退出码 2 拒绝，避免「删掉绑定就恒通过」。发布链上 `ci_gate.py` 另外要求性能证据的 `binding` 段存在、方法为 `git-source-id/v1`、且实测提交等于本次发布的提交。

**为什么受控预算仍然红。** 本轮校准发生在含未提交改动的工作区，且当时未登记 HEAD：按提交历史，2026-10-07 12:54 之前的最后一个提交是 `9ca041aeefa1c27588413c65c6e60da6e9589e73`（2026-10-06 22:01:42），但它不能代表被测源码的实际内容。因此 `baseline-2026-10-07.json` 的绑定置为 `binding_state: unbound-pending-recalibration`，`perf_budget.py` 对它返回退出码 2；重新校准与批准是下一步，需要目标环境，本轮不代为决定。设计、可复现性证明与负对照见[性能预算与基线 § 构件绑定](性能预算与基线.md#binding)。

<a id="verdict"></a>

## 超预算判定与处置

判定入口 [perf_budget.py](../../scripts/perf/perf_budget.py) 只消费「实测报告」与「受版本控制的预算文件」，不发请求、不读环境变量，同一对输入必然得到同一结论。

| 退出码 | 含义 | 处置 |
| --- | --- | --- |
| 0 | 全部场景满足绝对预算、回归预算、语句数与资源预算，且构件绑定成立 | 记录本次报告摘要与源码身份，作为该次发布的性能证据 |
| 1 | 存在超预算或证据不足（`over-budget`、`regression-budget`、`request-errors`、`scenario-missing`、`not-measured`、`sql-not-measured`、`resource-not-measured`、`build-mismatch`、`build-binding-mismatch`、`build-binding-missing`、`workload-mismatch`、`concurrency-mismatch`、`budget-below-noise-floor`、`resource-growth`） | **不得发布**；先看 `kind`：`build-mismatch`/`build-binding-mismatch`/`build-binding-missing`/`workload-mismatch`/`concurrency-mismatch` 说明证据不可比或根本不是被校准的那份代码，应重新校准而不是改代码；`regression-budget` 需确认是否落在已验证噪声内（对照 `noise_floor` 与本文[噪声下限](#noise)表）；`sql-not-measured`、`not-measured` 一律不算通过 |
| 2 | 报告或预算本身不可用（不可读、schema 不符、预算未声明可复现的构件绑定、被测目标不可达） | 视为未执行测量，不得记为通过；受控预算当前就属于这一类，见[构件绑定迁移](#binding-migration) |

判定为红时的处置顺序固定为：**先确认可比性 → 再确认是否落在已验证噪声内 → 仍超标才定位代码**。跳过前两步直接改代码，会把共享机器抖动当成回归去"优化"。

**当前门禁接入状态（如实记录）**：`perf_budget.py` 仍未登记进 `run_checks.py` 任一分组（合并请求不受影响），但**已进入 `ci_gate.py` 的发布链**：`RELEASE_CHECKS` 新增 `backend-performance-budget`，`backend` 作业发布阶段真实测量一次并写出 `perf-budget.json`，缺项即拒绝发布证据。因此上述退出码**会阻断发布**。接入后 release 因「预算未获有权者批准」而红，这是正确且预期的行为，接法见[性能预算与基线 § 发布门禁接入](性能预算与基线.md#release-gate)。是否接入、以何种负载接入原本属有权者决定，见[待有权者决定](#decisions)。

<a id="negative-controls"></a>

## 负对照

校准出来的预算必须证明「超标会红」，否则只是数字。本轮执行了三类对照，全部在隔离环境完成，未修改被测产品代码。

| 对照 | 注入方式 | 期望 | 实测 |
| --- | --- | --- | --- |
| 回归基线自洽 | 三次实测报告分别对照候选预算 | 全部通过 | 三次均 `passed`，退出码 **0**，各 10 项检查 |
| 真实变慢 | `--fault-delay-ms 120`，在环回地址插入固定 120 ms 转发延迟 | 超预算失败 | 见下表 |
| 预算收紧 | 把候选预算的 p50/p95/p99 收紧到 25% | 超预算失败 | 由 `scripts/tests/test_perf_budget.py` 的既有单元对照覆盖；本轮未新增实跑 |

真实变慢对照（`--fault-delay-ms 120`，完整两轮，耗时 1044.4 秒，退出码 **1**，共 50 项问题：30 项 `over-budget` + 20 项 `regression-budget`）：

| 场景 | 无延迟 p95（三次最坏） | 注入 120 ms 后 p95 | 预算 p95 | 判定 |
| --- | --- | --- | --- | --- |
| auth-login | 55.1 | 185.4 | 170 | **超预算**（4 项） |
| permission-info | 6.1 | 136.2 | 25 | **超预算**（5 项） |
| user-page-shallow | 7.8 | 137.8 | 25 | **超预算**（5 项） |
| user-page-deep | 9.9 | 134.8 | 30 | **超预算**（5 项） |
| dict-type-page | 5.9 | 128.7 | 25 | **超预算**（5 项） |
| dict-type-crud | 22.1 | 525.1 | 70 | **超预算**（5 项） |
| user-crud | 65.9 | 451.1 | 200 | **超预算**（5 项） |
| file-upload-64k | 5.2 | 132.4 | 25 | **超预算**（5 项） |
| file-upload-1m | 13.4 | 141.9 | 45 | **超预算**（5 项） |
| 并发-8 | 9.6 | 135.6 | 30 | **超预算**（6 项，含吞吐下限：1069.4 → **61.9 次每秒**） |

**10 个场景全部变红**。多请求场景（`dict-type-crud`、`user-crud` 一次动作含 4 个请求）的注入延迟按请求数累加，因此达到 525.1 ms 与 451.1 ms。这证明候选预算的绝对项与回归项都真实生效，不是「怎么测都通过」的数字。

注入延迟后各场景的业务错误仍为 **0**，说明红灯来自预算判定而不是测量失败——两者必须区分开，这也是[判定表](#verdict)里 `request-errors` 与 `over-budget` 分列的原因。

对照工具为 `scripts/perf/fault_proxy.py`，本轮由 `run_baseline.py --fault-delay-ms` 调用，**只用于本地负对照证据，禁止用于交付或联调环境**。判定逻辑的单元对照位于 `scripts/tests/test_perf_budget.py`；编排契约的单元对照位于 `scripts/tests/test_perf_run_baseline.py`（31 项），覆盖隔离资源只回收本次取得的、报告不得落在仓库内、两轮必须重启后端并切换 MyBatis 日志等前提。

## 本机未测项

以下项目在本机**没有测量**，不得据本文认为已验证：

| 未测项 | 原因 |
| --- | --- |
| 浏览器渲染、首屏交互、前端资源加载 | 本轮只测后端 HTTP 链路；仓库现有前端入口只提供构建体积分析与业务端到端，不构成浏览器性能门禁 |
| 真实网络、TLS、跨机数据库、容器运行时开销 | 本机为单机环回；A10 的容器验证只确认可用性，没有计时 |
| 图形验证码成本 | 测量前置条件关闭验证码（`BASIC_FRAMEWORK_CAPTCHA_ENABLE=false`）；验证码接口本身未纳入预算 |
| 长稳与内存泄漏 | 只观察单轮内的资源增长与回落，未做长时间压测 |
| 短信、OAuth2、定时任务、批量导入链路 | 本轮 10 个场景不覆盖 |
| 并发场景的逐次语句数 | 并发请求互相重叠，无法归属到单次迭代，只报告窗口总量 |
| 目标 CI 运行器上的表现 | 本轮全部在本机执行；共享运行器的物理隔离情况未核实，不能把本机数值直接当作 CI 门禁 |
| 生产业务数据规模 | 只用合成数据；真实数据分布（选择性、索引命中）未覆盖 |

<a id="decisions"></a>

## 待有权者决定

以下都是预算与门禁的业务决定，**本轮只提出建议，没有批准任何一项**：

1. **目标环境缺口的补齐**：数据规模、并发模型、业务 SLO、部署形态四项在仓库文档中没有规定。本文的数值只在[基准环境说明](#environment)下成立，业务目标确定后必须重新校准。
2. **预算数值本身**：9 个场景的绝对预算、回归容差与语句数预算是否接受；特别是 `dict-type-page` 50%、`file-upload-64k` 55% 这两个为容纳共享机器噪声而放宽的容差，是否接受，还是改为「在独占运行器上重新校准后再收紧」。
3. **`max_fd_growth` 由 0 改为 4**：见[变更说明](#delta)。若不认可，应保留 0 并把该指标移出共享运行器门禁。
4. **是否接入发布门禁**：接入方式已定并已实现（照第三方许可材料实查的范式）：`ci_gate.RELEASE_CHECKS` 新增 `backend-performance-budget`，发布阶段真实测量并写出 `perf-budget.json`，缺项即拒绝。仍需有权者决定的是**失败是否应当直接阻断发布**——本轮按「阻断」实现，且未提供任何豁免开关；以及**由谁复核并批准预算**（批准只能写进受控预算文件本身）。
5. **`user-crud` 与 `dict-type-crud` 的判定口径**：这两个场景一次动作含 4 个请求，注入延迟按请求数累加，负对照中分别达到 451.1 ms 与 525.1 ms。预算按「一次用户动作」判定是有意选择（面向用户体验），但它与「单请求延迟」不是同一口径，需要决定对多请求场景是否单列单请求指标。
6. **既有预算文件的处置**：`baseline-w7.json` 绑定的是已不存在的构件。是保留为历史记录、由候选文件取代，还是按新构件重新签发，需要决定。
7. **是否补做浏览器与长稳测量**：属于新增范围，需要单独授权与预算。
